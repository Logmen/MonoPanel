# MonoPanel

[English](README.en.md) · Русский

Панель управления веб-сервером для Debian/Ubuntu и RHEL-семейства: сайты, PHP, базы,
TLS, почта, бэкапы, firewall и переезд между серверами — одним статическим бинарником,
без рантайма, агентов на других языках и внешних зависимостей.

[![ci](https://github.com/Logmen/MonoPanel/actions/workflows/ci.yml/badge.svg)](https://github.com/Logmen/MonoPanel/actions/workflows/ci.yml)
[![release](https://img.shields.io/github/v/release/Logmen/MonoPanel)](https://github.com/Logmen/MonoPanel/releases)
[![license](https://img.shields.io/badge/license-Apache--2.0-blue)](LICENSE)
[![go](https://img.shields.io/badge/go-1.27-00ADD8)](go.mod)

Панель ставится одним пакетом, поднимает свой HTTPS-порт и не зависит от системного
nginx: если конфигурация сайта сломается, панель останется доступной и починит её.
Web UI, CLI, TUI и интеграции работают через один и тот же REST API — то, что можно
сделать мышкой, можно сделать и скриптом.

Состояние: **0.8.19**, ежедневно используется на боевом сервере с несколькими сайтами
и почтой. Разработка идёт быстро; до 1.0 возможны несовместимые изменения.

## Установка

```bash
curl -fsSL https://monopanel.app/install.sh | sh
mp setup
```

Адрес ведёт на [packaging/install.sh](packaging/install.sh) из этого репозитория.
Скрипт определяет ОС и архитектуру, скачивает пакет последнего релиза, сверяет
контрольную сумму и ставит его. Можно и вручную — `.deb` и `.rpm` для amd64 и arm64
лежат в [релизах](https://github.com/Logmen/MonoPanel/releases).

`mp setup` создаёт служебного пользователя, каталоги, базу, самоподписанный TLS и
администратора, после чего печатает адрес панели и пароль. Обновления панель берёт
из релизов того репозитория, из которого собран пакет (`mp update` показывает его как
«из сборки»); менять эту настройку нужно только для форка или приватного репозитория.

Скрипту не нужен GitHub API — тег последнего релиза берётся из редиректа
`/releases/latest`, файлы качаются по прямым ссылкам, так что анонимный лимит API
(60 запросов в час на адрес) установке не мешает. Так же поступает и сама панель при
проверке обновлений, если лимит исчерпан.

Нужны root, systemd и одна из систем: Debian 12/13, Ubuntu 22.04/24.04/26.04,
AlmaLinux, Rocky Linux или Oracle Linux 9/10. Вся матрица прогоняется на
[тестовой площадке](docs/08-testbed.md): установка панели, nginx, PHP, Percona и
сценарий e2e проходят на всех одиннадцати ОС.
На EL SELinux остаётся в enforcing: панель сама настраивает контексты и булевы под
хостинг и ставит свой небольшой модуль политики. На Ubuntu PHP ставится из `ppa:ondrej/php`;
если у PPA нет сборок для этого релиза Ubuntu, — из `packages.sury.org`, собственного репозитория того же
сопровождающего, а если нет и его, — из самой Ubuntu.

## Быстрый старт

```bash
mp setup --admin-password '…'   # или без пароля: сгенерирует и покажет
mp status                       # панель, хост, сервисы, задачи
mp stack install nginx
mp config set web.hostname panel.example.com --restart
mp ssl panel issue              # Let's Encrypt для имени панели, сразу на :8443

mp user add alex --generate --shell
mp php install 8.4              # + 7.4, 5.6 … параллельно
mp stack install percona        # Percona Server 8.4, root через auth_socket

mp site add example.com --user alex --www --preset wordpress
mp site add old.example.com --user alex --php 7.4 --mode apache
mp site add app.example.com --user alex --mode proxy --backend http://127.0.0.1:3000
mp db create shop --user alex   # пароль сгенерирует и покажет
mp stack install valkey && mp valkey add cache --user alex   # свой Valkey аккаунта
mp firewall enable && mp stack install fail2ban
mp backup target add local1 --repo /var/backups/monopanel --schedule daily

mp mail install --hostname mail.example.com   # postfix + dovecot + opendkim
mp mail domain add example.com --user alex    # + ключ DKIM
mp mail box add ivan@example.com --quota 2048
mp mail domain dns example.com                # что прописать в DNS
mp mail webmail webmail.example.com --user alex --port 2096   # Roundcube

# переезд аккаунта с другого сервера с MonoPanel
mp migrate grant user:alex                        # на старом сервере
mp migrate plan --source https://old:8443 --token … --scope user:alex
mp migrate run  --source https://old:8443 --token … --scope user:alex
# … или с BitrixVM и FASTPANEL: по ssh, источник только читается
mp migrate run --from bitrixvm  --source root@old.example.com --domain shop.example.com
mp migrate run --from fastpanel --source root@old.example.com --scope user:shop

mp                              # TUI-меню: разделы как в Web UI, любое действие — формой команды mp
```

Удалённо: `mp --server https://host:8443 --token <token> status`
(токен: `mp token create`); так же открывается и TUI — `mp --server … --token …`.

## Что умеет

Всё перечисленное проходит через один REST API и доступно в Web UI, CLI и TUI: у каждой
операции API есть команда `mp` и место в Web UI, а TUI предлагает каждую команду `mp`
формой. Это проверяет `go test ./internal/parity/` в `make test` и CI. Исключений
немного, и они намеренные: вход в браузере и консоль — только в Web UI, установка и
служебные роли бинарника — только в `mp`, `mp update trust` и `mp config … --local` —
только от root на сервере ([полный список](docs/04-cli-tui-api.md#1-принцип)).
Под каждым заголовком — команды `mp` этой области.

### Сайты

`mp site add|set|list|show|apply|fix|suspend|unsuspend|rm|logs|presets|move-ip`, `mp site nginx|php|tls`, `mp selinux`

- Три режима: `fpm` (nginx → php-fpm), `apache` (nginx → Apache аккаунта → php-fpm через mod_proxy_fcgi: у каждого аккаунта с сайтами в этом режиме свой Apache, `monopanel-apache@<логин>`, на своём адресе `127.100.x.y:81`, дочерние процессы — от имени аккаунта) и `proxy` (nginx → свой backend).
- У каждого сайта свой пул php-fpm, ACL для группы `monopanel-web`, страница-заглушка и автоматический сертификат; приостановленный сайт отдаёт страницу 503.
- Сайт слушает и на IPv6-адресе сервера (`--ipv6`, по умолчанию первый глобальный; `none` — только IPv4). Заголовки безопасности одним флагом (`--security-headers`: X-Content-Type-Options, X-Frame-Options, Referrer-Policy), ограничение частоты запросов с одного адреса на динамические страницы (`--rate-limit 10` — запросов в секунду, статика не считается, лишним — 429).
- Доступ только с перечисленных адресов (`--allow`), HSTS при принудительном HTTPS, свои директивы nginx в `sites/<domain>.d/*.conf`. `mp site nginx <domain> --set файл` записывает их с проверкой `nginx -t` и откатом, а то, что панель не принимает (`fastcgi_pass` не на пул сайта, `fastcgi_param PHP_VALUE` и подобное), отклоняет до записи и так и говорит; `mp site php <domain>` показывает действующие PHP-параметры и откуда каждый взялся.
- Пресеты CMS `--preset wordpress|joomla|bitrix|opencart` (`mp site presets`): свои location в nginx (ЧПУ, `/api` Joomla, `urlrewrite.php` Битрикса, `_route_` OpenCart, закрытые служебные каталоги, запрет PHP в uploads) и PHP-параметры по умолчанию. Битрикс настраивается по правилам BitrixVM: opcache на 100 000 файлов, без open_basedir.

### PHP 5.6–8.5

`mp php list|install|remove`, `mp php ext list|enable|disable`, `mp php ini [set|unset]`

- Ветки из Sury, PPA ondrej или Remi, сколько угодно параллельно; у каждой свой php-fpm и `99-monopanel.ini`.
- Параметры php.ini складываются из слоёв: панель → глобально (`mp php ini set`, страница PHP) → пресет → сайт (`mp site set --ini`). Любой параметр меняется для одного сайта или для всех сразу. Глобальный слой попадает и в `99-monopanel.ini` ветки, который читает PHP из командной строки, — с ним те же значения получают задания cron; расхождение видно в `mp doctor`.
- Расширения ветки включаются и выключаются (Debian/Ubuntu — `phpenmod`/`phpdismod`, EL — правка `extension=` в ini ветки Remi, затем перезапуск php-fpm). Действует на все сайты ветки: мастер php-fpm один на версию.
- Расширения, которые есть в репозитории, но не установлены (memcache, redis, imagick …), показываются в том же списке; включение ставит пакет.

### CMS

`mp cms list|install <домен> <cms>`

- Ставит WordPress, Joomla, OpenCart и 1С-Битрикс в существующий сайт: дистрибутив берётся с сайта производителя, распаковывается в docroot и отдаётся клиенту, создаётся своя база, сайт получает пресет.
- Установщик — штатный: wp-cli, CLI-установщики Joomla и OpenCart, веб-мастер Битрикса, который панель проходит сама. Для Битрикса — пробная редакция Старт, Стандарт, Малый бизнес или Бизнес, чистая установка из Маркетплейса или демо-сайт.
- Оборвавшуюся загрузку дистрибутива панель продолжает с места обрыва, если сервер отдаёт файл по частям (HTTP Range); то, что успело распаковаться до сбоя, отдаётся клиенту.
- Доступы администратора показываются один раз. В Web UI — вкладка «CMS» на странице сайта.

### Базы данных

`mp stack install percona|mysql`, `mp db create|list|passwd|rm`, `mp db engine [tune]`, `mp db config [set|unset]`

- Percona Server или MySQL 8.4 LTS; root через `auth_socket` (на EL панель сама переводит его с временного пароля пакета), настройки под объём памяти.
- Параметры сервера меняются в панели: значение встаёт на место панельного в `zz-monopanel.cnf`, перед перезапуском — `mysqld --validate-config`, при неудачном запуске прежние параметры возвращаются сами.
- Базы называются `<login>_<name>`, сгенерированные пароли проходят `validate_password`; `mysql_native_password` включается только при PHP < 7.4.

### Valkey на аккаунт

`mp stack install valkey`, `mp valkey add|restart|rm cache|sessions [--user <login>] [--memory МБ]`, `mp valkey list`, `mp site set <домен> --sessions valkey|files`

- У аккаунта два отдельных экземпляра: кеш (allkeys-lru, без записи на диск) и PHP-сессии (volatile-lru, снимок раз в минуту — сессии переживают перезапуск).
- Каждый — systemd-юнит `monopanel-valkey-<login>-<cache|sessions>` от имени пользователя с лимитом памяти. Слушает только unix-сокет `/run/monopanel-valkey/<login>-<cache|sessions>/valkey.sock` с правами 600: ни другие аккаунты, ни веб-сервер к нему не подключатся, TCP-порта нет вовсе. На EL экземпляры работают в домене SELinux `redis_t`.
- Valkey берётся из дистрибутива (где его нет — Ubuntu 22.04, Debian 12 без backports — Redis с тем же протоколом); общий экземпляр из пакета выключается.
- Сессии сайта переводятся в Valkey одной настройкой (нужно расширение redis у ветки PHP сайта); пока сайт держит там сессии, ни экземпляр, ни расширение не удалить. Сессии блокируются phpredis (`redis.session.locking_enabled`, как у файлов), ключи `redis.session.*` настраиваются в PHP-параметрах.
- В Web UI — кнопка valkey на странице «Пользователи» и поле «PHP-сессии» в настройках сайта.

### TLS

`mp ssl issue|import|list|show|renew|rm`, `mp site tls <домен>`, `mp ssl panel issue|import|self-signed`, `mp web tls`, `mp dns-provider add|list|rm|types`

- lego: HTTP-01 через webroot nginx, DNS-01 (Cloudflare, Hetzner, DigitalOcean, Gandi, deSEC, Namecheap, RFC2136) для wildcard, автопродление за 30 дней.
- Сертификат самой панели и сертификаты сайтов ведутся раздельно: панель заказывает только для своего имени и подхватывает его на лету, сайт заказывает для домена с алиасами и сам переключается на HTTPS. Занятый сертификат не удалить.
- Готовые сертификаты (купленные, корпоративные, выпущенные в другом месте) — `mp ssl import --cert --key` или кнопка «импорт» у сайта на странице SSL. Сайты, чьи имена сертификат покрывает, переходят на него; сертификат Let's Encrypt панель дальше продлевает сама, любой другой — нет.

### Почта

`mp mail install|status|settings|apply|domain|box|alias|webmail`

- postfix + dovecot + opendkim: домены, ящики (пароли и квоты в панели, Maildir у `vmail`), алиасы и catch-all, IMAP/POP3/submission с сертификатом панели, подпись DKIM, sieve-фильтры.
- Домен «только отправка»: почту домена принимает провайдер, здесь — подпись DKIM и отправка писем сайтов. Домен-приёмник (`--lenient`) примет письма и от криво настроенных отправителей.
- `mp mail domain dns` показывает нужные MX, SPF, DKIM, DMARC и PTR и проверяет их по публичным резолверам.
- Вебпочта Roundcube ставится отдельным сайтом или на порту почтового хоста (`--port 2096` — без своей записи в DNS и своего сертификата).
- Подробнее — [docs/06-mail.md](docs/06-mail.md).

### Бэкапы

`mp backup target add|list|rm`, `mp backup run|list|snapshots|restore`

- restic в local, SFTP, S3, B2 или REST: файлы, дампы MySQL и копия panel.db.
- Хранение по дням, неделям и месяцам, ежедневное расписание; восстановление в `/var/lib/monopanel-agent/restore/<snapshot>` (только для root) или на место.
- restic работает в песочнице Landlock: бэкап читает только сохраняемые каталоги и не следует ни по одной символической ссылке в сохраняемых деревьях (веб-корень, конфигурация панели, каталог данных с сертификатами и дампами); последнее держится и на ядре без Landlock; системные файлы `/etc` restic читает в собственном `/etc`, так что замена `resolv.conf` или `/etc/passwd` во время бэкапа не отнимает у него DNS и имена владельцев; восстановление пишет только в каталог назначения; если часть файлов прочесть не удалось, запуск помечается `partial`. Локальный репозиторий — отдельный каталог только для restic.
- Восстановление на место раскладывает снимок на той же файловой системе, куда он вернётся (для веб-корня — `<www_root>/.restore`, только для root), восстановление в сторону — в `/var/lib/monopanel-agent/restore`; до запуска restic агент сверяет объём выбранного по листингу снимка со свободным местом и inode (части одного восстановления на одной файловой системе — вместе) и при нехватке сразу отказывает; остатки прерванного восстановления на место убирает при старте.

### Файлы

`mp files ls|put|get|mkdir|touch|rm|mv|chmod|extract|size`

- Файловые операции выполняет `monopanel fsop` через helper с необратимым сбросом привилегий; пути — относительно домашнего каталога.
- В Web UI — файловый менеджер с редактором: обзор каталога, загрузка перетаскиванием, права, распаковка архивов. Файлы правятся в редакторе VS Code (Monaco): подсветка php, html, css, js, sql, yaml и ini, поиск и замена, мультикурсор, свёртка, палитра команд по F1.
- Вкладка «Файлы» в карточке сайта открывается сразу в его docroot.

### Пользователи, SFTP и SSH

`mp user add|set|list|show|totp-reset|rm`, `mp user share list|add|entry|rm`, флаги `--shell|--sftp-only`, `--password|--password-stdin|--generate`

- Аккаунт панели — это unix-пользователь. SFTP-only — chroot в `/var/www/<login>` через `sshd_config.d/monopanel.conf`; пароль общий для панели и SFTP; shell выдаётся флагом и вместе с ним — доступ к `mp` через локальный сокет (группа `monopanel-cli`); запросы к сокету из процессов php-fpm, Apache и nginx отклоняются.
- `mp user rm <login> [--purge]` удаляет аккаунт вместе с сайтами, базами, cron, app-сервисами, экземплярами Valkey и сертификатами.
- Обычный аккаунт видит в Web UI и TUI то, что касается его самого: свои сайты, базы, почту, файлы, задачи и страницу «Аккаунт» — cron, app-сервисы, Valkey, общие папки, API-токены, пароль и 2FA.
- Общая папка (`mp user share add <гость> --site <домен> --path <папка> [--no-php]`): каталог сайта одного аккаунта монтируется (bind, юнит systemd) в дом другого (аккаунту с shell — в `/var/www/.shares/<гость>`, в доме — символьная ссылка) — гость видит его после входа по SFTP и ничего больше, файлы читают и пишут оба аккаунта и веб-сервер (ACL), `--no-php` запрещает сайту выполнять PHP из этой папки, `--entry` (или `mp user share entry`) делает папку точкой входа — сессия SFTP начинается сразу в ней. Дом гостя не меняется: chroot остаётся root-овым, изоляция аккаунтов — прежней. Файл, загруженный по SFTP с правами 0644, другая сторона читает и удаляет, но не переписывает на месте — так работает маска ACL; `mp site fix` снимает это ограничение с уже лежащих файлов.

### Cron

`mp cron add|list|set|enable|disable|rm`

- Crontab пользователя целиком собирается из базы панели; в PATH есть `~/data/bin` с php нужной версии.

### App-сервисы

`mp app add|set|list|show|start|stop|restart|logs|rm`

- systemd-юнит `monopanel-app-<login>-<name>` от имени пользователя для gunicorn, node, ботов: команда, рабочий каталог и env-file внутри домашнего каталога, автозапуск, журнал через journalctl.

### Apache и расширения

`mp stack list`, `mp stack install apache`, `mp stack install|remove memcached|jpegoptim|git|composer|sphinx`, `mp stack memcached --memory-mb --max-conn`, `mp stack upgrade [nginx|php|apache|db]`, `mp stack auto-upgrade [--on|--off] [--hour 4]`

- Apache 2.4 на Debian/Ubuntu: на каждый аккаунт с сайтами в режиме apache — свой экземпляр `monopanel-apache@<логин>.service`; родитель от root слушает `127.<100+uid>>16>.<(uid>>8)&255>.<uid&255>:81` (привилегированный порт на адресе только этого аккаунта), дочерние процессы работают от имени аккаунта и читают только то, что читает он. Конфигурация — `/etc/apache2/monopanel/accounts/<логин>/` (`httpd.conf`, `backend.conf`, `sites/<домен>.conf`, `sites/<домен>.d/*.conf`); mpm_event и короткий список модулей без cgi, include, lua, ext_filter, status и info; `.htaccess` может всё (`AllowOverride All`), кроме общих папок с `--no-php`: там `.htaccess` не читается и PHP не выполняется. Apache аккаунта отвечает только nginx: каждый запрос nginx несёт секрет аккаунта (заголовок `X-MonoPanel-Backend`), а на прямое подключение к адресу Apache любого локального процесса — 403, так что `--allow`, лимит запросов и адрес клиента сайта в обход nginx не обойти; PHP секрета не видит. То, на что nginx отвечает 404 (dot-файлы вроде `.env` и `.git/`, `composer.json`, `.user.ini`), Apache аккаунта не отдаёт и с секретом. `apache2.service` дистрибутива панель останавливает и выключает, `www-data` выводит из группы `monopanel-web`. Собственные директивы сайта (`sites/<домен>.d/`) живут, пока жив сайт: смена режима и приостановка их не трогают.
- Пакеты стека, которые поставила панель, — nginx с nginx.org, ветки PHP из Sury, ppa:ondrej/php или Remi, Apache из дистрибутива, Percona или MySQL — обновляет из их репозиториев `mp stack upgrade` или кнопка «обновить» на странице «Расширения», и только уже установленные пакеты из её набора. Конфигурацию nginx, PHP и сервера БД до обновления проверяет ещё работающая версия (`nginx -t`, `php-fpm -t`, `mysqld --validate-config`): их пакеты сами перезапускают службы, и компонент, не прошедший проверку, не обновляется. После обновления конфигурацию проверяет новая версия, у Apache — каждого аккаунта (`apache2 -t`), затем службы перезагружаются или перезапускаются. Служба, не прошедшая проверку после обновления, не перезагружается и работает как работала — если только перезапуск её же пакета во время обновления уже не уронил её: тогда она остаётся остановленной, и задача это называет. Ничего не откатывается. nginx, PHP и Apache панель обновляет и сама, каждый день в 04:00 по времени сервера (`mp stack auto-upgrade`, «Настройки»); сервер баз данных — только по имени (`mp stack upgrade db`): его перезапуск — простой сайтов. `mp doctor` называет компоненты, у которых ждёт обновление, и службы, которые ещё работают на заменённом обновлением бинарнике.
- Страница «Расширения» в Web UI: memcached (только 127.0.0.1, память и число соединений настраиваются, перезапуск при смене), jpegoptim, git, composer (с getcomposer.org с проверкой контрольной суммы, работает на новейшей ветке PHP панели и от аккаунтов, не от root; повторная установка обновляет).
- Sphinx для 1С-Битрикс: Sphinx 2.2 из дистрибутива на Debian/Ubuntu, сборка Sphinx 3 с sphinxsearch.com на EL; индекс `bitrix` по эталону из настроек Битрикса, устаревший индекс на диске пересоздаётся, SphinxQL на 127.0.0.1:9306.

### Firewall и Real IP

`mp firewall status|enable|disable|apply|allow|deny|rm|ban|unban|trust|untrust`, `mp stack install fail2ban`, `mp stack real-ip --cloudflare [--from CIDR]`

- nftables `inet monopanel` с policy drop; SSH, 80, 443 и порт панели открыты всегда; юнит `monopanel-firewall`.
- Allow с источником проверяются раньше deny: `deny --port 8443` + `allow --port 8443 --source <VPN>` ограничивает панель адресами VPN. Deny, который запер бы вас самих (SSH или панель без allow с источником, ваш текущий адрес), панель отклоняет.
- fail2ban с jail'ами sshd, nginx и панели. Jail'ы nginx читают логи каждого сайта (список обновляется вместе с сайтами), а не только общий лог. Доверенные адреса (`mp firewall trust <ip|сеть>`) попадают в `ignoreip`. Свои настройки — в `/etc/fail2ban/jail.d/zz-local.local`, панель этот файл не трогает.
- Доверенные прокси для nginx `real_ip` (сети Cloudflare встроены): allow-list и логи видят адрес клиента, а не прокси.
- Модули ядра sctp, dccp, rds и tipc не загружаются: хостингу эти протоколы не нужны, а модуль протокола загружает любой локальный аккаунт, открыв его сокет. Правило — `/usr/lib/modprobe.d/monopanel.conf` из пакета (без пакета `mp setup` пишет `/etc/modprobe.d/monopanel.conf`); файл с тем же именем в `/etc/modprobe.d` его заменяет — так модуль разрешают снова. Уже загруженный модуль `mp doctor` называет.

### Метрики, логи и диагностика

`mp status`, `mp metrics`, `mp site logs`, `mp logs <unit>`, `mp service`, `mp job list|show|wait`, `mp doctor`, `mp audit`

- Сэмплер раз в 10 с, точки по минутам за 30 дней; хвост логов сайтов и journald через агент.
- Службы — юниты панели и стека (агент, веб-серверы, СУБД, каждая установленная ветка PHP) и любой юнит по имени: состояние, запуск, остановка, перезапуск, `reload-or-restart`, автозапуск и журнал — `mp service`, `mp logs`, страница «Службы». У экземпляров шаблонов (кроме Apache аккаунтов), целей, оболочек, юнитов питания и прогонов systemd-tmpfiles по всем файлам — только состояние. Пока дерево логов `/var/log/monopanel/sites` принадлежит не только root или не вычищено, php-fpm, nginx и Apache не запускаются, не перезапускаются и не перечитывают конфигурацию, а пакеты не ставятся, не обновляются и не удаляются; пока не только root'у принадлежит каталог сокетов `/run/monopanel/php` — то же с php-fpm и пакетами. Агент отказывает с причиной, а при своём старте забирает оба дерева себе. Остановку и перезапуск самой панели API выполняет уже после ответа. Остановка `monopanel-api` оставляет порт за сокетом, и следующее соединение снова запустит API (и агента, если он тоже остановлен); остановить панель целиком: `systemctl stop monopanel-api.socket monopanel-api monopanel-agent`. Обновление пакета остановленную так панель не запускает и выключенные юниты не включает (кроме установки после удаления пакета: она включает их, как свежая); чтобы панель не поднялась и после перезагрузки: `systemctl disable --now monopanel-api.socket monopanel-api.service monopanel-agent.service`.
- Долгие действия — задачи с журналом: `mp job list|show|wait`, страница «Задачи». Администратор видит все задачи, остальные аккаунты — свои; пароли и токены из параметров задачи в ответах скрыты.
- Логи сайтов лежат в `/var/log/monopanel/sites/<логин>/`, вне домашнего каталога (их открывают от root nginx, Apache и php-fpm), аккаунт читает их через свою группу; ротация раз в неделю или по 100 МБ: восемь копий, сжатие со второй.
- `mp doctor` проверяет сервисы, конфиги, диск, сертификаты, DNS, задачи и дрейф сгенерированных файлов, а ещё — ждущие обновления пакетов вендоров, загруженные модули ядра и то, что не доделали переезды обновления до 0.8.20.
- Журнал действий — кто и откуда входил, кто выпускал токены, кто что менял: `mp audit`, страница «Журнал», `GET /system/audit`; та же лента в `/var/log/monopanel/audit.log` строками JSON с ротацией, входы и отказы — ещё и в journald.

### Консоль в Web UI

`POST /system/console`

- Страница «Консоль»: команды `mp` от имени вошедшего администратора с потоковым выводом, одноразовый токен на команду.
- Адрес панели и токен команда получает через окружение, а секреты, набранные во флагах (`--password …`), консоль передаёт ей через stdin: в списке процессов их не видно, в журнал действий строка попадает без них. Команды, которые читают или пишут файлы на сервере (`files get|put`, `ssl import`, `--cert`/`--key`, `site nginx --set`, `migrate --key`), и `mp update trust` консоль не запускает: то же содержимое Web UI принимает своими формами.
- На дашборде у находок doctor есть кнопки «починить сайт» и «вернуть enforcing».

### TUI-меню

`mp` без аргументов в терминале — на сервере или удалённо (`mp --server … --token …`)

- Разделы — как в навигации Web UI; в каждом — его экраны и все команды его групп `mp`. Обычному аккаунту меню показывает то же, что ему показывает Web UI.
- Любое действие — команда `mp`: форма собирается из её аргументов и флагов, строка `mp …` видна, пока форма заполняется, и выполняется именно она — дочерним процессом, с выводом по мере появления. Секреты в строке скрыты и уходят команде через stdin.
- Подтверждения — как в Web UI; удаление аккаунта или сайта вместе с файлами подтверждается вводом имени. Файлы и nginx-директивы сайта правятся в `$EDITOR`.
- `?` — действия экрана и все команды раздела, `:` — любая команда `mp` с дополнением по Tab. Разделы и клавиши — в [docs/04-cli-tui-api.md](docs/04-cli-tui-api.md#3-tui-меню).

### Перенос между панелями

`mp migrate grant|plan|run`

- Аккаунт целиком переезжает на другой сервер с MonoPanel. Источник выдаёт токен с областью на один аккаунт и только читает; приёмник разбирает конфликты (`plan` ничего не меняет) и забирает аккаунт.
- Файлы и дамп идут потоком насквозь; пароли панели, SFTP, MySQL и почты переезжают хешами, поэтому пользователи смены сервера не замечают.
- Токен переезда выдаёт только администратор. В Web UI — страница «Перенос»: токен для другой панели, разбор и перенос с MonoPanel, FASTPANEL и BitrixVM.
- Подробнее — [docs/07-migration.md](docs/07-migration.md).

### Переезд с BitrixVM и FASTPANEL

`mp migrate plan|run --from bitrixvm|fastpanel`

- Тот же разбор и перенос, но с чужого сервера по ssh (пароль или ключ); источник только читается.
- BitrixVM: сайты из `/etc/nginx/bx`, реквизиты базы из `.settings.php`; симлинки link-сайтов и пути в `dbconn.php` и cron переписываются под новый дом.
- FASTPANEL: аккаунт, сайты, бэкенды PHP, базы с хешами паролей, allow-списки, сертификаты и cron из её базы и файлов.
- Пресет CMS определяется по файлам сайта.

### Обновления

`mp update`, `mp update check|apply|settings`, `mp update trust`

- Панель находит новую версию в релизах этого репозитория, скачивает пакет для своей ОС, проверяет подпись ed25519 и ставит его отдельным systemd-юнитом. Если новая версия не отвечает, возвращается прежний бинарник.
- Ключ, которым проверяется подпись, меняет только root на сервере (`mp update trust`): через процесс панели он не проходит — ни через API, ни через консоль; Web UI показывает его только для чтения.
- Версию старше установленной панель не ставит; если откат неизбежен, его делает root руками — см. [«Откат на старую версию»](#откат-на-старую-версию): с 0.8.20 на более старую версию после него нужны шаги.

### Настройки панели

`mp config show|set|templates`

- Имя и адрес панели, уровень и формат журнала и число одновременных задач (`web.hostname`, `web.listen`, `log.level`, `log.format`, `jobs.workers`) меняются через API — `mp config set` или «Настройки → Панель» в Web UI. Изменение вступает в силу после перезапуска monopanel-api, `--restart` перезапускает его сразу; порт нового адреса панель открывает в firewall до записи. Порт панели держит systemd (`monopanel-api.socket`), поэтому, пока API перезапускается, другой локальный процесс не займёт его; при смене `web.listen` сокет переезжает вместе с перезапуском.
- Если API не поднимается (например, после неудачного `web.listen`), root на сервере правит файл напрямую: `mp config set --local`. С `web.listen` он переносит и сокет порта, `--restart` перезапускает API вместе с ним. Правка `web.listen` в config.yaml руками не переносит сокет: выполните после неё `mp setup` или `mp config set --local web.listen <адрес> --restart`.
- `mp config templates` и та же страница показывают встроенные шаблоны конфигураций и какие из них переопределены файлами в `templates_dir`.

### Токены, 2FA и webhooks

`mp token create|list|revoke`, `mp totp status|setup|enable|disable`, `mp user totp-reset`, `mp webhook add|list|test|rm`, `mp whoami`

- Токен принадлежит аккаунту; администратор выпускает его и для другого аккаунта (`--user`), root по локальному сокету — для единственного администратора без флагов.
- TOTP 2FA с QR-кодом — в Web UI, в TUI и в терминале (`mp totp setup` рисует QR-код); настроить 2FA заново можно, только выключив её с паролем. Bearer-токены, webhooks с подписью HMAC-SHA256 на события задач.
- Новый пароль и приостановка аккаунта завершают его сессии в браузере (кроме той, из которой он сам сменил пароль); API-токены остаются, их отзывают отдельно. `mp whoami` показывает, кем вас видит панель: аккаунт, роль, способ входа, токен и 2FA.

### Языки

- Web UI на русском и английском: язык берётся из браузера (языки стран СНГ → русский, остальные → английский), переключается в «Настройках» и на экране входа, выбор запоминается в браузере.
- CLI и TUI говорят на языке локали терминала по тому же правилу; `MP_LANG=ru|en` задаёт его явно. Сообщения API, задач и диагностики — на английском.
- Заглушка нового сайта и страница приостановленного показываются на языке браузера посетителя.

Собственные сборки PHP (используются Sury/Remi), режим apache на EL, phpMyAdmin,

контент-фильтра (rspamd) нет. Переезд —

DNS; другие панели и серверы без панели — в планах ([docs/07-migration.md](docs/07-migration.md)).

## Как устроено

Один бинарник `monopanel` (он же `mp`) работает в нескольких ролях:

| Роль | Права | Зачем |
|---|---|---|
| `api` | обычный пользователь `monopanel` | HTTPS :8443, unix-сокет для CLI, очередь задач, планировщики |
| `agent` | root | закрытый набор типизированных операций по unix-сокету (никаких строк с командами) |
| `helper` | setuid, необратимый сброс прав | файловые операции от имени клиента |
| `fsop` | права клиента | сама файловая операция |

Состояние живёт в SQLite. Изменение сайта — это не правка файла на диске, а запись в
базу, из которой рендерятся конфиги: шаблон → валидация (`nginx -t`,
`apache2 -t -f <httpd.conf аккаунта>`, `php-fpm -t`) → атомарная запись всех файлов
сразу → reload. Любая неудача на этом
пути откатывает весь набор файлов и возвращает текст ошибки.

Принципы, коротко:

1. Один бинарник Go, без рантайма на хосте.
2. Разделение привилегий: непривилегированный API-процесс ↔ root-агент с allow-list операций и путей.
3. Один API для Web, CLI, TUI и интеграций.
4. Декларативное состояние → рендер → валидация → атомарное применение → reload, с откатом.
5. Панель слушает свой порт и не зависит от системного nginx.
6. Один php-fpm master на версию, пул на сайт; Apache только через `mod_proxy_fcgi`.

## Обновление панели

Версия выпускается тегом; всё остальное делает CI. Тег `v0.8.19` собирает `.deb` и
`.rpm` под amd64 и arm64, подписывает список контрольных сумм ключом ed25519 из
секрета репозитория и публикует релиз; текст аннотированного тега становится
описанием релиза.

```bash
make keygen                  # один раз: ключ подписи (приватный — в секрет MONOPANEL_RELEASE_KEY)
make release VERSION=0.8.19  # тег + push, дальше CI собирает и публикует
make packages VERSION=0.8.19 # то же локально, без публикации
```

На сервере:

```bash
mp update settings --repo owner/name     # --token-stdin для приватного репозитория
mp update                                # что установлено и что доступно
mp update apply                          # скачать, проверить подпись, установить, перезапуститься
mp update trust                          # каким ключом проверяется подпись (только root на сервере)
mp update trust --key <ключ форка>       # свой ключ вместо встроенного; --off выключает проверку
```

Публичный ключ подписи релизов вшит в панель и в `install.sh`, так что подпись
проверяется по умолчанию — и при первой установке (если есть openssl 1.1.1+), и при
каждом обновлении. Ключ можно сверить с тем, что печатает workflow `release-key`:

```
eoGfJciXIG9upyFNJQR7rIsXtSs506DkiXT5kiBUyhg=
```

Проверка обновлений идёт по расписанию (по умолчанию раз в сутки), `--auto-apply` ставит
обновление без участия человека. Устанавливает не сама панель: агент запускает
transient-юнит `monopanel-update.service`, который переживает перезапуск API и агента
и возвращает прежний бинарник, если новая версия не отвечает. Неподписанный релиз
не установится, пока проверка не выключена явно. Медленный канал не помеха: у загрузки
пакета нет общего таймаута, обрывается только застывший поток.

### Обновление до 0.8.20

Что заметит администратор после обновления с 0.8.19:

- Порт панели держит `monopanel-api.socket`. Остановленный `monopanel-api` первое же
  соединение запустит снова; остановить панель целиком —
  `systemctl stop monopanel-api.socket monopanel-api monopanel-agent`. Правка `web.listen`
  в `config.yaml` руками сокет не переносит: после неё — `mp setup` или
  `mp config set --local web.listen <адрес> --restart`. Если самообновление откатится,
  с портом делать ничего не нужно: drop-in юнита API перед стартом старой версии
  останавливает сокет, и она слушает порт сама. Понижение пакета до 0.8.19 требует
  шагов — см. [«Откат на старую версию»](#откат-на-старую-версию).
- Обновление пакета включённые и выключенные юниты оставляет как есть (до 0.8.19 оно
  каждый раз включало агента и API) и не запускает остановленную панель: если API не
  работал, его сокет тоже не запускается. Сокет порта панели при обновлении с 0.8.19
  включается, только если включён API. Установка пакета после его удаления
  (`apt remove`, `dnf remove`) включает панель, как свежая установка: выключило её
  удаление, а не администратор; запускает её `mp setup`.
- Юниты в `/etc/systemd/system`: `mp setup` до 0.8.19 копировал туда
  `monopanel-agent.service` и `monopanel-api.service` на каждом сервере, и копии навсегда
  заслоняли юниты пакета. Обновление удаляет те из них, что доказуемо сделала панель, и
  переводит симлинки включения на юниты пакета (`/usr/lib/systemd/system`); `mp setup`
  на сервере с пакетом юнитов в `/etc` больше не пишет. На серверах, настроенных 0.8.12
  и раньше, агент так впервые получает ограничения своего юнита (`ProtectHome=read-only`,
  `PrivateTmp=yes` и другие), которые у остальных были с 0.8.13. Свой юнит
  администратора или копию для другого бинарника обновление не трогает, а `mp setup`
  предупреждает, что она заменяет юнит пакета.
- После старта панель ждёт агента, сколько бы он ни запускался (он может, например,
  снимать небезопасные юниты общих папок): журнал API пишет
  `start-up refresh: waiting for the agent` и `the agent answers`, работа старта
  (переезды, проверки) начинается после ответа, а задания в очереди ждут агента до трёх
  минут и не падают на «agent unreachable». Если API остановят раньше, работа старта
  выполнится при следующем старте.
- Версию старше установленной панель не ставит (и релиз поверх более поздней сборки
  вроде `0.8.19-5-gabc1234`); отказ называет, что сломает откат, и ссылается на
  [«Откат на старую версию»](#откат-на-старую-версию).
- Режим apache: у каждого аккаунта свой Apache (`monopanel-apache@<логин>`). Сайты
  переезжают сами, по одному и без простоя, затем `apache2.service` дистрибутива
  останавливается и выключается — свои сайты администратора в нём, если были,
  перестанут работать, — а `www-data` выходит из `monopanel-web`. Apache аккаунта
  отвечает только nginx: каждый запрос nginx несёт секрет аккаунта (заголовок
  `X-MonoPanel-Backend`), а прямое подключение к `127.100.x.y:81` любого локального
  процесса получает 403. Остановка Apache аккаунта мягкая: запросы в работе дорабатывают
  до минуты. Где `net.ipv4.ip_unprivileged_port_start` не выше 81,
  `mp stack install apache` отказывает, а `mp doctor` предупреждает: порт Apache
  аккаунтов там мог бы занять любой аккаунт.
- Сайт режима apache остаётся на общем Apache, пока агент не примет для Apache аккаунта
  его собственные директивы: с `Include`, журналом в другом каталоге, переменными
  `APACHE_*`, а на уровне виртуального хоста — с `RewriteEngine Off` или
  `RewriteOptions Inherit`/`IgnoreInherit` (они сняли бы проверку секрета). Исправив их
  (`RewriteEngine Off` — в `<Directory>`, `Inherit` → `InheritBefore`), повторите
  `mp stack install apache`. Файлы директив читает агент (в том числе доступные только
  root, при umask 077) и переносит, не открывая шире: файл, доступный только root,
  остаётся таким и у Apache аккаунта. Это должны быть обычные файлы в
  `/etc/apache2/monopanel/sites/<домен>.d/` — символьная ссылка (на файл или на сам
  каталог `sites` или `<домен>.d`), жёсткая ссылка или файл больше 1 МиБ держат сайт на
  месте, пока на их место не положат сам файл; символьная ссылка root выше, например
  `/etc/apache2`, перенесённый в другое место, допустима. Так же держат сайт
  переопределения шаблонов из 0.8.19: `nginx/site.conf.tmpl` без
  `include {{ .ApacheBackendConf }};` в обоих location режима apache и
  `apache/site.conf.tmpl` без `RewriteEngine On` прямо в `<VirtualHost>`. Переезд не
  повторяется при каждом старте: после неудачи следующая попытка ждёт так же, как у
  логов (ниже), состояние видно в строке `service apache2.service` вывода `mp doctor`, а
  `mp stack install apache` пробует сразу.
- Штатный пул `www` каждой ветки php-fpm панель один раз делает пустым — при установке
  ветки или при первом старте 0.8.20: свой виртуальный хост, который ходил в его сокет
  (`/run/php/php<версия>-fpm.sock`, на EL — `/var/opt/remi/phpXY/run/php-fpm/www.sock`;
  например, phpMyAdmin из apt), перестанет работать. Если вернуть свой `www.conf`, панель
  его больше не трогает, а `mp doctor` предупреждает строкой `php X.Y pool www`; отдать
  файл панели — удалить его и перезапустить `monopanel-api`. Так же будет, если при ручном
  обновлении php-fpm на вопросе dpkg о `www.conf` выбрать версию сопровождающего; ответ по
  умолчанию оставляет пул панели, а apt, который запускает сама панель, этого вопроса не
  задаёт. `error_log = syslog` в `php-fpm.conf` на EL панель тоже ставит один раз: если
  строку потом убрать или изменить, `mp doctor` предупреждает в той же строке, а вернуть
  её нужно руками — `php-fpm.conf` панель заново не пишет. Вывод рабочих процессов php-fpm
  в журнал мастера больше не попадает (`catch_workers_output = no`); ошибки PHP —
  по-прежнему в `<домен>.php.error.log`. Пул, где он ещё включён, `mp doctor` называет в
  строке `php-fpm pools`: пулы сайтов теряют его, когда сайт переезжает (ниже), из своего
  пула строку уберите.
- Свои директивы nginx с `fastcgi_pass` не на пул сайта, `fastcgi_param PHP_VALUE` или
  `PHP_ADMIN_VALUE`, `uwsgi_modifier1` не 0, `proxy_method` не словом, `include` из
  `/etc/nginx/default.d` или с шаблоном в имени каталога, логом глубже
  `/var/log/monopanel/sites/<логин>/` или `proxy_pass` на Apache аккаунта без
  `include monopanel/apache/<логин>.conf;` панель больше не записывает. Записанный
  раньше `custom.conf` работает, но перезаписать его можно только без них.
- Юниты: у экземпляров шаблонов (кроме Apache аккаунтов), целей, оболочек вроде
  `debug-shell`, юнитов питания и прогонов systemd-tmpfiles по всем файлам
  (`systemd-tmpfiles-setup*`, `systemd-tmpfiles-clean`) `mp service` и «Службы»
  показывают только состояние.
- Каталог сокетов пулов `/run/monopanel/php` и дерево логов `/var/log/monopanel/sites`
  принадлежат только root: `php/` создаёт systemd-tmpfiles при загрузке, оба дерева агент
  готовит при старте, до API. Каталог, который сделал кто-то другой (до 0.8.19
  `/var/log/monopanel` принадлежал пользователю `monopanel`), агент забирает себе и
  вычищает из дерева то, что туда кладёт не root: каталоги уходят в
  `untrusted-<время>-<случайное>` рядом. Пока дерево логов не только root'а или не
  вычищено до конца, агент не запускает, не перезапускает и не перечитывает php-fpm, nginx
  и Apache, не запускает их проверки конфигурации, не ставит, не обновляет и не удаляет
  пакеты; пока не только root'а `php/` — то же для php-fpm и пакетов. На это агент
  отвечает 403 с причиной: чужой каталог он заберёт при перезапуске, а дерево логов
  пробует вычистить снова перед каждым таким действием. Строку для `php/` обновление
  дописывает и в копию `/etc/tmpfiles.d/monopanel.conf`, которую оставил `mp setup`, а
  `/etc/tmpfiles.d/monopanel-php.conf`, который писал API, удаляет; если в нём есть что-то
  ещё, пакет предупреждает — проверьте файл и удалите его.
- composer от root не запускается: `su -s /bin/sh -c 'composer …' <логин>`. Источники
  пакетов, которые панель записала по http (nginx.org, repo.mysql.com), она при старте
  переводит на https, а других уже не пишет. На Ubuntu с `ppa:ondrej/php` панель при
  старте один раз кладёт в связку ключей текущий ключ PPA (2024 года): прежний, rsa1024,
  apt 3 в Ubuntu 26.04 не принимает.
- Свой пароль в Web UI и по API-токену меняется только с текущим (`mp user set` —
  `--current-password`); по локальному сокету текущий не нужен. Смена пароля завершает
  остальные сессии аккаунта в браузерах, а 2FA заново настраивается только после
  выключения паролем. Токены переезда, оказавшиеся у обычных аккаунтов, панель отзывает
  при старте.
- Логи сайтов переезжают из `data/logs` в `/var/log/monopanel/sites/<логин>/`; старые
  файлы остаются аккаунту. При первом старте панель ставит в очередь `site.apply` для
  каждого сайта, который старая версия настроила с логами в `data/logs` (активного, с
  ошибкой или ожидающего применения; у приостановленного логов там нет), а `mail.apply` —
  для вебпочты на своём порту, и запоминает не очередь, а результат: сайт считается
  переехавшим только после успешного применения. Сайт, который применить не удалось
  (например, пропала его ветка PHP), остаётся на старых путях — `mp doctor` называет его и
  причину в строке `site logs`, — а панель повторяет попытку сама: при каждом старте и раз
  в час она снова ставит сайт в очередь, если подошёл срок, — через 10 минут после первой
  неудачи, затем каждый раз вчетверо дольше, но не реже раза в сутки. Исправив причину,
  можно сразу выполнить `mp site apply <домен>`. Пока сайт не переехал, его логи в
  `data/logs` никто не ротирует и fail2ban их не читает: root не работает с файлами в
  каталоге клиента. На EL с SELinux сайты переезжают только после того, как добавлено
  правило метки для дерева логов; не получилось — следующий старт пробует снова. История
  конфигов — в `/var/lib/monopanel-agent/confhistory/`.
- Бэкапы: restic работает в песочнице. Локальный репозиторий должен быть отдельным
  каталогом только для restic — цель с репозиторием прямо в каталоге, где лежат и
  другие файлы (например, `/var/backups`), перестанет работать: заведите новую,
  например `/var/backups/monopanel`. Учётные данные S3, B2 и REST — только в переменных
  цели; ключ root и `known_hosts` для SFTP готовятся заранее. Запуск, в котором restic
  не прочёл часть файлов, получает статус `partial`. Восстановление на место раскладывает
  снимок на той файловой системе, куда он вернётся (для веб-корня — в
  `/var/www/.restore`), и до запуска restic проверяет там свободное место и inode;
  восстановление в сторону проверяется так же. Если места не хватает, задача сразу
  завершается ошибкой и говорит, сколько нужно и сколько свободно.
- На Oracle Linux с ядром UEK Landlock собран, но не включён: restic работает без
  песочницы, а бэкап по-прежнему читает сохраняемые деревья без символических ссылок.
  Строка `restic sandbox` в `mp doctor` подсказывает, как включить Landlock:
  `grubby --update-kernel=ALL --args=lsm=$(cat /sys/kernel/security/lsm),landlock` и
  перезагрузка, или ядро RHCK (`dnf install kernel`, затем `grubby --set-default`).
- nginx, PHP и Apache панель теперь обновляет сама: каждый день в 04:00 по времени сервера
  она ставит то, что для её установленных пакетов предлагают их репозитории (nginx.org,
  Sury или ppa:ondrej/php, Remi, для Apache — дистрибутив), проверяет конфигурацию и
  перезагружает или перезапускает службы. Выключить — `mp stack auto-upgrade --off`,
  перенести — `mp stack auto-upgrade --hour <час>` или карточка «Ежедневное обновление
  nginx, PHP и Apache» в «Настройках». Сразу — `mp stack upgrade [nginx|php|apache|db]`
  или кнопки на странице «Расширения»; сервер баз данных обновляется только так, по имени.
  Пакеты, удержанные через `apt-mark hold`, панель не трогает; на EL так же остаются
  пакеты, закреплённые через `dnf versionlock`. `mp doctor` называет компоненты, у которых
  ждёт обновление, удержанные пакеты и службы стека, которые ещё работают на бинарнике,
  заменённом обновлением (в том числе обновлением дистрибутива); как такую службу
  перезапустить, говорит сама строка — для nginx, PHP, Apache и сервера БД это
  `mp stack upgrade <компонент>`, после проверки конфигурации. needrestart в Ubuntu после
  apt, которым панель ставит и обновляет стек, теперь только перечисляет службы на старых
  библиотеках и сам ничего не перезапускает, сервер БД тоже.
- Модули ядра sctp, dccp, rds и tipc больше не загружаются
  (`/usr/lib/modprobe.d/monopanel.conf`). Уже загруженный модуль остаётся до перезагрузки
  или `rmmod`, и `mp doctor` о нём предупреждает. Разрешить модуль — положить в
  `/etc/modprobe.d/monopanel.conf` копию файла без его строки (пустой файл разрешает все
  четыре).
- Общие папки гостей с shell переезжают в `/var/www/.shares/<гость>/<имя>`, а в доме
  остаётся символьная ссылка; занятая папка переедет при следующем старте или после
  `mp site fix <домен>`.
- Консоль Web UI не запускает команды, которые читают или пишут файлы на сервере
  (`files get|put`, `ssl import`, `site nginx --set`, `migrate --key`), и
  `mp update trust`: это делают страницы панели или `mp` по SSH.

Подробнее — в [docs/05-roadmap.md](docs/05-roadmap.md) и в документах по ссылкам оттуда.

### Откат на старую версию

Версию старше установленной панель сама не ставит: старый релиз вернул бы то, что
исправили следующие, в том числе проверки самого агента, — отказ `mp update apply`
ведёт сюда. Если откат неизбежен, root ставит старый пакет руками, поверх нового:
`apt install --allow-downgrades ./monopanel_<версия>_<arch>.deb` или
`dnf downgrade ./monopanel-<версия>.<arch>.rpm`. Ставьте его именно поверх, а не после
`apt remove` или `dnf remove`: только так скрипт пакета сохраняет шаблон Apache
аккаунтов и печатает, что сломается и что делать.

Откат с 0.8.20 и новее на версию старше 0.8.20 требует шагов: старая версия не знает, что
0.8.20 поменяла на сервере. Скрипт пакета 0.8.20 и новее установку не прерывает (упавший
prerm оставил бы dpkg с полуустановленным пакетом, а rpm — с двумя версиями сразу), а
сохраняет шаблон Apache аккаунтов и печатает, что сломается и что делать. Подробнее:

- логи сайтов лежат в `<log_dir>/sites` (`/var/log/monopanel/sites`), а logrotate и
  fail2ban старой версии смотрят в `data/logs` аккаунтов: логи не ротируются, атаки на
  сайты не видны. Пакет старой версии к тому же снова отдаёт `/var/log/monopanel`
  пользователю `monopanel`, и логи, которые root открывает в нём, оказываются под
  каталогом служебного пользователя — примените сайты сразу;
- сайты в режиме apache работают на Apache своих аккаунтов (`monopanel-apache@<логин>`),
  а `apache2.service` дистрибутива выключен. Шаблона `monopanel-apache@.service` в старом
  пакете нет: скрипт копирует его в `/etc/systemd/system`, и Apache аккаунтов переживают
  перезагрузку. Но сайт, который старая панель применит (правка, выпуск сертификата),
  она отправит на общий Apache, и до `mp stack install apache` он отвечает 502;
- app-сервисы с env-файлом запускаются через `monopanel app-exec`, которого в старой
  версии нет, и при следующем старте не поднимутся — скрипт их называет;
- общие папки shell-гостей остаются смонтированы в `/var/www/.shares` и доступны по
  ссылке из дома; старая панель показывает их несмонтированными и пересоздать не может —
  не трогайте их до следующего обновления (`mp user share rm` в старой версии оставит
  монтирование);
- порт панели: ничего делать не нужно — drop-in юнита API перед стартом старой версии
  останавливает сокет, и она слушает порт сама; drop-in можно удалить:
  `rm /etc/systemd/system/monopanel-api.service.d/socket.conf && systemctl daemon-reload`.

Когда старая версия запустилась, от root по порядку:

```sh
mp stack install apache          # если есть сайты в режиме apache: снова общий Apache, до сайтов
mp site list | awk 'NR > 1 {print $1}' | while read -r d; do mp site apply "$d"; done
mp mail apply                    # если у вебпочты свой порт
mp app set <имя> --user <логин>  # каждый app-сервис с env-файлом (mp app list)
systemctl disable --now monopanel-apache@<логин>   # Apache каждого аккаунта, когда его сайты применены
```

`mp site apply` пишет nginx, пул и Apache сайта так, как их делает старая версия: логи
снова идут в `data/logs`, которые её logrotate и fail2ban уже смотрят (обе конфигурации
она переписала при старте); файлы в `/var/log/monopanel/sites` больше никто не пишет —
сохраните или удалите их. `mp app set` без флагов изменений (только с `--user`)
переписывает юнит app-сервиса и перезапускает его; root-файлы переменных в
`/etc/monopanel/apps/` старая версия не читает.

Обратно на 0.8.20 и новее: копию шаблона Apache в `/etc/systemd/system` пакет при
обновлении удаляет сам. Однократные переезды 0.8.20 помнят, что выполнены, и после
такого обновления сами не повторяются: выполните `mp stack install apache` (если есть
сайты в режиме apache), `mp site apply` для каждого сайта и `mp mail apply`, если у
вебпочты свой порт.

## Переезд

Аккаунт переезжает целиком: unix-пользователь с прежним паролем, сайты, базы с
прежними паролями, cron, сертификаты, а между двумя MonoPanel — ещё почта, app-сервисы
(выключенными) и настройки экземпляров Valkey. Перенос запускается на **новом** сервере,
источник только читается — там не меняется ни один файл, и старый сервер остаётся
запасным, пока DNS не переключён. `plan` ничего не создаёт и показывает, что
приедет и что мешает: занятый логин (`--as <логин>`), домен или база, которые
здесь уже есть, ветка PHP, которой нет (`mp php install 8.2`), нехватка места.

**С другого сервера с MonoPanel.** На старом сервере выдаётся токен — на один
аккаунт, только на чтение, со сроком жизни:

```bash
mp migrate grant user:alex                                             # на старом сервере
mp migrate plan --source https://old:8443 --token … --scope user:alex   # на новом: разбор
mp migrate run  --source https://old:8443 --token … --scope user:alex   # на новом: перенос
```

**С BitrixVM / bitrix-env 7–9.** Нужен ssh на старый сервер под root: ключом
(`--key`, по умолчанию `~/.ssh/id_ed25519` того, кто запускает `mp`) или паролем
(`--password-stdin`). Основной сайт BitrixVM живёт под `server_name _`, имя ему
даёт `--domain`; дополнительные сайты из `/home/bitrix/ext_www` приезжают под
своими именами. Аккаунт один — `bitrix`, здесь его можно принять под другим
логином (`--as`).

```bash
mp migrate plan --from bitrixvm --source root@old.example.com --domain shop.example.com
mp migrate run  --from bitrixvm --source root@old.example.com --domain shop.example.com
```

Реквизиты базы берутся из `bitrix/.settings.php` (или `dbconn.php`), аккаунт MySQL
заводится с тем же паролем; пути `/home/bitrix` переписываются в `dbconn.php`,
`.settings*.php`, командах cron и симлинках link-сайтов. Кеш Битрикса, push-сервер,
memcached и msmtp окружения не едут (`mp stack install memcached`, если нужен).
Работает и с bitrix-env 7 на CentOS 7: дамп MySQL 5.7 по пути приводится к
MySQL 8.

**С FASTPANEL 2.** Тот же ssh под root. Без `--scope` разбор перечислит аккаунты
панели:

```bash
mp migrate plan --from fastpanel --source root@old.example.com                 # кто есть на источнике
mp migrate run  --from fastpanel --source root@old.example.com --scope user:shop [--as shop2]
```

Приезжают сайты с их версией PHP и режимом (php-fpm или Apache), docroot,
алиасами и allow-списками, базы с прежними хешами паролей, сертификаты
(загруженные и Let's Encrypt), cron. Почта FASTPANEL не переносится — разбор
скажет, сколько ящиков заводить заново.

**После переноса** (любой источник):

1. Проверить сайт по адресу нового сервера, не трогая DNS:
   `curl --resolve shop.example.com:80:<новый IP> http://shop.example.com/`.
2. Аккаунту, приехавшему с чужой панели, задать пароль для входа в панель:
   `mp user set <логин> --generate` (unix-пароль для SFTP приехал прежним).
3. Переключить DNS. Перевезённые сертификаты работают сразу, дальше их продлевает
   панель; сайту без сертификата — `mp ssl issue <домен>`.

Если у старого сервера сломан DNS (мёртвый nameserver в `resolv.conf`), каждая
ssh-команда разбора занимает секунды — почините `resolv.conf` там. Что именно
переносится и что нет: [docs/07-migration.md](docs/07-migration.md).

## Стек

| Слой | Выбор |
|---|---|
| Ядро, CLI, TUI | Go 1.27, один статический бинарник (`CGO_ENABLED=0`) |
| HTTP / API | `chi` + `huma` v2 (OpenAPI 3.1 из типов), SSE для прогресса задач |
| Состояние | SQLite (WAL) через `modernc.org/sqlite`, встроенные SQL-миграции |
| Web UI | Svelte 5 + SvelteKit 2 (static), TypeScript, Tailwind 4 — собирается в `web/build` и вшивается в бинарник; адаптивен: на телефоне меню выезжает, а таблицы становятся карточками |
| CLI / TUI | `cobra`, Bubble Tea v2 + Lip Gloss v2 |
| ACME | `lego` как библиотека |
| Почта | postfix + dovecot (IMAP/POP3/LMTP/sieve) + opendkim, вебпочта Roundcube |
| systemd | D-Bus (`go-systemd`) |
| Упаковка | `nfpm` → .deb/.rpm, релизы с подписанными контрольными суммами |

## Разработка

```bash
make build            # dist/monopanel
make check            # gofmt + go vet + golangci-lint + тесты + проверка типов Web UI
make web              # Web UI в web/build (нужен node + pnpm)
make help             # все цели
```

Прогон всего набора занимает пару секунд, поэтому его дёшево запускать на каждое
изменение.

| Команда | Что делает |
| --- | --- |
| `make test` | юнит-тесты; вся логика панели проверяется через фейковый агент, без root и systemd |
| `make check` | то же плюс `gofmt`, `go vet`, `golangci-lint` и `svelte-check` — то, что гоняет CI |
| `make test-race` | детектор гонок (≈1 мин): очередь задач, SSE-брокер, кеш сертификатов |
| `make cover` | покрытие по пакетам; `make cover-html` — отчёт в браузере |
| `make web-check` | типы и разметка Web UI (`svelte-check`) |
| `scripts/check-templates.sh` | скармливает сгенерированные конфиги настоящим `nginx -t` и `apache2 -t` (вся конфигурация Apache аккаунта с виртуальным хостом) |
| `make e2e` | сценарий на живой панели: пользователь → сайт с пресетом → база → удаление |
| `make testbed-matrix` | тот же сценарий на одиннадцати VM площадки (по одной на каждую ОС матрицы) параллельно, с откатом к чистому снимку; `make testbed-migrate SRC= DST=` — настоящий переезд аккаунта между двумя из них с проверкой |

Фейковый агент (`internal/agent/agenttest`) поднимает unix-сокет и отвечает на операции
привилегированного агента, записывая всё, что панель попыталась сделать. Тест видит
содержимое сгенерированного server-блока nginx и пула php-fpm и проверяет поведение
целиком: пресеты CMS, allow-list по IP, приостановку сайта, каскадное удаление
пользователя, проверку подписи обновления.

`internal/parity` сверяет три клиента с API: у каждой операции должны быть команда `mp`
и место в Web UI, у каждой команды — место в меню TUI, у каждого поля запроса — флаг и
поле на странице, а обычному аккаунту не должно достаться действий администратора.
Тест называет, чего и где не хватает; намеренные исключения перечислены в нём самом и в
[docs/04-cli-tui-api.md](docs/04-cli-tui-api.md#1-принцип).

End-to-end гоняется против настоящей панели и убирает за собой всё, что создал:

```bash
make e2e HOST=<ssh-алиас>   # токен берётся по ssh и отзывается после прогона
# или явно:
MONOPANEL_URL=https://panel:8443 MONOPANEL_TOKEN='…' make e2e
```

CI на каждый push: тесты с детектором гонок и покрытием, линтер, проверка шаблонов
реальными `nginx -t` и `apache2 -t` (вся конфигурация Apache аккаунта с виртуальным хостом), сборка Web UI с проверкой типов, сборка бинарника под amd64
и arm64. E2E запускается вручную (`workflow_dispatch`) — ему нужен доступ к живому хосту.
Матрица ОС гоняется с рабочего места на площадке Proxmox
([docs/08-testbed.md](docs/08-testbed.md)): скрипты в `scripts/testbed/`, адрес хоста и
сеть — в git-игнорируемом `.dev/testbed.env`.

```
cmd/monopanel/        точка входа

internal/jobs/        очередь задач, воркеры, брокер событий

internal/osprofile/   различия Debian/RHEL

internal/updater/     поиск релиза, проверка подписи, установка пакета с откатом
internal/cli/ tui/    команды mp и TUI-меню
internal/client/      Go-клиент API (CLI, TUI, setup)
internal/parity/      проверка, что Web UI, mp и TUI умеют одно и то же
templates/            nginx/, apache/, php-fpm/, systemd/
web/                  SvelteKit-приложение (build/ вшивается в бинарник)

```
