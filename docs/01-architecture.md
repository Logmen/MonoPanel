# 01. Архитектура MonoPanel

Состояние на октябрь 2026 (MonoPanel 0.9.3). Версии компонентов указаны на этот момент; перед релизом их проверяет прогон матрицы ОС на [площадке](08-testbed.md).

> Это проектный документ: он описывает решения и их обоснование, в том числе те части, до которых реализация ещё не дошла. Что действительно работает — в [README](../README.md) и в отметках [x] в [05-roadmap.md](05-roadmap.md). Ниже такие места помечены как «планируется».

## 1. Цели и границы

**Что делаем**

- Панель управления веб-хостингом на одном сервере (класс FASTPANEL / ISPmanager Lite).
- ОС: Debian 12/13, Ubuntu 22.04/24.04/26.04 LTS; RHEL 9/10 и клоны (AlmaLinux, Rocky Linux, Oracle Linux).
- Режимы сайта: `nginx → php-fpm` и `nginx → Apache → php-fpm`.
- PHP 5.6 … 8.5 одновременно, версия выбирается на сайт; расширения по версиям.
- СУБД: MySQL 8.4 LTS **или** Percona Server for MySQL 8.4 LTS (выбор при установке, единый провайдер в коде).
- Интерфейсы: Web UI, CLI (скриптуемый, `--json`), TUI-меню (интерактивное, по SSH), REST API (OpenAPI 3.1).
- TLS (ACME), бэкапы, cron, firewall, защита от перебора, метрики, логи, файловый менеджер.

**Чего не будет в 1.0** (см. [дорожную карту](05-roadmap.md)): DNS-сервера, управления несколькими серверами, контейнерных приложений, WAF, роли реселлера. Почта (postfix + dovecot + opendkim + Roundcube) в первоначальный план не входила, появилась позже и описана отдельно — [06-mail.md](06-mail.md).

## 2. Архитектурные решения (ADR, кратко)

| # | Решение | Почему |
|---|---|---|
| A1 | Ядро панели — один статический бинарник на **Go** | На хосте не нужен рантайм (два семейства ОС, одиннадцать релизов); один файл — и демон, и CLI, и TUI; простая упаковка в .deb/.rpm, быстрый старт CLI, встроенные HTTP-сервер и TLS |
| A2 | **Разделение привилегий**: `monopaneld api` (пользователь `monopanel`) ↔ `monopaneld agent` (root) через unix-сокет | Код, который разбирает чужой ввод и отдаёт веб-интерфейс, не работает от root. Агент принимает только типизированные команды с allow-list путей и операций |
| A3 | **Один API для всех клиентов**: Web UI, CLI, TUI и внешние интеграции ходят в один REST API | Нет расхождений в логике; всё, что можно в Web, можно в CLI и TUI и наоборот — это проверяет тест `internal/parity` (§11) |
| A4 | **Декларативное состояние → рендер → валидация → атомарное применение → reload, с откатом** | Панель — источник истины; ручные правки живут в include-каталогах; сломанный конфиг никогда не доходит до reload |
| A5 | Панель слушает **собственный** HTTPS-порт (8443) на Go `net/http`; сам порт держит systemd (`monopanel-api.socket`) и передаёт его процессу | Панель доступна, даже если системный nginx сломан или ещё не установлен; пока API перезапускается или остановлен, порт занят, и локальный пользователь не поднимет на нём поддельную панель |
| A6 | Состояние панели — **SQLite** (WAL) | Панель обязана работать, когда MySQL не установлен или упал; бэкап состояния — один файл |
| A7 | PHP: **один php-fpm master на версию, пул на сайт**; Apache — только через `mod_proxy_fcgi` | Одна FPM-инфраструктура для обоих режимов; переключение режима = смена шаблона nginx/Apache. `mod_php` не поддерживается принципиально (одна версия на процесс Apache, работа от `www-data`) |
| A8 | PHP-сборки: этап 1 — репозитории Sury (deb) / Remi (rpm); этап 2 — **собственные сборки** с единой раскладкой `/opt/monopanel/php/<X.Y>` | Быстрый старт без сборочной фермы; затем независимость от сторонних репозиториев (каждый держит один человек) и одинаковые пути на всех ОС |
| A9 | nginx — из **nginx.org** (stable) на всех ОС; Apache — из дистрибутива | Одинаковая раскладка nginx (`conf.d`, пользователь `nginx`) и свежие версии с HTTP/3 на всех ОС; Apache в дистрибутивах достаточно свежий и хорошо уживается с SELinux и AppArmor |
| A10 | Абстракция ОС — **OS Profile** (`debian`, `rhel`): пакетный менеджер, пути, имена сервисов, MAC (SELinux/AppArmor), firewall | Вся разница между семействами локализована в одном пакете кода |
| A11 | ACME-клиент встроен (библиотека **lego**) | Без certbot/python на хосте; HTTP-01 и DNS-01 (wildcard) из одного места, единая логика продления |
| A12 | Файловые операции от имени клиента — через **helper с понижением привилегий** | Защита от symlink-атак и подмены путей: агент никогда не трогает файлы клиента от root |
| A13 | Внутренний RPC api↔agent — HTTP/JSON поверх unix-сокета с `SO_PEERCRED` | Те же типы и инструменты, что во внешнем API; когда серверов станет несколько, транспорт сменится на mTLS без переписывания операций |

### 3.1 `monopaneld api` — непривилегированный процесс

- HTTPS-сервер панели (порт 8443, привязка к IP по выбору; сертификат: self-signed при установке → ACME для hostname панели). Порт привязывает PID 1 через сокет `monopanel-api.socket` (`BindIPv6Only=both`, `FreeBind=yes`) и передаёт API (socket activation): при перезапуске, падении, остановке API и на загрузке до его старта порт занят, и локальный аккаунт (клиент с SSH, PHP сайта) не займёт его, чтобы собирать пароли и коды TOTP администраторов. Адрес следует `web.listen` через drop-in `/etc/systemd/system/monopanel-api.socket.d/listen.conf`, который пишет только root: агент при смене `web.listen` через API, `mp setup`, `mp config set --local` и скрипт пакета (`monopanel api-socket-sync`). API его не пишет и содержимое не выбирает. Порт ниже `net.ipv4.ip_unprivileged_port_start` сокет не держит: такой порт и так не займёт непривилегированный процесс, а PID 1 отдал бы API порт, который тот сам привязать не может. Без сокета API слушает `web.listen` сам, как раньше. Сокет на другом адресе API закрывает со своей стороны, с предупреждением в журнале, и тоже слушает `web.listen` сам; если сокет держит тот же порт на другом адресе (`web.listen` правили руками или drop-in не удалось записать), API ещё и останавливает его через агента. Сокет переходит на `web.listen` только после `mp setup` или `mp config set --local web.listen …`; перезагрузка этого не исправляет. Неудачный старт API, запущенного сокетом, ждёт 2 с перед выходом: иначе ожидающее соединение перезапускало бы его без паузы, и после 20 запусков за 2 с systemd закрыл бы сокет (trigger-limit-hit), освободив порт. API сначала занимает всё, на чём работает, — сертификат, локальный сокет `api.sock`, HTTPS-порт (сокет systemd или свой), — и только потом запускает задачи, стартовое обновление и фоновые циклы (продление сертификатов, резервные копии по расписанию, ежедневное обновление). Старт, которому это не удалось (порт `web.listen` занят другим процессом, ключ TLS не читается, `api.sock` не заменить), ничего на хосте не меняет: в журнале — `monopanel api cannot start`, процесс завершается, и systemd запускает его снова (`Restart=on-failure`; запущенный сокетом — после паузы 2 с). Если сервер упал уже во время работы, вместе с ним останавливаются и задачи; прерванные выполняются снова после перезапуска. Откуда порт у работающего API, говорит `GET /system/status` (`panel.listen_via`: `socket` или `itself`).
- Раздаёт Web UI (SvelteKit static-сборка, вшита через `embed.FS`).
- REST API `/api/v1`: OpenAPI 3.1 генерируется из Go-типов (`huma`), SSE для прогресса задач. Веб-терминал на WebSocket — планируется; пока в Web UI есть «Консоль»: команды `mp` с потоковым выводом по HTTP.
- Аутентификация: сессии (cookie `Secure; HttpOnly; SameSite=Strict`), Bearer-токены, TOTP; WebAuthn (passkeys) — планируется. RBAC: `admin`, `user`. Scope у токена ограничивает только токены переезда (`migrate:user:<логин>`, бывают только у администраторов — §7), остальные scope — пометки.
- Unix-сокет `/run/monopanel/api.sock` для CLI (0660, группа `monopanel-cli`): uid 0 → admin без пароля; uid аккаунта с shell-доступом → его права (клиент по SSH управляет своими сайтами через `mp`). Аккаунты без shell в группу не входят, а запрос из рабочего процесса php-fpm, Apache или nginx — в том числе через `exec()` — отклоняется по цепочке предков в `/proc`: взломанный сайт не должен управлять аккаунтом своего владельца.
- Очередь задач в SQLite и несколько воркеров: задача — последовательность повторяемых шагов с логом и прогрессом; над одной сущностью одновременно идёт только одна задача (блокировка по `site_id`/`user_id`). Задача идёт не дольше часа от своего старта, потом её контекст заканчивается и она падает; бэкапу (`backup.run`) дано 8 часов — 6 у restic на сам бэкап, час на чистку по политике хранения и час перед ними, которого обычно хватает на установку пакета, проверку репозитория и дампы баз (каждый дамп может идти до часа), — восстановлению (`backup.restore`) 7 — 6 у restic и ещё час, — переезду (`migrate.run`) сутки: он переносит аккаунт целиком — домашний каталог, каждую базу и Maildir каждого почтового домена по очереди, и каждый такой поток агент обрывает через 6 часов. Пока такие долгие задачи занимают все воркеры (`jobs.workers`), ещё один воркер берёт остальные задачи, по одной, чтобы применение сайта или продление сертификата не ждали часами; долгих задач он не берёт и, пока свободен хотя бы один из воркеров `jobs.workers`, не берёт ничего. Задачу, которую API при старте застал выполняющейся (его перезапустили посреди неё), он снова ставит в очередь, и она начинается заново, с полным лимитом; переезд же сразу останавливается на аккаунте, который создал его первый запуск (`account <login>: already exists`): этот аккаунт удаляют (`mp user rm <логин> --purge`) и запускают переезд снова. Поэтому автоматическое обновление, которое перезапускает API, ждёт, пока бэкап, восстановление или переезд стоят в очереди или идут, и ставится в один из следующих ежечасных заходов; обновление, которое запустил администратор, не ждёт.
- Перед работой старта (переезды обновления, перепроверки) API ждёт агента — пингует его с паузой от 1 до 15 секунд, пока работает сам, и пишет об этом в журнал (`start-up refresh: waiting for the agent`, `the agent answers`); воркеры не берут задания, пока агент не ответит или не пройдут шесть минут — вдвое больше того, что агент может занять до того, как начнёт слушать (проверки песочницы бэкапов, забор mount-юнитов общих папок прежней версии, уборка после запусков пакетного менеджера прежнего агента). Переезды обновления хранят результат, а не очередь: незавершённые API раз в час ставит в очередь снова, когда подошёл срок следующей попытки (§9).
- Рендер конфигураций (`text/template`) из встроенных шаблонов с переопределением в `/etc/monopanel/templates/`.
- Планировщик внутренних задач: продление сертификатов, бэкапы по расписанию, сбор метрик, проверка обновлений панели, ежедневное обновление nginx, PHP и Apache (§9).
- Хранит ключи ACME и секреты клиентов в зашифрованном виде (см. 3.6).

### 3.2 `monopaneld agent` — привилегированный процесс

- Тот же бинарник, режим `agent`, unit `monopanel-agent.service`, root.
- Сокет `/run/monopanel/agent.sock` (0660 root:monopanel). Проверка `SO_PEERCRED`: принимаются только uid `monopanel` и root.
- Операции — закрытый типизированный набор (нет «выполни строку в shell»):
  - `config/apply` — транзакционная запись набора файлов: прежние версии уходят в `confhistory` → запись во временный файл + `rename` → валидаторы (`nginx -t`, `apache2 -t -f /etc/apache2/monopanel/accounts/<логин>/httpd.conf`, `php-fpm -t`) → при ошибке восстановление и возврат stderr; при успехе reload сервисов.
  - `user/ensure|remove|password|shadow`, `group/ensure`, `dirs/ensure`, `file/ensure|read`, `sitelogs/ensure|remove`, `symlink/ensure`, `acl/set`, `chown`, `paths/remove`, `dir/list`, `stat`.
  - `shares/bind|unbind|status|records` — общие папки: монтирование из открытых каталогов, размонтирование, что лежит в точках монтирования и записи агента о папках (§7, [10](10-shared-folders.md)).
  - `service` — start/stop/reload/restart/enable/disable/status и daemon-reload через systemd D-Bus (`go-systemd`), а не `systemctl`.
  - `pkg` — update-index/install/remove/upgrade и чтение (query/available/candidates) через apt/dnf по OS Profile, с глобальной блокировкой и логом в задачу. `candidates` только читает индекс (что предлагают репозитории для установленных пакетов), `upgrade` обновляет только установленные пакеты из набора панели (§7). Запуск менеджера пакетов не зависит от запроса API: перезапуск `monopanel-api` или предел времени задачи не обрывают apt/dnf посреди транзакции. Изменения запускает не агент дочерним процессом, а systemd — transient-юнитом `monopanel-pkg-<run>.service` (как `monopanel-update.service` при обновлении панели), так что и остановка или перезапуск самого агента — самообновлением, `systemctl restart`, цепочкой `Requires=` API — не обрывает транзакцию dpkg/rpm. У юнита те же ограничения, что у агента (`ProtectHome=read-only`, `PrivateTmp`, `ProtectKernel*`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `RestrictRealtime`, `LockPersonality`, `SystemCallArchitectures=native`), и `OOMPolicy=continue`. Вывод идёт не в pipe, а в файл агента `/var/lib/monopanel-agent/pkg/<run>.out` (root, 0600; systemd получает его дескриптор): агент читает его после запуска и удаляет, а файлы запусков, переживших прежний агент, пишет в свой журнал и удаляет, когда запуск закончился. Изменения идут по одному; после перезапуска агент сначала ждёт запуск, оставшийся от прежнего агента, и установку обновления панели. Обновление индекса пакетов агент повторяет до десяти минут, пока другой `apt-get update` держит блокировку списков (`/var/lib/apt/lists/lock`) — так бывает с apt-daily сразу после загрузки: `DPkg::Lock::Timeout` касается только блокировок dpkg, и раньше такое обновление падало сразу (установка PHP, обновление стека; переезд на Sury откладывался до следующего старта API). Свободна ли блокировка, агент спрашивает у неё самой (fcntl), а не новым запуском apt, и запускает обновление снова, когда она освободилась: в журнале systemd остаётся одна неудачная попытка юнита `monopanel-pkg-<run>.service` («Failed to start MonoPanel package manager…», приоритет err), а не по одной каждые пять секунд. Блокировку скачанных пакетов (`/var/cache/apt/archives/lock`) установка не ждёт: пока её держит другой apt без блокировки dpkg, установка падает сразу. Это редкость: unattended-upgrade сначала берёт блокировку dpkg, а её установка ждёт. apt и dnf агент запускает с пустым `LANGUAGE`: иначе `LANGUAGE`, заданный на сервере, переводил бы вывод apt, в котором панель ищет нужные слова. Предел — 2 часа: агент останавливает юнит, а если агента нет — systemd через минуту. `TimeoutStopSec` запуска — 90 секунд, что бы ни задал администратор в `DefaultTimeoutStopSec`. После запуска его `/tmp` и `/var/tmp` очищает `ExecStopPost` (`monopanel clean-private-tmp`), если это собственный `/tmp` юнита; иначе в конце журнала задачи остаётся строка «… left as they are» ([02 §6](02-platform-matrix.md#6-selinux-el9--el10)). Запуск, который остановила не панель (`systemctl stop`, выключение), агент дожидается до конца и сообщает «stopped outside the panel (…)»; упавшего юнита он не оставляет. Если агент пропал посреди вызова, задача получает сообщение с именем юнита и командой `journalctl -u monopanel-pkg-<run>.service`. Установка почты на EL 9 с CodeReady Builder (`dnf install --enablerepo=crb`) идёт тем же путём; её предел — 15 минут от начала самого запуска, а не от запроса: ожидание очереди пакетного менеджера его не съедает. Release-пакет (percona-release на Debian и Ubuntu) агент скачивает в `/var/lib/monopanel-agent/pkg/release-*` и удаляет после запуска; оставшиеся от прежнего агента удаляются при старте, когда ни один запуск не идёт.
  - `apache/legacy` читает для обновления собственные директивы общего Apache 0.8.19: только обычные файлы `*.conf` с единственным именем в `/etc/apache2/monopanel/sites/<домен>.d/`, не больше 1 МиБ на файл, вместе с их правами; путь до `/etc/apache2/monopanel` проходится так же, как к другим каталогам `/etc` (допускается символьная ссылка root в каталоге root), а от `sites/` и ниже — без единой символьной ссылки; без домена — имена в `sites/`.
  - `tool` — закрытый список программ с проверкой аргументов: `mysql`/`mysqldump` (root через `auth_socket`, пароль root не хранится), `restic`, `nft`, `crontab`, `semanage`/`restorecon`/`setsebool`, `firewall-cmd`, `postfix`/`doveadm` и другие.
  - `runas` — helper с понижением привилегий для файловых операций клиента; `stream/in|out` — потоки tar для переезда; `panel/install` — установка пакета панели при обновлении; `panel/config` — собственные настройки панели в `config.yaml`, ровно пять ключей (`web.hostname`, `web.listen`, `log.level`, `log.format`, `jobs.workers`): остальной файл остаётся байт в байт, права и владелец — прежними, прежняя версия уходит в `confhistory`.
- Allow-list путей записи (`DefaultAllowedWritePrefixes` в `internal/config`): `/etc/monopanel/`, каталоги панели в конфигах nginx и Apache, конфиги PHP (`/etc/php/`, `/etc/opt/remi/`), MySQL, почты, memcached, Sphinx, источники пакетов, `/etc/nftables.d/`, `/etc/logrotate.d/`, `/etc/fail2ban/jail.d/`, снимки Valkey `/var/lib/monopanel-valkey/`, `/var/lib/monopanel/`; crontab — через `crontab -u`; файлы клиентов `/var/www/<user>/...` — через `runas`. Исключения из allow-list — `config.yaml` и `secret.key`: общие операции не пишут, не удаляют и не меняют права и владельца ни их, ни каталогов над ними (§7).

### 3.3 Helper (drop-privileges)

`monopaneld helper --uid N --gid N --groups ... -- <op> <args>`: агент форкает процесс, который до выполнения операции необратимо понижает привилегии (`setgroups` → `setgid` → `setuid`) и работает с файлами как клиент. Через него идут файловый менеджер, загрузка и распаковка архивов, установщики CMS (`wp-cli` и другие); git-деплой и терминал — планируются. Сам helper не имеет привилегированных путей кода.

### 3.4 Web UI

- SvelteKit 2 (Svelte 5, runes), `adapter-static`, TypeScript strict, Tailwind CSS 4. Сторонних UI-библиотек нет: компоненты, графики и таблицы свои; единственная внешняя зависимость в рантайме — `qrcode` (QR-код для TOTP).
- Два языка без библиотеки: словарь `web/src/lib/i18n` (фрагмент на страницу, `frag({ en, ru })` — тип требует одинаковый набор ключей, `t()`/`tn()` читают текущий язык из состояния на рунах, так что переключение перерисовывает всё сразу). Язык по умолчанию берётся из `navigator.languages`: языки стран СНГ → русский, остальные → английский; выбор в настройках хранится в `localStorage.lang`, `<html lang>` выставляется до загрузки приложения. Сообщения API, задач и диагностики — на английском; CLI и TUI выбирают язык по локали терминала по тому же правилу (`internal/i18n`, `MP_LANG=ru|en` задаёт его явно).
- Планируется: библиотека компонентов (shadcn-svelte / Bits UI), TanStack Query + Table, CodeMirror 6 для редактора конфигов, xterm.js для терминала, генерация клиента из OpenAPI (`@hey-api/openapi-ts`).
- Сборка в `web/build` и вшивание в бинарник; SPA, один HTML, целевой размер JS ≈ 200–300 КБ gzip.
- Два режима интерфейса: администратор видит весь сервер и все страницы; обычный аккаунт — дашборд (нагрузка и службы сервера, без диагностики), а на страницах сайтов, «Аккаунта» (свои cron, app-сервисы, Valkey, общие папки, API-токены и пароль), баз данных, почты, файлов, задач, журнала и настроек — только своё. Страницы по одной — в [09-web-ui.md](09-web-ui.md).

### 3.5 CLI и TUI

- `monopanel` (alias `mp`) — Cobra-команды, вывод таблицей или `--json`. Коды выхода: 0 — успех, 1 — ошибка, 2 — неверные аргументы или нет нужного ввода, 3 — задача завершилась с ошибкой, 4 — нет прав. У каждого секрета — паролей, токенов, секрета webhook, учётных данных DNS-провайдера, переменных бэкапа и app-сервисов — есть двойник `--…-stdin`: значение не остаётся ни в истории команд, ни в `ps`.
- Без аргументов в интерактивном терминале — TUI-меню (Bubble Tea v2 + Lip Gloss). Разделы повторяют навигацию Web UI, и обычный аккаунт видит те же разделы и команды, что в Web UI. Каждое действие — команда `mp`: форма строится из её флагов, рядом видна эквивалентная строка `mp` (секреты скрыты), команда запускается дочерним процессом того же бинарника, а её вывод идёт на экран по ходу выполнения. Перед тем, что удаляет или прерывает, TUI спрашивает так же, как Web UI, а удаление аккаунта, удаление сайта с файлами и восстановление снимка поверх файлов просят набрать имя аккаунта, домен или снимок. `?` или F1 — действия экрана, команды раздела и клавиши, `:` — любая команда `mp`, `*` — все команды раздела. Работает по SSH: локально через сокет, удалённо — с `--server` и `--token`; дочерним командам адрес и токен передаются через окружение, а не в командной строке.
- CLI/TUI — тонкие клиенты API (локально `/run/monopanel/api.sock`, удалённо `https://host:8443` с токеном; переменные окружения `MP_SERVER`, `MP_TOKEN`, `MP_INSECURE=1`). Ни одна операция не реализована «только в CLI»: без API работают только `help`, `completion`, `version`, а от root на сервере — `setup`, `config show|set --local` (восстановление, когда API не запускается) и `update trust`.
- Что каждая операция и каждое поле запроса API доступны из Web UI, `mp` и TUI, кроме намеренных исключений, проверяет тест `internal/parity` (§11). Детали и список исключений — в [04-cli-tui-api.md](04-cli-tui-api.md).

### 3.6 Хранилище состояния

- `/var/lib/monopanel/panel.db` — SQLite, WAL, `foreign_keys=ON`, `busy_timeout`. Драйвер `modernc.org/sqlite` (чистый Go, без CGO — бинарник остаётся статическим). Запросы написаны руками в `internal/store`, миграции — встроенные SQL-файлы, применяются при старте.
- Секреты (пароли БД клиентов, токены DNS-провайдеров, ключи ACME, пароли SFTP/S3 бэкапов, секреты, которыми nginx открывает Apache аккаунтов) шифруются AES-256-GCM ключом из `/etc/monopanel/secret.key` (0640 root:monopanel). Бэкап SQLite без ключа для атакующего бесполезен.
- История конфигов: `/var/lib/monopanel-agent/confhistory/` (каталог агента, только root; до 0.8.19 — `/var/lib/monopanel/confhistory/`) — прежние версии сгенерированных файлов, которые агент сохраняет при записи; diff в UI и ручной откат — планируются.
- Снимок состояния входит в бэкап сервера (`mp backup run`, область `server`): копия `panel.db` (`VACUUM INTO`), `/etc/monopanel` вместе с ключом секретов, `/var/lib/monopanel/{certs,acme}`, `/var/www` и дампы всех баз. Восстановление панели из него на новом сервере — вручную; если базу панели восстанавливают на том же сервере, общие папки, которых в ней нет, панель при старте размонтирует сама ([10](10-shared-folders.md)). Переносить аккаунты между живыми серверами удобнее `mp migrate` ([07](07-migration.md)).

### 3.7 Почтовая политика

`monopanel-mailpolicy.service` — тот же бинарник в роли milter postfix (`monopanel mail-policy`), от своего системного пользователя `monopanel-mail`, без привилегий, на сокете, который держит systemd (`monopanel-mailpolicy-unix.socket` на Debian и Ubuntu, `monopanel-mailpolicy-inet.socket` на EL): postfix спрашивает его раньше opendkim, кто отправитель и чей домен в письме. На EL `monopanel-mailguard.service` (root, oneshot) загружает таблицу nftables, которая пускает к портам milter (8890 политики, 8891 opendkim) только root и postfix. Политику (`/etc/postfix/monopanel/mail-policy.json`) пишет API через агента; служба только читает её и `/proc/net/tcp`. Подробно — [06 §11](06-mail.md#11-почтовая-политика).

## 4. Стек панели и обоснование

### 4.1 Бэкенд / ядро

- WebSocket только для интерактивного терминала (планируется).
- Внутренний RPC api↔agent — тот же HTTP/JSON поверх unix-сокета (те же типы huma), с обязательной проверкой peer-cred.

Основные сущности (упрощённо):

```
                 quota_mb, email, created_at

                 log_path, requested_by, lock_key, idempotency_key, created_at, finished_at

sessions         id, user_id, expires_at, ip, ua

```

Инварианты:
- `domain` уникален (punycode, нижний регистр, без завершающей точки); алиас не может совпадать с доменом другого сайта.
- Один сайт = один пул FPM = один unix-сокет `/run/monopanel/php/<domain>.sock`.
- `php_version` ссылается на установленную версию; удаление версии блокируется, пока есть сайты на ней.
- Удаление пользователя каскадно удаляет сайты/БД/cron/сертификаты только с явным `purge` (иначе — `suspend`).
- Задачи с одинаковым `lock_key` выполняются строго последовательно. Кроме того, обновление стека (`stack.upgrade` — ежедневное и `mp stack upgrade`) и обновление панели (`panel.update`) не выполняются одновременно ни в каком порядке, хотя ключи у них разные (`stack`, `panel:update`): пришедшая второй ждёт в очереди и не падает; остальные задачи идут рядом с ними, как раньше.

## 6. Конвейер применения конфигурации

```
API: PATCH /sites/{domain} ─▶ валидация ─▶ desired state в SQLite ─▶ job "site.apply" (lock_key=site:<id>)
                                                                      │
worker: 1) собрать модель сайта из БД (site + user + php_version + cert + ip + settings)
        2) отрендерить: nginx sites/<domain>.conf, пул FPM, (default-server IP);
           в режиме apache — ещё httpd.conf и sites/<domain>.conf Apache аккаунта
        3) режим apache, раньше nginx: agent.ApplyConfigSet(httpd.conf + виртуальный хост,
              validate = ["apache2 -t -f <httpd.conf аккаунта>"], reload = [monopanel-apache@<login>])
           — или запуск и enable, если он не работал, и ожидание ответа на его адресе
        4) agent.ApplyConfigSet(
              files    = [...],
              validate = ["nginx -t", "php-fpm -t -y <fpm.conf>"],
              reload   = [nginx, php-fpm@X.Y (или старый и новый master при смене версии)])
           агент: backup старых файлов → запись во временные → rename → валидаторы;
                  ошибка → восстановить backup → вернуть stderr валидатора в лог задачи;
                  ok     → reload через D-Bus → confhistory
        5) сайт ушёл из режима apache или приостановлен — теперь, после nginx, он уходит из Apache аккаунта
        6) пост-шаги: restorecon (SELinux), ACL, симлинк data/bin/php при смене версии
        7) job=done, событие SSE ⇒ UI обновляет карточку сайта
```

В режиме apache сайт сначала получает Apache своего аккаунта: `httpd.conf` и `sites/<домен>.conf`, `apache2 -t -f`, reload (graceful) или запуск и `enable`, ожидание ответа на его адресе; затем nginx и php-fpm — пока nginx не перезагрузится, сайт обслуживается там, где был. Сайт, уходящий из Apache (режим, приостановка, удаление), сначала уходит из nginx, потом из Apache. Apache без сайтов останавливается и выключается, его `httpd.conf` и виртуальные хосты удаляются; собственные директивы сайта (`sites/<домен>.d/`) остаются, пока жив сайт, а каталог аккаунта уходит с последним его сайтом. Apache одного аккаунта меняется по одному сайту за раз: задания двух его сайтов, идущие параллельно, не мешают друг другу.

Принципы:
- Панель владеет только файлами в своих каталогах и главным `nginx.conf` (по шаблону, с `include conf.d/*.conf` для ручных правок). Чужие конфиги не редактируются построчно.
- Пользовательские правки — только через include-каталоги `<domain>.d/*.conf`; панель их не перезаписывает, но валидирует вместе со всем набором.
- Шаблоны переопределяются файлом с тем же путём в `/etc/monopanel/templates/` (например `nginx/site.conf.tmpl`); `mp config templates` (и карточка «Шаблоны конфигураций» в настройках Web UI) перечисляет встроенные и показывает, какие из них переопределены. Команды, которые копируют встроенный шаблон и показывают его расхождение с новой версией панели, — планируются.
- Сайт перегенерируется из БД целиком командой `mp site apply <домен>` (`mp site fix` — ещё и владелец, права и метки файлов). Полный reconcile всего сервера одной командой — планируется.
- Смена версии PHP: новый пул создаётся до удаления старого, оба master перезагружаются, затем переключается nginx/Apache — простоя нет.
- Запуск, перезапуск или reload-or-restart юнита (операция `service`, перезагрузки `config/apply` и `paths/remove`), который systemd отклонил из-за лимита запусков (`Result=start-limit-hit`: юнит перезапускали слишком часто — пакеты ветки PHP, новые сайты для fail2ban, — а не он падал), агент повторяет один раз: после `reset-failed` и тех же проверок, что перед первой попыткой (деревья php-fpm и логов сайтов, mount-юниты ниже веб-корня); юнит, отказавший снова, — ошибка с его собственной причиной. Цикл падений так не обойти: когда лимит останавливает перезапуски падающего юнита, systemd оставляет в `Result` причину падения (`exit-code`, `signal`…), и такой юнит агент не сбрасывает; каждый юнит, который называет вызов API, получает не больше одного повтора.

## 7. Безопасность

- Панель: TLS 1.2/1.3, HSTS, CSP без inline-скриптов, проверка Origin у мутаций по сессии (cookie и так `SameSite=Strict`), ограничение частоты входа + jail fail2ban по логу панели, argon2id, TOTP (WebAuthn планируется), аудит всех мутаций, API-токены со scope и сроком, по желанию привязка панели к отдельному IP или VPN.
- Сессии и токены: смена пароля завершает остальные сессии аккаунта в браузерах (та, из которой его сменили, остаётся), а сброс пароля администратором и блокировка аккаунта — все; API-токены при этом не отзываются — их отзывают отдельно, — но у заблокированного аккаунта не действуют, пока его не разблокируют. Двухфакторную аутентификацию нельзя настроить заново поверх включённой: сначала её выключают, а для этого нужен пароль. Область переезда (`migrate:user:<логин>`) открывает хеши паролей, ключи, файлы и базы аккаунта, поэтому бывает только у токенов администраторов: обычный аккаунт не может записать её в свой токен, администратор — в токен, который выпускает обычному аккаунту, а обработчики `/migrate` требуют роль администратора при любой области. Такие токены обычных аккаунтов, оставшиеся с прежних версий, панель отзывает при старте и пишет об этом в журнал действий. Логины системных учёток сервера (uid ниже `UID_MIN`) и имена, которыми панель подписывает свои задачи и записи журнала (`scheduler`, `system`), аккаунтам не даются.
- Процессы: api — `User=monopanel`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, `CapabilityBoundingSet=` (пусто), `ReadWritePaths=/var/lib/monopanel /run/monopanel /var/log/monopanel`; agent — root (ставит пакеты, заводит пользователей, пишет `/etc`), поэтому `ProtectSystem=` и урезанные capabilities ему невозможны, но остальное отрезано: `ProtectHome=read-only` (клиенты живут в `/var/www`), `ProtectKernelModules`, `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `PrivateTmp`, `RestrictRealtime`, `LockPersonality`, `SystemCallArchitectures=native`; плюс allow-list операций и путей, все exec — массив `argv` без shell. У юнита агента есть `ExecStopPost=-/usr/bin/monopanel clean-private-tmp monopanel-agent.service`: до 0.8.19 агент запускал скрипты пакетов своими дочерними процессами, и то, что они оставили в его `/tmp`, он убирает сам ([02 §6](02-platform-matrix.md#6-selinux-el9--el10)). Изменения пакетного менеджера агент запускает transient-юнитом с теми же ограничениями, что у него самого (§3.2); аргумент с `$` (systemd раскрыл бы его в командной строке юнита) не передаётся.
- Агент: `config.yaml` и `secret.key` не трогает ни одна общая операция записи, удаления, смены прав или владельца, хотя `/etc/monopanel/` в allow-list (там шаблоны и модуль SELinux): в `config.yaml` решается, каким ключом проверяются релизы, ставящиеся от root (`update.public_key` подменяет вшитый ключ или выключает проверку), а `secret.key` расшифровывает все секреты. Пять собственных настроек в `config.yaml` панель меняет отдельной операцией `panel/config`, остальное в файле — только root (`mp config set --local`, `mp update trust`). Каталоги и файлы под `/var/www` агент создаёт и читает от root, проходя путь по одному каталогу и не следуя символьным ссылкам: клиент, подменивший каталог ссылкой, не направит такую запись в `/etc` или `/root` и не прочитает через неё `/etc/shadow`. Логи сайтов, которые от root открывают nginx, Apache и php-fpm, лежат вне домашних каталогов, в `/var/log/monopanel/sites/<логин>/`, где записи создаёт и меняет только root; агент проходит это дерево так же и не работает в каталоге, куда может писать кто-то ещё, а читает логи для API только через каталоги без ссылок и файлы с единственным именем. Каталог сокетов пулов `/run/monopanel/php` и дерево логов `/var/log/monopanel/sites` лежат в каталогах, куда пишет и API (`root:monopanel` 1771, с битом sticky), а мастера php-fpm, nginx и Apache действуют в них от root по имени: php-fpm удаляет то, что лежит на пути сокета, создаёт сокет и меняет его владельца и ACL по пути, серверы создают и дописывают логи. Поэтому оба дерева принадлежат root раньше, чем стартует API: `php/` создаёт systemd-tmpfiles при загрузке по строке `d /run/monopanel/php 0755 root root -` из файла пакета и `mp setup`, оба дерева — агент при старте. Каталог, который сделал кто-то другой (до 0.8.19 это мог API), агент при старте забирает себе через открытый каталог: сначала владелец root, затем ACL снимаются, затем права; с `php/` ACL снимается, даже если каталог уже принадлежит root (systemd-tmpfiles из postinstall передаёт root владельца и права, но не ACL). Потом агент вычищает дерево от того, что туда кладёт не root: удаляет ссылки, FIFO, файлы со вторым именем (кроме журнала ошибок PHP самого аккаунта) и сокеты служебного пользователя в `php/`, а каталоги переносит в карантин `untrusted-<время>-<случайное>` (0700 root) рядом с деревом. Запись, которую убрать не удалось, не мешает остальным: каждый каталог аккаунта агент всё равно забирает и ссылки удаляет. Пока дерево логов не только root'а или не вычищено до конца (например, на заполненном диске не создать карантин), агент не запускает, не перезапускает и не перечитывает php-fpm, nginx и Apache, не запускает их проверки конфигурации (`nginx -t` и `php-fpm -t` открывают логи) и не ставит, не обновляет и не удаляет пакеты — их скрипты делают то же самое, на EL это касается и `dnf install` при установке почты; пока не только root'а `php/` — то же для php-fpm и пакетов. На это агент отвечает 403: чужой каталог он заберёт при перезапуске, дерево логов пробует вычистить снова перед каждым таким действием. Что агент при старте не смог убрать из `php/`, он называет в своём журнале (убрать это нужно руками), но ничего из-за этого не запрещает: мастер php-fpm перед bind сам удаляет то, что лежит на пути сокета. Логи сайтов nginx, Apache и php-fpm пишут только прямо в каталог аккаунта в `sites/`: глубже мог бы остаться каталог, сделанный не root'ом, и confcheck такой путь не примет. Строк tmpfiles API не пишет: `/etc/tmpfiles.d` нет в allow-list записи. Файл вывода операции `tool` должен быть обычным файлом с одним именем, а системную учётку (uid ниже `UID_MIN`) агент аккаунтом панели не сделает. Общую папку ([10](10-shared-folders.md)) агент монтирует сам (`/v1/shares/bind`): поток, вошедший в пространство монтирования PID 1 (`setns`; у агента своё — `ProtectHome=`, `PrivateTmp=`), открывает папку от веб-корня без символьных ссылок — каталог владельца в его доме, не в `.restore`/`.shares`, не под чужой точкой монтирования, причём и владелец, и гость проходят проверку аккаунта панели, — и точку монтирования, каждый каталог до которой принадлежит root и закрыт от записи для остальных (с учётом маски ACL и записей, которые маска сдерживает), и монтирует открытый каталог на открытый (`open_tree` + `move_mount`); размонтирует тоже агент (`/v1/shares/unbind`). Клон каталога становится частным до `move_mount` (`mount_setattr`) и получает свою группу распространения: то, что гость смонтирует внутри папки, в дерево сайта не попадает. В пространство монтирования PID 1 входит никогда не главный поток процесса: его Go не завершает, а оставил бы там навсегда, и агент выглядел бы живущим в пространстве хоста. Mount-юнитов агент не пишет (`/v1/units/apply` их отклоняет), а mount-юниты ниже веб-корня не запускает, не перезапускает, не перечитывает и не включает (`/v1/service`, 403): systemd смонтировал бы их по пути, а владелец папки мог подменить её ссылкой. Свои монтирования агент записывает в `/var/lib/monopanel-agent/shares/`; пока запись (или mount-юнит ниже веб-корня) есть, ни одна операция агента (`dirs/ensure`, `chown`, `user/ensure`, `user/remove`, `acl/set`, `acl/site`, `paths/remove`, `symlink/ensure`, `file/ensure`, распаковка tar, восстановление на место) не отдаёт каталог на пути к точке монтирования аккаунту, не открывает его на запись, не удаляет и не подменяет — 409. `/v1/units/remove` юнита общей папки прежних версий держит блокировку общих папок, удаляет файл и делает daemon-reload до ответа (если reload не удался, файл возвращается): загруженный юнит systemd смонтировал бы и без файла. При старте агент забирает mount-юниты общих папок, которые писали прежние версии: сначала записывает каждую папку (юнит с заголовком панели — каким бы ни был теперь аккаунт гостя или владельца), затем снимает монтирование, которое показывает не тот каталог, что агент смонтировал, и не папку, какой её сейчас открыл бы и принял агент (каждая проверка — не дольше 10 с; опоздавшая ничего не снимает), и только потом отключает и удаляет юниты (`disable`, удаление файла и daemon-reload; если reload не удался, файл возвращается, а папка остаётся записанной); панель монтирует папки заново при каждом своём старте. Запись агента о папке снимает только размонтирование. API при старте получает записи (`/v1/shares/records`) раньше, чем читает базу, и размонтирует те, чью точку монтирования не называет ни одна общая папка базы (в доме гостя или в `.shares`); занятую — при следующем старте, а `mp doctor` её называет. Папку каждой записи API сверяет с папкой общей папки базы с той же точкой монтирования и монтирует папку базы, если запись называет другую. Размонтировать папку, о которой у агента есть запись или юнит в форме панели, можно без проверки аккаунта (только по виду пути): размонтирование лишь отнимает у гостя; монтирование по-прежнему требует аккаунта панели. Там, где у агента от папки нет ничего (не смонтировано, нет записи, нет юнита), API размонтирования не запрашивает: такой вызов ничего бы не изменил, а для гостя, которого агент не считает аккаунтом панели, был бы отклонён. Монтирование в точку, о которой у агента уже есть запись, если не удалось, возвращает запись как была — с папкой и каталогом, которые там смонтированы: список записей не врёт о том, что смонтировано. Каталог прямо под домом владельца на пути к папке, кроме `data`, должен лежать на монтировании самого дома (statx `STATX_MNT_ID` открытых дескрипторов): только там в доме бывает точка монтирования другой общей папки (на `data`, через который идёт путь к любой папке сайтов, её не бывает: имя `data` панель общей папке не даёт, а агент монтирует только на каталоги root), а обход до папки идёт до блокировки общих папок, и записи могут ещё или уже не знать о такой точке на пути — размонтирование без `MNT_DETACH` не снимет точку, которую держит дескриптор обхода (EBUSY), но монтирование другой папки в ту же точку снимает прежнюю с `MNT_DETACH`. Монтирования на `data` и глубже в доме (том или датасет администратора для файлов аккаунта или сайта, FUSE-монтирование владельца) этой проверке не мешают. Отказ агента в монтировании или размонтировании API передаёт клиенту с его статусом: 403 — папку или точку монтирования агент не принимает, 409 — папка занята, 503 — блокировку общих папок дольше 30 с держат распаковка, восстановление или другой обход дерева ниже веб-корня; 502 — только когда агент недоступен или операция не удалась.
- Порт панели: HTTPS-порт держит `monopanel-api.socket` (PID 1), а не процесс API, поэтому он не освобождается, пока API перезапускается (после изменения настроек, обновления, падения), остановлен или ещё не запущен на загрузке. Drop-in с адресом пишет только root из `web.listen` в `config.yaml`; типизированный `/v1/units/*` его не знает. Перезапуск без смены адреса перезапускает только `monopanel-api.service`. Со сменой адреса API сначала останавливает сокет, и перезапуск API поднимает его на новом адресе: пока служба работает, systemd сокет не запускает. По той же причине перезапуск самого `monopanel-api.socket` (страница «Службы», `mp service restart`) панель выполняет как остановку сокета и перезапуск `monopanel-api`.
- Агент не доверяет и самому API: процесс API, перехваченный через уязвимость, не должен получить root. Операции `tool`, `stream`, `pkg`, проверки конфигов и операции с учётками принимают только те формы аргументов, что строит панель — лишний ключ, чужой путь или учётка не из панели (uid ниже `UID_MIN`, дом вне веб-корня, привилегированная группа) дают отказ 403 с причиной. Архивы распаковывает сам агент, а не `tar` от root; снимки restic восстанавливаются рядом в `/var/lib/monopanel-agent/restore/` или на место только в веб-корень, конфигурацию панели, сертификаты, учётную запись ACME и дампы. Содержимое конфигов демонов, работающих от root (nginx — `fastcgi_pass` только на пулы сайтов панели, без `PHP_VALUE`/`PHP_ADMIN_VALUE`, первые байты запроса к сокету не выбирает клиент; Apache аккаунтов; php-fpm и `php.ini` — штатный пул `www` каждой ветки только как пустой пул панели, секция `[www]` — только в нём; MySQL, Postfix, Dovecot, OpenDKIM, logrotate, fail2ban, sshd; источники apt и dnf — только https; обёртка composer не запускается от root, в том числе когда `/usr/bin/id` не ответил), проверяется перед записью: директивы, которые загружают код, запускают программы или пишут файлы от root, отклоняются. `include` в nginx, php-fpm и dovecot проверяется так, как его раскрывает glob(3): шаблон только в имени файла, без `\` и фигурных скобок. Файлы Apache аккаунта агент пишет только для аккаунта хостинга и только в виде, где родитель слушает адрес этого аккаунта, а дочерние процессы работают от его имени: `User`, `Group`, `Listen`, pid-файл, блокировки и модули (по списку, без CGI, SSI, Lua, status и info) задаёт только `httpd.conf` аккаунта, он подключает только проверку секрета nginx (`backend.conf`, ровно в виде панели) и свои виртуальные хосты, они — только свои директивы, а те — ничего; журналы — только прямо в каталоге логов аккаунта. Ни один из этих файлов не выключает переписывание mod_rewrite, которым проверяется секрет, а location nginx, который проксирует на Apache аккаунта, агент принимает только вместе с секретом этого аккаунта ([03 §4](03-web-stack.md#4-шаблон-apache-режим-b)). Файлы в `/etc/systemd` общая запись не трогает: юниты панели пишут типизированные операции `units/apply|remove`, принимающие только её юниты и ключи. Юниты systemd агент запускает, останавливает и включает любые по имени, кроме экземпляров шаблонов (`modprobe@…`, `getty@…`), целей, слайсов, устройств и scope, оболочек (`debug-shell`, `emergency`, `rescue`, `console-getty`), юнитов питания (`systemd-halt`, `-poweroff`, `-reboot`, `-kexec`, `-soft-reboot`, `-exit`, `-suspend`, `-hibernate`, `-hybrid-sleep`, `-suspend-then-hibernate`), `systemd-sysext`/`systemd-confext`, прогонов systemd-tmpfiles по всем файлам (`systemd-tmpfiles-setup*.service`, `systemd-tmpfiles-clean.service` и `.timer`) и собственных запусков панели — самообновления (`monopanel-update.service`) и пакетного менеджера (`monopanel-pkg-*.service`), которые остановка или перезапуск оборвали бы на полпути, — у них только состояние; mount-юниты ниже веб-корня агент не запускает и не включает (выше). Экземпляры шаблона панели `monopanel-apache@<логин>` агент запускает и останавливает: имя выбирает только `/etc/apache2/monopanel/accounts/<логин>/httpd.conf`, без которого юнит не стартует, а его агент пишет лишь в описанном виде. `a2enmod`, `a2enconf` и `a2ensite` агент не запускает (только `a2dis*` — выключить включённое прежней версией в Apache дистрибутива), а учётку Apache дистрибутива (`www-data`) может только вывести из `monopanel-web`. Своё (историю конфигов, восстановленные снимки, пакет обновления и прежний бинарник) агент держит в `/var/lib/monopanel-agent` (0700 root), раскладку восстановлений на место в веб-корень — в `<www_root>/.restore` (0700 root), кеш и временный каталог restic — в `/var/cache/monopanel-agent`, а не в каталоге данных API, куда API мог бы подложить ссылку.
- Обновление пакетов агентом (`/v1/pkg` с `upgrade`) принимает только имена, только из набора панели (nginx, PHP, Apache, сервер БД; `osprofile.UpgradeComponent`) и только установленные: пакета, которого нет на хосте, по имени не поставит (новую зависимость обновлённого пакета apt и dnf всё же поставят), а apt ещё и ничего не удаляет (`apt-get --only-upgrade --no-remove`, `dnf upgrade`); пакеты, удержанные через `apt-mark hold`, оставляет как есть. Статус службы говорит, работает ли она на бинарнике, который заменило обновление.
- restic работает в песочнице Landlock (`monopanel sandbox-exec`): при бэкапе он читает только сохраняемые деревья — агент открыл их без следования по ссылкам и передал дескрипторами, — при восстановлении пишет только в каталог назначения — в `/var/lib/monopanel-agent/restore/` или в каталог раскладки восстановления на место (ниже); кроме того, ему доступны лишь свой кеш и временный каталог (`/var/cache/monopanel-agent/`), локальный репозиторий и общедоступные системные файлы (учётные базы, DNS, часовой пояс, сертификаты УЦ, библиотеки). Клиент, подменивший во время бэкапа свой каталог ссылкой на `/`, не заставит root сохранить как свои файлы `/etc/shadow`, ключи root или состояние агента, а при серверном бэкапе — и конфигурацию панели, сертификаты, дампы или файлы другого аккаунта: restic их не прочтёт, снимок будет создан, а запуск получит статус `partial` со списком пропущенного. Кроме того, бэкап читает все сохраняемые деревья — веб-корень, конфигурацию панели и каталог данных (сертификаты, учётная запись ACME, дампы запуска; представление ставится на сам каталог данных, потому что каталог, который API может переименовать, увёл бы представление с собой) — в собственном пространстве монтирования restic, где они перемонтированы с `nosymfollow` и закрыты для распространения: ни одна символическая ссылка ниже них не разрешается (Landlock пропускает дерево, каким бы путём к нему ни пришли, а серверный бэкап читает и конфигурацию панели, сертификаты, дампы и чужие домашние каталоги), а монтирование, появившееся во время бэкапа (общая папка), внутрь не попадает. Landlock для этого не нужен: на ядре без него бэкап идёт через `sandbox-exec --no-landlock` с одним этим представлением. Системные файлы `/etc` (учётные базы, DNS, часовой пояс, сертификаты УЦ, crypto-policies) restic видит в собственном `/etc` — tmpfs с копиями файлов и привязанными каталогами, — который Landlock пропускает целиком: правило на файл держится за его inode, и `resolv.conf`, `hosts` или `passwd`, заменённые переименованием (NetworkManager, dhclient, useradd), иначе пропали бы посреди бэкапа; `resolv.conf`, ведущий ссылкой в `/run` (systemd-resolved), остаётся ссылкой. Агент проверяет эти возможности при старте; где монтировать нельзя (профиль контейнера), остаются правила на отдельные файлы, а агент и `mp doctor` предупреждают. Локальный репозиторий должен быть отдельным каталогом restic: песочница даёт restic читать его целиком, поэтому каталог с посторонними файлами (например, `/var/backups` с копиями `/etc/shadow`) не принимается. К SFTP-репозиторию restic подключается через мастер-соединение ssh, которое агент открывает вне песочницы с ключами root (ControlMaster); ssh внутри песочницы не читает ни ключей, ни конфигурации. Из `/proc` restic доступен один файл — переключатель FIPS ядра `/proc/sys/crypto/fips_enabled`, только на чтение: Go от Red Hat, которым собран restic из EPEL, читает его при старте любой программы и завершает её, если прочитать не удалось, а libcrypto в EL (и у ssh) по нему решает, включать ли режим FIPS. Для режима FIPS в собственном `/etc` restic есть и `/etc/pki/tls/fips_local.cnf` — настройки FIPS-провайдера из crypto-policies; сторонние провайдеры из `/etc/pki/tls/openssl.d` в песочницу не попадают. Дескриптор правила на файл procfs restic наследует: procfs заводит новый inode, когда ищет имя заново, а правило Landlock держится за прежний. При старте агент в фоне, не задерживая свой старт, запускает установленный restic (`restic version`) в той же песочнице, что и бэкап, и повторяет это при запросе состояния (`mp doctor`, дашборд), если бинарник restic сменился (панель ставит restic с первым бэкапом, пакетный менеджер его обновляет) или неудаче больше 10 минут; ответ агента на такой запрос ждёт проверку не дольше 2 с. Если restic в песочнице не запускается, бэкапы падают с той же ошибкой — её и что делать называют строка «restic sandbox» в `mp doctor` (это сбой: `mp doctor` завершается с кодом 3) и журнал агента. Вне песочницы агент restic не запускает и тогда. Если `restic version` не уложился в 30 секунд, это предупреждение, а не сбой: хост мог быть просто перегружен; агент повторит проверку при первом запросе состояния через 10 минут, а если тайм-аут повторяется, бэкапы будут зависать так же — строка и журнал агента говорят, на что смотреть. Без Landlock (ядро ниже 5.13 или `lsm=` без landlock) restic работает без песочницы, кроме представления без ссылок для бэкапа; агент предупреждает при старте, а строка «restic sandbox» в `mp doctor` подсказывает, как включить Landlock, если он собран в ядро (`grubby --update-kernel=ALL --args=lsm=<текущий список>,landlock` на EL, `lsm=` в `GRUB_CMDLINE_LINUX` и `update-grub` на Debian/Ubuntu, на Oracle Linux с UEK — или ядро RHCK). На Landlock ABI 1 (ядро 5.15 в Ubuntu 22.04) восстановление идёт без песочницы: в этой версии нельзя создать жёсткую ссылку в другом каталоге. Восстановление на место раскладывает снимок в каталоге агента на той же файловой системе, куда он вернётся: содержимое веб-корня — в `<www_root>/.restore/.in-place-*` (root, 0700, рядом с `.shares`), остальное — в `/var/lib/monopanel-agent/restore/`. До запуска restic агент сверяет объём выбранного по листингу снимка со свободным местом и inode (`statfs`) и при нехватке отказывает, а при старте удаляет то, что оставило прерванное восстановление. Части одного восстановления на место, лежащие на одной файловой системе (на хосте с одной ФС — `.restore` и `restore/`), проверяются вместе. Восстановление в сторону проверяется так же — в `/var/lib/monopanel-agent/restore` на его файловой системе, после удаления прежнего восстановления с тем же именем; включения-шаблоны (`*`, `?`, `[`) отдают выбор restic, и тогда проверки нет. Каталог раскладки ничего не наследует: ACL по умолчанию, который администратор поставил на `.restore` или `restore/` (например `setfacl -R -d` по веб-корню), в восстановленные домашние каталоги не попадает. Каталог `.restore` принадлежит агенту: вызовы API (каталоги, файлы, ссылки, ACL, chown, удаление, tar, du, бэкап отдельного пути) к нему не допускаются, серверный бэкап его исключает, слияние снимка ничего в него не переносит. Восстановлению песочница не даёт создавать файлы устройств, FIFO и сокеты; агент отклоняет снимок, в выбранных путях которого есть такой узел или файл с setuid/setgid (по `restic ls --json`), ещё до записи (каталог с setgid проходит), а восстановление на место держит блокировку общих папок от запуска `restic restore` до конца переноса: монтирование и размонтирование общей папки ждут её до 30 с, потом получают 503.
- Клиенты: отдельный unix-пользователь и группа, домашний каталог `0710`, доступ nginx через ACL для группы `monopanel-web`; пулы FPM от имени клиента; `open_basedir`, отдельные `tmp`/`session`; `disable_functions` по умолчанию; защита от symlink (`disable_symlinks if_not_owner` в nginx; Apache аккаунта работает от его имени, и ссылка на чужой файл ему ничего не даёт); сайты в режиме apache обслуживает Apache своего аккаунта (`monopanel-apache@<логин>`) — родитель от root слушает адрес только этого аккаунта на порту 81, так что и пока Apache перезапускается, чужой процесс не примет запросы его сайтов, а `.htaccess` сайта не дотянется ни до чужого пула, ни до чужих файлов, ни до страницы состояния сервера. Apache аккаунта отвечает только на запросы nginx с секретом аккаунта (`X-MonoPanel-Backend`, файлы root 0600, проверка агентом): прямое подключение другого аккаунта к `127.100.x.y:81` получает 403 и не обходит `--allow`, лимит запросов и адрес клиента. Опционально — cgroup-лимиты через изолированные пулы (см. [03-web-stack.md](03-web-stack.md) §6). Имя базы `<логин>_<имя>`, которое панель уже записала за базой или аккаунтом MySQL другого аккаунта (в логинах бывает `_`), не принимается. Сайт или почтовый домен обычный аккаунт не заведёт ни на имени самой панели или её почтового сервера (cookie сессии не привязана к порту, и такой сайт получал бы сессию администраторов), ни на имени, которое есть или лежит под сайтом или почтовым доменом другого аккаунта (почту своих доменов этот сервер доставляет себе сам); администратор ставит имена куда угодно.
- Сгенерированные файлы: значение, которое панель пишет в файл построчно, не может начать свою строку. Задание cron — одна строка без управляющих символов, с расписанием, которое понимают оба cron; значения юнита app-сервиса — без переводов строки и других управляющих символов и без `\` в конце, которой systemd продолжает строку; имена в картах postfix, passwd-файле dovecot и таблицах opendkim — без пробелов, управляющих символов, `:`, `/` и `,`, домен — по правилам DNS. Почтовые карты проверяются при каждой записи, так что и значение, попавшее в базу в обход API, останавливает применение, а не дописывает строку ([06](06-mail.md)). Переменные app-сервисов лежат в `EnvironmentFile` с правами root 0600 (`/etc/monopanel/apps/`), а не в `Environment=` юнита, который виден любому локальному пользователю; собственный env-файл аккаунта читает от его имени служебная команда `mp app-exec`, а не systemd от root, — символьная ссылка оттуда не откроет чужой файл.
- Вывод в терминал: имена, комментарии, сообщения и журналы задач, строки логов и записи журнала действий приходят от клиентов, от незнакомцев у формы входа и от источников переезда, поэтому `mp` и TUI печатают их без управляющих символов и последовательностей терминала (`internal/termsafe`): такая строка не сдвинет курсор, не подделает вывод, не сменит заголовок окна и не запишет в буфер обмена администратора.
- Переезд: посылка источника — ввод, а не конфигурация. Каждое её значение приёмник проверяет по тем же правилам, что API применяет к тому же значению, набранному человеком; нарушившее правило разбор показывает конфликтом, а задача такую запись не берёт и завершается ошибкой. `CREATE USER` источника не выполняется как есть, а собирается заново из плагина и хеша; дамп грузится от имени аккаунта самой базы, без команд клиента `mysql` и `LOAD DATA LOCAL`; из потока tar остаются только файлы, каталоги и ссылки внутри дерева, без setuid и файлов устройств; свои директивы nginx сайтов не применяются, а сохраняются для проверки. Подробно — в [07](07-migration.md#5-что-уже-работает).
- SSH/SFTP: клиент получает shell только по флагу; SFTP-only через `Match Group monopanel-sftp` + `ChrootDirectory`.
- Обновления панели — только релизы с подписью ed25519 (§9); компоненты стека — только из официальных репозиториев их разработчиков.
- SELinux на EL остаётся в enforcing (см. [02-platform-matrix.md](02-platform-matrix.md) §6).
- Секреты в БД зашифрованы, ключ вне БД. Пароли и токены не попадают в командные строки, которые видит любой локальный пользователь (`ps`): установщики CMS получают пароли на stdin, `install.sh` передаёт токен приватного репозитория `curl` конфигом на stdin, консоль Web UI и TUI дают дочернему `mp` адрес панели и токен через окружение (`MP_SERVER`, `MP_TOKEN`), а введённые пароли — на stdin через флаги `--…-stdin`. Параметры задач API отдаёт без секретов — пароли, ключи и токены в них заменены на `[redacted]` (пароли и ключи и в самой базе лежат зашифрованными), — и так же без них задача уходит в webhooks; журнал действий и эхо консоли скрывают значения секретных флагов.

## 8. Наблюдаемость

- Логи панели: `slog` → journald (`monopanel-api`, `monopanel-agent`), `mp logs <unit>`. Журнал действий (кто, что, откуда: входы удачные и нет, токены, изменения, отказы сокету) — таблица `audit_log` в базе панели, её показывают `mp audit`, `GET /system/audit` и страница «Журнал» (администратор видит всё, аккаунт — только своё); та же лента пишется строками JSON в `/var/log/monopanel/audit.log` (`log.audit_file`, ротация logrotate), а входы и отказы попадают и в journald. Лог каждой задачи хранится вместе с задачей (`mp job show <id>`, страница «Задачи»).
- Метрики: сэмплер раз в 10 с читает `/proc` (CPU, load, память, диск, сеть) и складывает точки по минутам на 30 дней — `mp metrics` и графики на дашборде. Разбор access-логов nginx по сайтам (запросы, трафик, время ответа) и endpoint `/metrics` для Prometheus — планируются.
- Логи сайтов: `/var/log/monopanel/sites/<user>/<domain>.{access,error}.log`, `<domain>.php.error.log`, `<domain>.php.slow.log`, у сайтов в режиме apache — `<domain>.apache.{access,error}.log` и `apache.error.log` самого Apache аккаунта; `mp site logs`, вкладка «Логи» сайта. Каталог `root:<user>` 0751, вне домашнего каталога: логи открывают от root nginx, Apache и php-fpm, и в каталоге клиента их можно было подменить ссылкой. Клиент читает их через свою группу. Трассировки в slow-логе php-fpm на EL разрешает модуль политики панели ([02](02-platform-matrix.md#6-selinux-el9--el10)).
- Ротация логов сайтов — `/etc/logrotate.d/monopanel-sites`: по два блока на аккаунт, от root, раз в неделю или раньше, если лог перевалил за 100 МБ, восемь копий, сжатые начиная со второй. Логи серверов — `root:<логин>` 0640, журнал ошибок PHP — аккаунта с правами 0660: панель создаёт их до того, как их откроют nginx, Apache и php-fpm; nginx и Apache аккаунта переоткрывают логи по USR1 через свои pid-файлы (`/run/nginx.pid`, `/run/monopanel-apache/<логин>/httpd.pid`). Файл logrotate панель переписывает при появлении и удалении аккаунта и при старте, а перед записью проверяет его `logrotate --debug`. Подробности — в [03](03-web-stack.md#2-файловая-структура-на-сервере).
- Уведомления: webhooks с подписью HMAC-SHA256 на завершение задач — `job.done`, `job.failed` и `<тип задачи>.done|failed` (`site.apply`, `cert.issue`, `backup.run`…). Почта и Telegram — планируются.
- Диагностика: `mp doctor` и блок на дашборде — сервисы (и Apache каждого аккаунта с `apache2 -t` его конфигурации), синтаксис конфигов, диск, память, сертификаты, DNS имени панели, упавшие задачи (упавшая считается исправленной, если позже прошла та же работа — тот же тип задачи и ключ блокировки, у задач стека и тот же компонент; переезд сайтов на Apache аккаунтов (`apache.migrate`, `apache.backend`) исправляет и прошедший `mp stack install apache`; не считается и упавшая задача, чей объект удаление убрало уже после неё: сайт или аккаунт её ключа блокировки, а у `mail.webmail` — сайт вебпочты и, пока сайта с таким именем нет, аккаунт, для которого её просили, — прошёл `site.delete` или `user.delete`, который уносит и сайты аккаунта, поставленный в очередь после задачи или, если шёл рядом с ней под другим ключом блокировки, закончившийся после её старта (`user.delete`, поставленный прежней версией панели, сайтов аккаунта не знает, и их неудачи считаются, пока не пройдут сутки); `site.apply`, который дошёл до уже удалённого сайта, завершается успешно — «the site is gone: nothing to apply»; упавший бэкап считается, пока не пройдёт следующий бэкап в ту же цель; сутки считаются от падения), неудачная или откатившаяся установка обновления панели («update attempt»), отказы SELinux для веб-сервера, дрейф сгенерированных файлов, песочница restic и запускается ли в ней установленный restic («restic sandbox»), общие папки, которые не смонтированы или где смонтирован не тот каталог, и почему, и папки, которые агент держит, а ни одна общая папка базы не называет («shared folders»), общий `apache2.service` прежних версий, если он работает (с состоянием переезда сайтов на Apache аккаунтов) или выключен, но включён в автозагрузку («service apache2.service»), сайты, которые он ещё обслуживает, пока переезд не закончен («apache move»), Apache аккаунта, ещё не требующий секрета nginx («backend monopanel-apache@<логин>.service»), порт Apache аккаунтов, доступный аккаунтам («apache port»); сайты, которые ещё пишут логи в `data/logs`, и почему — задание в очереди, неудачи с ошибкой и временем следующей попытки, ожидание правила SELinux («site logs»); штатный пул ветки, ещё не пустой или изменённый администратором («php X.Y pool www»); пулы с включённым `catch_workers_output` («php-fpm pools»); ждущие обновления пакетов стека («update <строка>», например «update php-8.4», сводка «updates», удержанные через apt-mark — «held <строка>», неудачное последнее обновление — «stack upgrade») и службы на бинарнике, который заменило обновление («service <юнит>»); модули ядра sctp, dccp, rds и tipc («kernel modules»; в контейнере — предупреждение, что модули грузит ядро хоста, [02](02-platform-matrix.md)). У части находок есть кнопка «починить» или ссылка «к обновлению». Пока переезд сайтов на Apache аккаунтов не закончен, Apache аккаунта, ни один сайт которого ещё не переехал, не проверяется (у него ещё нет `httpd.conf`), а остановленный в это время общий Apache — провал (`systemctl start apache2.service`), а не совет его выключить. Строку «api socket» считает сам API на своём хосте: предупреждение, если API слушает порт сам, хотя сокет мог бы его держать, — включён сокет или нет (юнит API запускает его вместе с собой, `Wants=`); предупреждение и тогда, когда API работает на порту, который передал сокет, а сокет с тех пор остановлен (так его оставляют «Остановить» на странице «Службы» и `systemctl restart monopanel-api.socket` вручную при работающем API): как только API остановится или упадёт, порт никто не держит. ok — пока порт держит сокет, для порта ниже `net.ipv4.ip_unprivileged_port_start` и когда сокет замаскирован или его нет (со следующего старта API слушает порт сам); замаскированный сокет (`systemctl mask monopanel-api.socket`; на установке без пакета сначала удаляют копию его юнита в `/etc/systemd/system`, которую пишет `mp setup`) — способ намеренно оставить порт самому API, и `mp setup` оставляет его замаскированным. Строка входит в итог и в `--json`, видна на дашборде и в TUI, и с `mp --server` её судит нужный хост; `mp doctor` считает её сам только для API, который её не даёт.

## 9. Упаковка, установка, обновление

- Сборка: `make packages VERSION=…` → бинарники amd64/arm64 → `nfpm` → `monopanel_<ver>_<arch>.deb`, `monopanel-<ver>.<arch>.rpm`, голые бинарники и `SHA256SUMS`. В пакете: бинарник, unit-файлы `monopanel-api.service`, `monopanel-api.socket`, `monopanel-agent.service` и шаблон `monopanel-apache@.service`, sysusers/tmpfiles, `/usr/lib/modprobe.d/monopanel.conf` (модули ядра sctp, dccp, rds и tipc не загружаются; установке без пакета `mp setup` пишет `/etc/modprobe.d/monopanel.conf`), `/etc/monopanel/config.yaml`; шаблоны конфигов вшиты в бинарник. postinstall сначала удаляет копии юнитов пакета, которые панель оставила в `/etc/systemd/system` (`monopanel prune-unit-copies`: копия уходит, только если её текст — текст какой-то версии `mp setup` или пакета для `/usr/bin/monopanel` и она не новее юнита пакета; симлинки включения переводятся на юнит пакета; свой юнит администратора, маска и копия для другого бинарника остаются). Свежая установка включает агента, сокет и API; так же — установка после удаления пакета: preremove при удалении оставляет отметку `/var/lib/monopanel-agent/package-removed` (каталог только root), потому что dpkg передаёт такой установке удалённую версию, как обновлению. Обновление включённое и выключенное не трогает, кроме сокета в первый раз (пока нет его drop-in `listen.conf`): он включается, только если включён API. Затем адрес сокета приводится к `web.listen` (`monopanel api-socket-sync`). При обновлении перезапускается только то, что работало: слушающий сокет держит порт, пока перезапускаются агент и API; работающий API, который держит порт сам (0.8.19 и ниже) или чей сокет сдвинулся, перезапускается вместе с сокетом одним вызовом `systemctl restart` — systemd запускает сокет между выходом старого API и стартом нового; остановленный API остаётся остановленным, а сокет, который не слушал, не запускается (`try-restart`). preremove при понижении до версии ниже 0.9.0 (dpkg: `upgrade <версия>` и `dpkg --compare-versions … lt 0.9.0~` — сборки разработки 0.9.0 (`0.8.19~<n>-g<коммит>`) dpkg считает более старыми; rpm: `$1` ≥ 1 и бинарник новой версии не отвечает на `api-socket-sync --probe` — сборка разработки, сделанная после появления этой команды, тут сходит за 0.9.0) транзакцию не прерывает: копирует шаблон `monopanel-apache@.service` в `/etc/systemd/system`, если у аккаунтов есть Apache, и печатает, что сломается и что делать ([README, «Откат на старую версию»](../README.md#откат-на-старую-версию)). `mp setup` пишет в `/etc/systemd/system` только юниты, которых нет в пакете (установка без пакета; с `--binary` другого бинарника — юниты агента и API), и свои копии удаляет так же. Копию `/etc/tmpfiles.d/monopanel.conf`, которую оставил `mp setup` до 0.8.19 (при загрузке она заменяет файл пакета), postinstall дополняет: строка `/run/monopanel` получает sticky-бит (1771), а для `php/` в `run_dir` дописывается `d <run_dir>/php 0755 root root -`; `/etc/tmpfiles.d/monopanel-php.conf`, который писал API, остаётся (он нужен версии ниже 0.9.0 после её `mp setup`; одна и та же строка в двух файлах tmpfiles — не предупреждение); если в нём больше этой строки — предупреждение: проверьте, что файл создаёт от root при загрузке, и оставьте в нём строку панели. На установке без пакета этот файл, если его нет, пишет `mp setup`. `monopanel prune-unit-copies` удаляет и `/etc/modprobe.d/monopanel.conf` от `mp setup`, когда есть `/usr/lib/modprobe.d/monopanel.conf`, а копия — выпущенный текст правила не новее пакетного (изменённый файл остаётся, с предупреждением). При откате ниже 0.9.0 и при удалении с сервера, где запускался `mp setup`, preremove пишет `d <run_dir>/php 0755 root root -` в `monopanel-php.conf`, если его нет (а если не может — говорит, куда положить строку), и сохраняет шаблон Apache; при удалении называет app-сервисы с env-файлом, которые остановятся. Почтовую политику ([§3.7](#37-почтовая-политика)) preremove при удалении убирает из `main.cf` и перезагружает postfix до того, как остановит её юниты, а postremove (`postrm` dpkg, `%postun` rpm) делает то же, когда оставшийся бинарник её не знает (откат ниже 0.9.0): иначе postfix, которому велено ждать политику (`default_action=tempfail`), держал бы всю почту.
- Релиз: тег `v<ver>` → CI собирает пакеты, подписывает `SHA256SUMS` ключом ed25519 (`SHA256SUMS.sig`) и публикует релиз на GitHub; текст аннотированного тега становится описанием. Своего apt/yum-репозитория нет — планируется; пакеты берутся из релизов.
- Установка: `curl -fsSL https://monopanel.app/install.sh | sh` (адрес ведёт на `packaging/install.sh`): скрипт определяет ОС и архитектуру, берёт тег последнего релиза из редиректа `/releases/latest` (без GitHub API и его лимита), скачивает пакет, сверяет контрольную сумму и ставит его. Затем `mp setup`: служебный пользователь, каталоги, база, самоподписанный сертификат, администратор; адрес панели и пароль печатаются в конце, параметры задаются флагами (`--hostname`, `--listen`, `--admin-password`…). Стек — nginx, PHP, СУБД и остальное — ставится потом из официальных репозиториев: `mp stack install`, `mp php install` или из Web UI. TUI-мастер установки — планируется.
- Обновление панели: `mp update apply` или кнопка в «Настройках» (задача `panel.update`): поиск релиза, проверка подписи ed25519 списка контрольных сумм (ключ вшит в панель; `update.public_key` в `config.yaml` подменяет его для форка или выключает проверку значением `none`), загрузка пакета, установка агентом в transient-юните `monopanel-update.service` — он переживает перезапуск api и агента и возвращает прежний бинарник, если новая версия не отвечает; миграции базы применяются при старте. Агент запускает этот юнит, только когда не идёт ни один запуск пакетного менеджера (`monopanel-pkg-*`), а запуски, пришедшие во время установки, ждут её конца: свой `apt-get`/`dnf install` пакета панели не упирается в блокировку dpkg (apt ждёт её 10 минут и сдаётся). Менеджер пакетов работает с тем же окружением, что у запусков агента (`NEEDRESTART_MODE=l` на Ubuntu). Версию, которая уже числится в базе пакетов, он ставит заново (`apt-get install --reinstall`, `dnf reinstall`): после отката, который возвращает только бинарник, обычная установка ничего бы не изменила. Автоматическое обновление пропускает версию, чья последняя установка откатилась (следующий релиз ставит как обычно); `GET /system/update` помечает такую попытку `reinstall`. Агент копирует пакет из загрузок API в свой каталог `/var/lib/monopanel-agent/updates` (только root), не следуя символьным ссылкам, и проверяет подпись и сумму уже копии: имя, которое ставит `mp update-run`, получает только копия, чей SHA-256 совпал с тем, что подписанный список сумм даёт файлу пакета этого релиза, а запрос, который не совпал, ничего уже подготовленного не меняет. Версию ниже установленной агент не ставит — и релиз, из которого собрана более поздняя сборка (`git describe`, например `0.8.19-5-gabc1234`), тоже; отказ называет, что сломает откат (ниже 0.9.0 — сайты в режиме apache, app-сервисы с env-файлом и логи сайтов), и ссылается на [«Откат на старую версию»](../README.md#откат-на-старую-версию) в README. Drop-in `/etc/systemd/system/monopanel-api.service.d/socket.conf` перед каждым стартом API спрашивает бинарник: `monopanel api-socket-sync --probe`. Версии 0.8.19 и ниже этой команды не знают и сокет не берут. Поэтому после отката самообновления (он возвращает только бинарник) или после даунгрейда пакета drop-in останавливает `monopanel-api.socket`, и старый API слушает порт сам, вместо того чтобы падать на EADDRINUSE при каждом старте; с портом делать ничего не нужно (остальное после даунгрейда пакета — README, «Откат на старую версию»), но, пока работает старая версия, порт снова свободен, пока API перезапускается. Следующее обновление до 0.9.0 и новее возвращает сокет само. После даунгрейда пакета drop-in можно удалить: `rm /etc/systemd/system/monopanel-api.service.d/socket.conf && systemctl daemon-reload`. Проверка идёт по расписанию (раз в сутки), `--auto-apply` ставит найденное само.
- Переезды обновления хранят результат, а не очередь: `sites.moves` (сайты, ещё не переехавшие на дерево логов и Apache аккаунтов, с попытками), `stack.apache.migrate` (переезд на Apache аккаунтов), `php.distro_idle.<X.Y>` (пул `www` ветки уже сделан пустым); переезд PHP на Ubuntu с `ppa:ondrej/php` на Sury узнаётся по самому файлу PPA (`ondrej-php.list` есть — переезд не сделан), а `php.repo.switch` хранит для `mp doctor` причину последней неудачи. Неудавшийся переезд (`sites.moves`, `stack.apache.migrate`) снова ставится в очередь при старте или раз в час, когда подошёл срок: через 10 минут после первой неудачи, затем вчетверо дольше после каждой следующей, но не реже раза в сутки; пул `www`, ещё не сделанный пустым, панель пробует при каждом старте.
- Пакеты вендоров, которые ставит панель (nginx с nginx.org, PHP из Sury или Remi, Apache из дистрибутива, Percona/MySQL), обновляет `mp stack upgrade` (задача `stack.upgrade`), а nginx, PHP и Apache — ещё и ежедневный запуск самой панели (по умолчанию включён, 04:00 по времени сервера; `mp stack auto-upgrade`). Обновляются только установленные пакеты из набора панели (`apt-get --only-upgrade --no-remove` с сохранением конфигов или `dnf upgrade`), удержанные через apt-mark остаются как есть. Перед обновлением конфигурация nginx, PHP и сервера БД проверяется ещё работающей версией (`nginx -t`, `php-fpm -t`, `mysqld --validate-config`; Apache аккаунтов пакеты Apache не перезапускают, и каждый проверяется перед своим перезапуском): пакеты сами перезапускают свои службы (двоичное обновление nginx.org, которое на Debian убивает старый мастер, если новый не поднялся; php-fpm в Debian; сервер БД), и на конфигурации, которая не проходит проверку уже сейчас, этот перезапуск уронил бы службу. Такой компонент или ветка PHP не обновляется, задача завершается ошибкой и называет причину. После обновления — проверка новой версией и reload nginx (restart, если он ещё работает на заменённом бинарнике), restart php-fpm каждой обновлённой ветки, мягкий перезапуск Apache каждого аккаунта (полный, если работает заменённый бинарник); не прошедшая проверку служба не перезагружается и работает как работала — если только перезапуск её же пакета во время обновления уже не уронил её: тогда она остаётся остановленной, и задача это называет; ничего не откатывается. Двоичное обновление nginx (новый мастер записал PID-файл, старый дорабатывает свои запросы) считается уже выполненным: nginx при этом не перезапускается. Агент запускает apt с `NEEDRESTART_MODE=l`: needrestart в Ubuntu только перечисляет службы на старом коде, ничего не перезапуская сам (в том числе сервер БД). Сервер БД — только по имени (`mp stack upgrade db`), мажорные версии не автоматизированы. unattended-upgrades не трогается: API никогда не пишет в `/etc/apt/apt.conf.d`. Обновление стека и обновление панели не выполняются одновременно (§5): пришедшее вторым ждёт в очереди. Если агент перезапустится посреди обновления, apt/dnf доводят транзакцию до конца в `monopanel-pkg-<run>.service`; задача, которую оборвал перезапуск панели (`Requires=` перезапускает API вместе с агентом), выполняется снова после него и ждёт этот запуск, а если агент пропал, а API остался, задача завершается ошибкой с именем юнита. Итог запуска показывает `journalctl -u monopanel-pkg-<run>.service`, конец вывода — журнал агента, весь вывод — `/var/log/apt/term.log` или `/var/log/dnf.log`. Пока переезд сайтов на Apache аккаунтов не закончен, общий `apache2.service`, который ещё обслуживает непереехавшие сайты, обновление Apache сначала проверяет (`apache2ctl -t`) — при ошибке Apache не обновляется: его пакет перезапустил бы общий Apache на этой конфигурации, — а после обновления, после той же проверки, мягко перезапускает (полностью, если тот работает на заменённом бинарнике или пакет его уронил). Если проверка прошла, а перезапуск не удался, задача так и пишет: «<юнит> was restarted but did not come up (<состояние>): journalctl -u <юнит>». В записи последнего обновления (`mp stack auto-upgrade`, «Настройки», TUI, строка «stack upgrade» в `mp doctor`) остаётся одна строка ошибки, около 300 символов, — её начало (что упало) и конец, где apt-get или dnf называют причину; целиком ошибка — в `mp job show <id>`. Ежедневное обновление запускается раз в сутки: если час перенесли на более поздний уже после сегодняшнего запуска, следующий — завтра.

## 11. Тестирование

- Unit (`make test`, пара секунд): логика панели проверяется через фейковый агент (`internal/agent/agenttest`) без root и systemd — тест видит сгенерированные файлы и все вызовы агента; шаблоны — golden-файлами (`go test ./internal/render -update` обновляет их); валидаторы ввода, очередь задач, OS Profile. Отдельные тесты держат границы из §7: область переезда у обычного аккаунта, сессии после смены пароля, секреты в параметрах задач, почтовые карты против подложенных строк, пароли установщиков CMS вне командной строки, запись и чтение агента под `/var/www` мимо символьных ссылок, общие операции агента мимо `config.yaml` и `secret.key`, общие папки: точки монтирования и монтирование из дескрипторов в пространстве монтирования хоста, проверенное в пространствах имён пользователя (`sharemount_test.go`, `sharebind_test.go`, `sharebind_ns_test.go`), узлы снимков при восстановлении (`restore_nodes_test.go`), запуски пакетного менеджера в своих юнитах (`pkg_unit_test.go`), повтор юнита после отказа по лимиту запусков (`startlimit_test.go`), сокет порта панели (`apisocket_test.go`, `listener_test.go`), Apache аккаунтов и секрет nginx для них (`apache_test.go`, `apache_backend_test.go`, `confcheck`), пустые пулы php-fpm (`php_pools_test.go`), каталоги, где root действует по имени (`roottrees_test.go`), песочница restic и раскладка восстановлений (`restic_sandbox_test.go`, `restore_staging_test.go`, `internal/sandbox`), обновление пакетов агентом (`pkg_upgrade_test.go`), переезды обновления (`moves_test.go`), скрипты пакета (`internal/setup/scripts_test.go`), посылки переезда с подложенными значениями от MonoPanel, FASTPANEL и BitrixVM (`migrate_security_test.go`). `make check` добавляет `gofmt`, `go vet` и `golangci-lint`.
- Паритет клиентов (`go test ./internal/parity/`, входит в `make test` и CI): тест поднимает API за фейковым агентом и через манифест (`internal/parity/manifest_*.go` — у каждой операции её команды `mp`, места в Web UI и поля) сверяет четыре стороны: операции и поля запросов API из его описания OpenAPI, дерево команд `mp`, меню и формы TUI для администратора и для обычного аккаунта и исходники Web UI (`web/src`: какие пути и поля шлют страницы, спрятаны ли действия администратора от обычного аккаунта, нет ли вызовов путей, которых у API нет). Он падает, если операция или поле недоступны в каком-то клиенте, кроме намеренных исключений (`exempt.go` и списки в `parity_test.go`), и говорит, что и где исправить.
- Консоль Web UI проверяется по настоящему дереву команд `mp` (`internal/api/console_cobra_test.go`): команду она находит так же, как cobra, — с любыми флагами перед ней; команды и флаги, которые она отклоняет или считает собственными флагами команды, в `mp` есть; каждый секретный флаг, у которого в `mp` есть двойник `--…-stdin`, она переносит на stdin.
- Регресс шаблонов: `scripts/check-templates.sh` скармливает сгенерированные конфиги настоящим `nginx -t` и `apache2 -t` (вся конфигурация Apache аккаунта с виртуальным хостом; в CI — на каждый push).
- E2E (`make e2e HOST=<ssh-алиас>`): на живой панели — пользователь → сайт с пресетом → база → nginx и PHP отвечают → удаление; `mp doctor` без ошибок.
- Матрица ОС — на площадке Proxmox ([08-testbed.md](08-testbed.md)), а не в CI: одиннадцать VM (Debian 12/13, Ubuntu 22.04/24.04/26.04, AlmaLinux 9/10, Rocky Linux 9/10, Oracle Linux 9/10) с откатом к чистому снимку. Перед релизом — `make testbed-full`: матрица, переносы между панелями, CMS на каждой машине, переезд с BitrixVM и FASTPANEL, doctor везде.
- Планируются: HTTPS через Pebble (тестовый ACME), бэкап → восстановление → suspend → purge в сценарии e2e, e2e Web UI на Playwright.
