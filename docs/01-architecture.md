# 01. Архитектура MonoPanel

Состояние на октябрь 2026 (MonoPanel 0.8.19). Версии компонентов указаны на этот момент; перед релизом их проверяет прогон матрицы ОС на [площадке](08-testbed.md).

> Это проектный документ: он описывает решения и их обоснование, в том числе те части, до которых реализация ещё не дошла. Что действительно работает — в [README](../README.md) и в отметках [x] в [05-roadmap.md](05-roadmap.md). Ниже такие места помечены как «планируется».

## 1. Цели и границы

**Что делаем**

- Панель управления веб-хостингом на одном сервере (класс FASTPANEL / ISPmanager Lite).
- ОС: Debian 12/13, Ubuntu 22.04/24.04/26.04 LTS; RHEL 9/10 и клоны (AlmaLinux, Rocky Linux, Oracle Linux).
- Режимы сайта: `nginx → php-fpm` и `nginx → Apache → php-fpm`.
- PHP 5.6 … 8.5 одновременно, версия выбирается на сайт; расширения по версиям.
- СУБД: MySQL 8.4 LTS **или** Percona Server for MySQL 8.4 LTS (выбор при установке, единый провайдер в коде).
- Интерфейсы: Web UI, CLI (скриптуемый, `--json`), TUI-меню (интерактивное, по SSH), REST API (OpenAPI 3.1).
- TLS (ACME), бэкапы, cron, firewall, защита от перебора, метрики, логи, файловый менеджер.

**Чего не будет в 1.0** (см. [дорожную карту](05-roadmap.md)): DNS-сервера, управления несколькими серверами, контейнерных приложений, WAF, роли реселлера. Почта (postfix + dovecot + opendkim + Roundcube) в первоначальный план не входила, появилась позже и описана отдельно — [06-mail.md](06-mail.md).

## 2. Архитектурные решения (ADR, кратко)

| # | Решение | Почему |
|---|---|---|
| A1 | Ядро панели — один статический бинарник на **Go** | На хосте не нужен рантайм (два семейства ОС, одиннадцать релизов); один файл — и демон, и CLI, и TUI; простая упаковка в .deb/.rpm, быстрый старт CLI, встроенные HTTP-сервер и TLS |
| A2 | **Разделение привилегий**: `monopaneld api` (пользователь `monopanel`) ↔ `monopaneld agent` (root) через unix-сокет | Код, который разбирает чужой ввод и отдаёт веб-интерфейс, не работает от root. Агент принимает только типизированные команды с allow-list путей и операций |
| A3 | **Один API для всех клиентов**: Web UI, CLI, TUI и внешние интеграции ходят в один REST API | Нет расхождений в логике; всё, что можно в Web, можно в CLI и TUI и наоборот — это проверяет тест `internal/parity` (§11) |
| A4 | **Декларативное состояние → рендер → валидация → атомарное применение → reload, с откатом** | Панель — источник истины; ручные правки живут в include-каталогах; сломанный конфиг никогда не доходит до reload |
| A5 | Панель слушает **собственный** HTTPS-порт (8443) на Go `net/http` | Панель доступна, даже если системный nginx сломан или ещё не установлен |
| A6 | Состояние панели — **SQLite** (WAL) | Панель обязана работать, когда MySQL не установлен или упал; бэкап состояния — один файл |
| A7 | PHP: **один php-fpm master на версию, пул на сайт**; Apache — только через `mod_proxy_fcgi` | Одна FPM-инфраструктура для обоих режимов; переключение режима = смена шаблона nginx/Apache. `mod_php` не поддерживается принципиально (одна версия на процесс Apache, работа от `www-data`) |
| A8 | PHP-сборки: этап 1 — репозитории Sury (deb) / Remi (rpm); этап 2 — **собственные сборки** с единой раскладкой `/opt/monopanel/php/<X.Y>` | Быстрый старт без сборочной фермы; затем независимость от сторонних репозиториев (каждый держит один человек) и одинаковые пути на всех ОС |
| A9 | nginx — из **nginx.org** (stable) на всех ОС; Apache — из дистрибутива | Одинаковая раскладка nginx (`conf.d`, пользователь `nginx`) и свежие версии с HTTP/3 на всех ОС; Apache в дистрибутивах достаточно свежий и хорошо уживается с SELinux и AppArmor |
| A10 | Абстракция ОС — **OS Profile** (`debian`, `rhel`): пакетный менеджер, пути, имена сервисов, MAC (SELinux/AppArmor), firewall | Вся разница между семействами локализована в одном пакете кода |
| A11 | ACME-клиент встроен (библиотека **lego**) | Без certbot/python на хосте; HTTP-01 и DNS-01 (wildcard) из одного места, единая логика продления |
| A12 | Файловые операции от имени клиента — через **helper с понижением привилегий** | Защита от symlink-атак и подмены путей: агент никогда не трогает файлы клиента от root |
| A13 | Внутренний RPC api↔agent — HTTP/JSON поверх unix-сокета с `SO_PEERCRED` | Те же типы и инструменты, что во внешнем API; когда серверов станет несколько, транспорт сменится на mTLS без переписывания операций |

### 3.1 `monopaneld api` — непривилегированный процесс

- HTTPS-сервер панели (порт 8443, привязка к IP по выбору; сертификат: self-signed при установке → ACME для hostname панели).
- Раздаёт Web UI (SvelteKit static-сборка, вшита через `embed.FS`).
- REST API `/api/v1`: OpenAPI 3.1 генерируется из Go-типов (`huma`), SSE для прогресса задач. Веб-терминал на WebSocket — планируется; пока в Web UI есть «Консоль»: команды `mp` с потоковым выводом по HTTP.
- Аутентификация: сессии (cookie `Secure; HttpOnly; SameSite=Strict`), Bearer-токены, TOTP; WebAuthn (passkeys) — планируется. RBAC: `admin`, `user`. Scope у токена ограничивает только токены переезда (`migrate:user:<логин>`, бывают только у администраторов — §7), остальные scope — пометки.
- Unix-сокет `/run/monopanel/api.sock` для CLI (0660, группа `monopanel-cli`): uid 0 → admin без пароля; uid аккаунта с shell-доступом → его права (клиент по SSH управляет своими сайтами через `mp`). Аккаунты без shell в группу не входят, а запрос из рабочего процесса php-fpm, Apache или nginx — в том числе через `exec()` — отклоняется по цепочке предков в `/proc`: взломанный сайт не должен управлять аккаунтом своего владельца.
- Очередь задач в SQLite и несколько воркеров: задача — последовательность повторяемых шагов с логом и прогрессом; над одной сущностью одновременно идёт только одна задача (блокировка по `site_id`/`user_id`).
- Рендер конфигураций (`text/template`) из встроенных шаблонов с переопределением в `/etc/monopanel/templates/`.
- Планировщик внутренних задач: продление сертификатов, бэкапы по расписанию, сбор метрик, проверка обновлений.
- Хранит ключи ACME и секреты клиентов в зашифрованном виде (см. 3.6).

### 3.2 `monopaneld agent` — привилегированный процесс

- Тот же бинарник, режим `agent`, unit `monopanel-agent.service`, root.
- Сокет `/run/monopanel/agent.sock` (0660 root:monopanel). Проверка `SO_PEERCRED`: принимаются только uid `monopanel` и root.
- Операции — закрытый типизированный набор (нет «выполни строку в shell»):
  - `config/apply` — транзакционная запись набора файлов: прежние версии уходят в `confhistory` → запись во временный файл + `rename` → валидаторы (`nginx -t`, `apachectl -t`, `php-fpm -t`) → при ошибке восстановление и возврат stderr; при успехе reload сервисов.
  - `user/ensure|remove|password|shadow`, `group/ensure`, `dirs/ensure`, `file/ensure|read`, `sitelogs/ensure|remove`, `symlink/ensure`, `acl/set`, `chown`, `paths/remove`, `dir/list`, `stat`.
  - `service` — start/stop/reload/restart/enable/disable/status и daemon-reload через systemd D-Bus (`go-systemd`), а не `systemctl`.
  - `pkg` — install/remove/query/available через apt/dnf по OS Profile, с глобальной блокировкой и логом в задачу.
  - `tool` — закрытый список программ с проверкой аргументов: `mysql`/`mysqldump` (root через `auth_socket`, пароль root не хранится), `restic`, `nft`, `crontab`, `semanage`/`restorecon`/`setsebool`, `firewall-cmd`, `postfix`/`doveadm` и другие.
  - `runas` — helper с понижением привилегий для файловых операций клиента; `stream/in|out` — потоки tar для переезда; `panel/install` — установка пакета панели при обновлении; `panel/config` — собственные настройки панели в `config.yaml`, ровно пять ключей (`web.hostname`, `web.listen`, `log.level`, `log.format`, `jobs.workers`): остальной файл остаётся байт в байт, права и владелец — прежними, прежняя версия уходит в `confhistory`.
- Allow-list путей записи (`DefaultAllowedWritePrefixes` в `internal/config`): `/etc/monopanel/`, каталоги панели в конфигах nginx и Apache, конфиги PHP (`/etc/php/`, `/etc/opt/remi/`), MySQL, почты, memcached, Sphinx, источники пакетов, `/etc/nftables.d/`, `/etc/logrotate.d/`, `/etc/fail2ban/jail.d/`, снимки Valkey `/var/lib/monopanel-valkey/`, `/var/lib/monopanel/`; crontab — через `crontab -u`; файлы клиентов `/var/www/<user>/...` — через `runas`. Исключения из allow-list — `config.yaml` и `secret.key`: общие операции не пишут, не удаляют и не меняют права и владельца ни их, ни каталогов над ними (§7).

### 3.3 Helper (drop-privileges)

`monopaneld helper --uid N --gid N --groups ... -- <op> <args>`: агент форкает процесс, который до выполнения операции необратимо понижает привилегии (`setgroups` → `setgid` → `setuid`) и работает с файлами как клиент. Через него идут файловый менеджер, загрузка и распаковка архивов, установщики CMS (`wp-cli` и другие); git-деплой и терминал — планируются. Сам helper не имеет привилегированных путей кода.

### 3.4 Web UI

- SvelteKit 2 (Svelte 5, runes), `adapter-static`, TypeScript strict, Tailwind CSS 4. Сторонних UI-библиотек нет: компоненты, графики и таблицы свои; единственная внешняя зависимость в рантайме — `qrcode` (QR-код для TOTP).
- Два языка без библиотеки: словарь `web/src/lib/i18n` (фрагмент на страницу, `frag({ en, ru })` — тип требует одинаковый набор ключей, `t()`/`tn()` читают текущий язык из состояния на рунах, так что переключение перерисовывает всё сразу). Язык по умолчанию берётся из `navigator.languages`: языки стран СНГ → русский, остальные → английский; выбор в настройках хранится в `localStorage.lang`, `<html lang>` выставляется до загрузки приложения. Сообщения API, задач и диагностики — на английском; CLI и TUI выбирают язык по локали терминала по тому же правилу (`internal/i18n`, `MP_LANG=ru|en` задаёт его явно).
- Планируется: библиотека компонентов (shadcn-svelte / Bits UI), TanStack Query + Table, CodeMirror 6 для редактора конфигов, xterm.js для терминала, генерация клиента из OpenAPI (`@hey-api/openapi-ts`).
- Сборка в `web/build` и вшивание в бинарник; SPA, один HTML, целевой размер JS ≈ 200–300 КБ gzip.
- Два режима интерфейса: администратор видит весь сервер и все страницы; обычный аккаунт — дашборд (нагрузка и службы сервера, без диагностики), а на страницах сайтов, «Аккаунта» (свои cron, app-сервисы, Valkey, общие папки, API-токены и пароль), баз данных, почты, файлов, задач, журнала и настроек — только своё. Страницы по одной — в [09-web-ui.md](09-web-ui.md).

### 3.5 CLI и TUI

- `monopanel` (alias `mp`) — Cobra-команды, вывод таблицей или `--json`. Коды выхода: 0 — успех, 1 — ошибка, 2 — неверные аргументы или нет нужного ввода, 3 — задача завершилась с ошибкой, 4 — нет прав. У каждого секрета — паролей, токенов, секрета webhook, учётных данных DNS-провайдера, переменных бэкапа и app-сервисов — есть двойник `--…-stdin`: значение не остаётся ни в истории команд, ни в `ps`.
- Без аргументов в интерактивном терминале — TUI-меню (Bubble Tea v2 + Lip Gloss). Разделы повторяют навигацию Web UI, и обычный аккаунт видит те же разделы и команды, что в Web UI. Каждое действие — команда `mp`: форма строится из её флагов, рядом видна эквивалентная строка `mp` (секреты скрыты), команда запускается дочерним процессом того же бинарника, а её вывод идёт на экран по ходу выполнения. Перед тем, что удаляет или прерывает, TUI спрашивает так же, как Web UI, а удаление аккаунта, удаление сайта с файлами и восстановление снимка поверх файлов просят набрать имя аккаунта, домен или снимок. `?` или F1 — действия экрана, команды раздела и клавиши, `:` — любая команда `mp`, `*` — все команды раздела. Работает по SSH: локально через сокет, удалённо — с `--server` и `--token`; дочерним командам адрес и токен передаются через окружение, а не в командной строке.
- CLI/TUI — тонкие клиенты API (локально `/run/monopanel/api.sock`, удалённо `https://host:8443` с токеном; переменные окружения `MP_SERVER`, `MP_TOKEN`, `MP_INSECURE=1`). Ни одна операция не реализована «только в CLI»: без API работают только `help`, `completion`, `version`, а от root на сервере — `setup`, `config show|set --local` (восстановление, когда API не запускается) и `update trust`.
- Что каждая операция и каждое поле запроса API доступны из Web UI, `mp` и TUI, кроме намеренных исключений, проверяет тест `internal/parity` (§11). Детали и список исключений — в [04-cli-tui-api.md](04-cli-tui-api.md).

### 3.6 Хранилище состояния

- `/var/lib/monopanel/panel.db` — SQLite, WAL, `foreign_keys=ON`, `busy_timeout`. Драйвер `modernc.org/sqlite` (чистый Go, без CGO — бинарник остаётся статическим). Запросы написаны руками в `internal/store`, миграции — встроенные SQL-файлы, применяются при старте.
- Секреты (пароли БД клиентов, токены DNS-провайдеров, ключи ACME, пароли SFTP/S3 бэкапов) шифруются AES-256-GCM ключом из `/etc/monopanel/secret.key` (0640 root:monopanel). Бэкап SQLite без ключа для атакующего бесполезен.
- История конфигов: `/var/lib/monopanel/confhistory/` — прежние версии сгенерированных файлов, которые агент сохраняет при записи; diff в UI и ручной откат — планируются.
- Снимок состояния входит в бэкап сервера (`mp backup run`, область `server`): копия `panel.db` (`VACUUM INTO`), `/etc/monopanel` вместе с ключом секретов, `/var/lib/monopanel/{certs,acme}`, `/var/www` и дампы всех баз. Восстановление панели из него на новом сервере — вручную; переносить аккаунты между живыми серверами удобнее `mp migrate` ([07](07-migration.md)).

## 4. Стек панели и обоснование

### 4.1 Бэкенд / ядро

| Кандидат | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Go 1.26+** | Статический бинарник, быстрый старт, goroutines для задач, stdlib HTTP/TLS, зрелые библиотеки для systemd/ACME/nftables/TUI, кросс-сборка amd64/arm64, nfpm | Паузы сборщика мусора для панели несущественны | **выбран** |
| Rust | Максимальная производительность и безопасность памяти | В 2–3 раза дольше разработка; узкое место панели — nginx/PHP, а не ядро | нет |
| Python (FastAPI) | Скорость разработки | Интерпретатор на хосте: конфликты версий на одиннадцати релизах ОС, venv, медленный старт CLI | нет |
| PHP / Node.js | Знакомы веб-разработчикам | Рантайм на хосте; плохо подходят для системного демона с root-операциями | нет |

Библиотеки: `go-chi/chi` (роутер), `danielgtaylor/huma/v2` (OpenAPI 3.1 из типов, валидация), `modernc.org/sqlite`, `coreos/go-systemd/v22` (D-Bus), `go-acme/lego/v4` (ACME), `x/crypto/argon2`, `pquerna/otp` (TOTP), `boombuler/barcode` (QR-код в терминале для `mp totp setup`), `spf13/cobra`, `charm.land/bubbletea/v2` + `lipgloss/v2`, `miekg/dns`, `log/slog`, `goccy/go-yaml`, `goreleaser/nfpm` (deb/rpm, отдельный инструмент). Планируется: `go-webauthn/webauthn`, `google/nftables` (сейчас nftables управляется через файл правил и `nft`), `yookoala/gofast` (FastCGI-клиент для phpMyAdmin через панель).

### 4.2 Фронтенд

| Кандидат | Решение |
|---|---|
| **Svelte 5 + SvelteKit 2** | **выбран**: самый маленький бандл и самая быстрая работа в браузере среди популярных фреймворков, компилируемая реактивность (runes), статический адаптер, зрелая экосистема админ-компонентов (shadcn-svelte, Bits UI, TanStack) |
| React 19 + Vite | Экосистема больше, но бандл и рантайм тяжелее; приемлемая замена, если команда знает React |
| Vue 3 / Nuxt | Хорош, но без преимуществ перед Svelte для этой задачи |

Инструменты: Node 24 LTS, pnpm, Vite (последний стабильный), TypeScript strict, ESLint + Prettier, Vitest (unit), Playwright (e2e).

### 4.3 Транспорт и протоколы

- REST + JSON, OpenAPI 3.1, ошибки в формате RFC 9457 (`application/problem+json`).
- SSE для потоков (события задач, логи, метрики): проходит через любые прокси, без проблем с таймаутами, которыми страдает WebSocket.
- WebSocket только для интерактивного терминала (планируется).
- Внутренний RPC api↔agent — тот же HTTP/JSON поверх unix-сокета (те же типы huma), с обязательной проверкой peer-cred.

Инварианты:
- `domain` уникален (punycode, нижний регистр, без завершающей точки); алиас не может совпадать с доменом другого сайта.
- Один сайт = один пул FPM = один unix-сокет `/run/monopanel/php/<domain>.sock`.
- `php_version` ссылается на установленную версию; удаление версии блокируется, пока есть сайты на ней.
- Удаление пользователя каскадно удаляет сайты/БД/cron/сертификаты только с явным `purge` (иначе — `suspend`).
- Задачи с одинаковым `lock_key` выполняются строго последовательно.

## 6. Конвейер применения конфигурации

```
API: PATCH /sites/{domain} ─▶ валидация ─▶ desired state в SQLite ─▶ job "site.apply" (lock_key=site:<id>)
                                                                      │
worker: 1) собрать модель сайта из БД (site + user + php_version + cert + ip + settings)
        2) отрендерить: nginx sites/<domain>.conf, (apache sites/<domain>.conf), пул FPM, (default-server IP)
        3) agent.ApplyConfigSet(
              files    = [...],
              validate = ["nginx -t", "apachectl -t"?, "php-fpm -t -y <fpm.conf>"],
              reload   = [nginx, apache?, php-fpm@X.Y (или старый и новый master при смене версии)])
           агент: backup старых файлов → запись во временные → rename → валидаторы;
                  ошибка → восстановить backup → вернуть stderr валидатора в лог задачи;
                  ok     → reload через D-Bus → confhistory
        4) пост-шаги: restorecon (SELinux), ACL, симлинк data/bin/php при смене версии
        5) job=done, событие SSE ⇒ UI обновляет карточку сайта
```

Принципы:
- Панель владеет только файлами в своих каталогах и главным `nginx.conf` (по шаблону, с `include conf.d/*.conf` для ручных правок). Чужие конфиги не редактируются построчно.
- Пользовательские правки — только через include-каталоги `<domain>.d/*.conf`; панель их не перезаписывает, но валидирует вместе со всем набором.
- Шаблоны переопределяются файлом с тем же путём в `/etc/monopanel/templates/` (например `nginx/site.conf.tmpl`); `mp config templates` (и карточка «Шаблоны конфигураций» в настройках Web UI) перечисляет встроенные и показывает, какие из них переопределены. Команды, которые копируют встроенный шаблон и показывают его расхождение с новой версией панели, — планируются.
- Сайт перегенерируется из БД целиком командой `mp site apply <домен>` (`mp site fix` — ещё и владелец, права и метки файлов). Полный reconcile всего сервера одной командой — планируется.
- Смена версии PHP: новый пул создаётся до удаления старого, оба master перезагружаются, затем переключается nginx/Apache — простоя нет.

## 7. Безопасность

- Панель: TLS 1.2/1.3, HSTS, CSP без inline-скриптов, проверка Origin у мутаций по сессии (cookie и так `SameSite=Strict`), ограничение частоты входа + jail fail2ban по логу панели, argon2id, TOTP (WebAuthn планируется), аудит всех мутаций, API-токены со scope и сроком, по желанию привязка панели к отдельному IP или VPN.
- Сессии и токены: смена пароля завершает остальные сессии аккаунта в браузерах (та, из которой его сменили, остаётся), а сброс пароля администратором и блокировка аккаунта — все; API-токены при этом не отзываются — их отзывают отдельно, — но у заблокированного аккаунта не действуют, пока его не разблокируют. Двухфакторную аутентификацию нельзя настроить заново поверх включённой: сначала её выключают, а для этого нужен пароль. Область переезда (`migrate:user:<логин>`) открывает хеши паролей, ключи, файлы и базы аккаунта, поэтому бывает только у токенов администраторов: обычный аккаунт не может записать её в свой токен, администратор — в токен, который выпускает обычному аккаунту, а обработчики `/migrate` требуют роль администратора при любой области. Такие токены обычных аккаунтов, оставшиеся с прежних версий, панель отзывает при старте и пишет об этом в журнал действий. Логины системных учёток сервера (uid ниже `UID_MIN`) и имена, которыми панель подписывает свои задачи и записи журнала (`scheduler`, `system`), аккаунтам не даются.
- Процессы: api — `User=monopanel`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, `CapabilityBoundingSet=` (пусто), `ReadWritePaths=/var/lib/monopanel /run/monopanel /var/log/monopanel`; agent — root (ставит пакеты, заводит пользователей, пишет `/etc`), поэтому `ProtectSystem=` и урезанные capabilities ему невозможны, но остальное отрезано: `ProtectHome=read-only` (клиенты живут в `/var/www`), `ProtectKernelModules`, `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `PrivateTmp`, `RestrictRealtime`, `LockPersonality`, `SystemCallArchitectures=native`; плюс allow-list операций и путей, все exec — массив `argv` без shell.
- Агент: `config.yaml` и `secret.key` не трогает ни одна общая операция записи, удаления, смены прав или владельца, хотя `/etc/monopanel/` в allow-list (там шаблоны и модуль SELinux): в `config.yaml` решается, каким ключом проверяются релизы, ставящиеся от root (`update.public_key` подменяет вшитый ключ или выключает проверку), а `secret.key` расшифровывает все секреты. Пять собственных настроек в `config.yaml` панель меняет отдельной операцией `panel/config`, остальное в файле — только root (`mp config set --local`, `mp update trust`). Каталоги и файлы под `/var/www` агент создаёт и читает от root, проходя путь по одному каталогу и не следуя символьным ссылкам: клиент, подменивший каталог ссылкой, не направит такую запись в `/etc` или `/root` и не прочитает через неё `/etc/shadow`. Логи сайтов, которые от root открывают nginx, Apache и php-fpm, лежат вне домашних каталогов, в `/var/log/monopanel/sites/<логин>/`, где записи создаёт и меняет только root; агент проходит это дерево так же и не работает в каталоге, куда может писать кто-то ещё, а читает логи для API только через каталоги без ссылок и файлы с единственным именем. Файл вывода операции `tool` должен быть обычным файлом с одним именем, а системную учётку (uid ниже `UID_MIN`) агент аккаунтом панели не сделает.
- Клиенты: отдельный unix-пользователь и группа, домашний каталог `0710`, доступ веб-серверов через ACL для группы `monopanel-web`; пулы FPM от имени клиента; `open_basedir`, отдельные `tmp`/`session`; `disable_functions` по умолчанию; защита от symlink (`disable_symlinks if_not_owner` в nginx, `SymLinksIfOwnerMatch` в Apache); опционально cgroup-лимиты через изолированные пулы (см. [03-web-stack.md](03-web-stack.md) §6). Имя базы `<логин>_<имя>`, которое панель уже записала за базой или аккаунтом MySQL другого аккаунта (в логинах бывает `_`), не принимается. Сайт или почтовый домен обычный аккаунт не заведёт ни на имени самой панели или её почтового сервера (cookie сессии не привязана к порту, и такой сайт получал бы сессию администраторов), ни на имени, которое есть или лежит под сайтом или почтовым доменом другого аккаунта (почту своих доменов этот сервер доставляет себе сам); администратор ставит имена куда угодно.
- Сгенерированные файлы: значение, которое панель пишет в файл построчно, не может начать свою строку. Задание cron — одна строка без управляющих символов, с расписанием, которое понимают оба cron; значения юнита app-сервиса — без переводов строки и других управляющих символов и без `\` в конце, которой systemd продолжает строку; имена в картах postfix, passwd-файле dovecot и таблицах opendkim — без пробелов, управляющих символов, `:`, `/` и `,`, домен — по правилам DNS. Почтовые карты проверяются при каждой записи, так что и значение, попавшее в базу в обход API, останавливает применение, а не дописывает строку ([06](06-mail.md)). Переменные app-сервисов лежат в `EnvironmentFile` с правами root 0600 (`/etc/monopanel/apps/`), а не в `Environment=` юнита, который виден любому локальному пользователю; собственный env-файл аккаунта читает от его имени служебная команда `mp app-exec`, а не systemd от root, — символьная ссылка оттуда не откроет чужой файл.
- Вывод в терминал: имена, комментарии, сообщения и журналы задач, строки логов и записи журнала действий приходят от клиентов, от незнакомцев у формы входа и от источников переезда, поэтому `mp` и TUI печатают их без управляющих символов и последовательностей терминала (`internal/termsafe`): такая строка не сдвинет курсор, не подделает вывод, не сменит заголовок окна и не запишет в буфер обмена администратора.
- Переезд: посылка источника — ввод, а не конфигурация. Каждое её значение приёмник проверяет по тем же правилам, что API применяет к тому же значению, набранному человеком; нарушившее правило разбор показывает конфликтом, а задача такую запись не берёт и завершается ошибкой. `CREATE USER` источника не выполняется как есть, а собирается заново из плагина и хеша; дамп грузится от имени аккаунта самой базы, без команд клиента `mysql` и `LOAD DATA LOCAL`; из потока tar остаются только файлы, каталоги и ссылки внутри дерева, без setuid и файлов устройств; свои директивы nginx сайтов не применяются, а сохраняются для проверки. Подробно — в [07](07-migration.md#5-что-уже-работает).
- SSH/SFTP: клиент получает shell только по флагу; SFTP-only через `Match Group monopanel-sftp` + `ChrootDirectory`.
- Обновления панели — только релизы с подписью ed25519 (§9); компоненты стека — только из официальных репозиториев их разработчиков.
- SELinux на EL остаётся в enforcing (см. [02-platform-matrix.md](02-platform-matrix.md) §6).
- Секреты в БД зашифрованы, ключ вне БД. Пароли и токены не попадают в командные строки, которые видит любой локальный пользователь (`ps`): установщики CMS получают пароли на stdin, `install.sh` передаёт токен приватного репозитория `curl` конфигом на stdin, консоль Web UI и TUI дают дочернему `mp` адрес панели и токен через окружение (`MP_SERVER`, `MP_TOKEN`), а введённые пароли — на stdin через флаги `--…-stdin`. Параметры задач API отдаёт без секретов — пароли, ключи и токены в них заменены на `[redacted]` (пароли и ключи и в самой базе лежат зашифрованными), — и так же без них задача уходит в webhooks; журнал действий и эхо консоли скрывают значения секретных флагов.

## 8. Наблюдаемость

- Логи панели: `slog` → journald (`monopanel-api`, `monopanel-agent`), `mp logs <unit>`. Журнал действий (кто, что, откуда: входы удачные и нет, токены, изменения, отказы сокету) — таблица `audit_log` в базе панели, её показывают `mp audit`, `GET /system/audit` и страница «Журнал» (администратор видит всё, аккаунт — только своё); та же лента пишется строками JSON в `/var/log/monopanel/audit.log` (`log.audit_file`, ротация logrotate), а входы и отказы попадают и в journald. Лог каждой задачи хранится вместе с задачей (`mp job show <id>`, страница «Задачи»).
- Метрики: сэмплер раз в 10 с читает `/proc` (CPU, load, память, диск, сеть) и складывает точки по минутам на 30 дней — `mp metrics` и графики на дашборде. Разбор access-логов nginx по сайтам (запросы, трафик, время ответа) и endpoint `/metrics` для Prometheus — планируются.
- Логи сайтов: `/var/log/monopanel/sites/<user>/<domain>.{access,error}.log`, `<domain>.php.error.log`, `<domain>.php.slow.log`, у сайтов в режиме apache — `<domain>.apache.{access,error}.log`; `mp site logs`, вкладка «Логи» сайта. Каталог `root:<user>` 0751, вне домашнего каталога: логи открывают от root nginx, Apache и php-fpm, и в каталоге клиента их можно было подменить ссылкой. Клиент читает их через свою группу. Трассировки в slow-логе php-fpm на EL разрешает модуль политики панели ([02](02-platform-matrix.md#6-selinux-el9--el10)).
- Ротация логов сайтов — `/etc/logrotate.d/monopanel-sites`: по два блока на аккаунт, от root, раз в неделю или раньше, если лог перевалил за 100 МБ, восемь копий, сжатые начиная со второй. Логи серверов — `root:<логин>` 0640, журнал ошибок PHP — аккаунта с правами 0660: панель создаёт их до того, как их откроют nginx, Apache и php-fpm; nginx и Apache переоткрывают логи по USR1 через свои pid-файлы. Файл logrotate панель переписывает при появлении и удалении аккаунта и при старте, а перед записью проверяет его `logrotate --debug`. Подробности — в [03](03-web-stack.md#2-файловая-структура-на-сервере).
- Уведомления: webhooks с подписью HMAC-SHA256 на завершение задач — `job.done`, `job.failed` и `<тип задачи>.done|failed` (`site.apply`, `cert.issue`, `backup.run`…). Почта и Telegram — планируются.
- Диагностика: `mp doctor` и блок на дашборде — сервисы, синтаксис конфигов, диск, память, сертификаты, DNS имени панели, упавшие задачи, отказы SELinux для веб-сервера, дрейф сгенерированных файлов; у части находок есть кнопка «починить».

## 9. Упаковка, установка, обновление

- Сборка: `make packages VERSION=…` → бинарники amd64/arm64 → `nfpm` → `monopanel_<ver>_<arch>.deb`, `monopanel-<ver>.<arch>.rpm`, голые бинарники и `SHA256SUMS`. В пакете: бинарник, unit-файлы `monopanel-api.service` и `monopanel-agent.service`, sysusers/tmpfiles, `/etc/monopanel/config.yaml`; шаблоны конфигов вшиты в бинарник.
- Релиз: тег `v<ver>` → CI собирает пакеты, подписывает `SHA256SUMS` ключом ed25519 (`SHA256SUMS.sig`) и публикует релиз на GitHub; текст аннотированного тега становится описанием. Своего apt/yum-репозитория нет — планируется; пакеты берутся из релизов.
- Установка: `curl -fsSL https://monopanel.app/install.sh | sh` (адрес ведёт на `packaging/install.sh`): скрипт определяет ОС и архитектуру, берёт тег последнего релиза из редиректа `/releases/latest` (без GitHub API и его лимита), скачивает пакет, сверяет контрольную сумму и ставит его. Затем `mp setup`: служебный пользователь, каталоги, база, самоподписанный сертификат, администратор; адрес панели и пароль печатаются в конце, параметры задаются флагами (`--hostname`, `--listen`, `--admin-password`…). Стек — nginx, PHP, СУБД и остальное — ставится потом из официальных репозиториев: `mp stack install`, `mp php install` или из Web UI. TUI-мастер установки — планируется.
- Обновление панели: `mp update apply` или кнопка в «Настройках» (задача `panel.update`): поиск релиза, проверка подписи ed25519 списка контрольных сумм (ключ вшит в панель; `update.public_key` в `config.yaml` подменяет его для форка или выключает проверку значением `none`), загрузка пакета, установка агентом в transient-юните `monopanel-update.service` — он переживает перезапуск api и агента и возвращает прежний бинарник, если новая версия не отвечает; миграции базы применяются при старте. Проверка идёт по расписанию (раз в сутки), `--auto-apply` ставит найденное само. Обновление компонентов стека — по инициативе администратора; мажорные апгрейды СУБД не автоматизируются.

## 10. Структура репозитория

```
monopanel/
├── cmd/monopanel/            # единая точка входа: api | agent | helper | fsop | CLI/TUI
├── internal/
│   ├── api/                  # HTTP API (huma + chi), auth, SSE, Web UI, TLS панели, обработчики задач
│   ├── apitypes/             # типы запросов и ответов API — общие для сервера, CLI и TUI
│   ├── agent/                # привилегированный агент и его операции; agenttest — фейк для тестов
│   ├── jobs/                 # очередь задач, воркеры, блокировки по сущности, брокер событий
│   ├── store/                # SQLite: запросы, модели, встроенные миграции
│   ├── render/               # рендер шаблонов + golden-тесты
```

## 11. Тестирование

- Unit (`make test`, пара секунд): логика панели проверяется через фейковый агент (`internal/agent/agenttest`) без root и systemd — тест видит сгенерированные файлы и все вызовы агента; шаблоны — golden-файлами (`go test ./internal/render -update` обновляет их); валидаторы ввода, очередь задач, OS Profile. Отдельные тесты держат границы из §7: область переезда у обычного аккаунта, сессии после смены пароля, секреты в параметрах задач, почтовые карты против подложенных строк, пароли установщиков CMS вне командной строки, запись и чтение агента под `/var/www` мимо символьных ссылок, общие операции агента мимо `config.yaml` и `secret.key`, посылки переезда с подложенными значениями от MonoPanel, FASTPANEL и BitrixVM (`migrate_security_test.go`). `make check` добавляет `gofmt`, `go vet` и `golangci-lint`.
- Паритет клиентов (`go test ./internal/parity/`, входит в `make test` и CI): тест поднимает API за фейковым агентом и через манифест (`internal/parity/manifest_*.go` — у каждой операции её команды `mp`, места в Web UI и поля) сверяет четыре стороны: операции и поля запросов API из его описания OpenAPI, дерево команд `mp`, меню и формы TUI для администратора и для обычного аккаунта и исходники Web UI (`web/src`: какие пути и поля шлют страницы, спрятаны ли действия администратора от обычного аккаунта, нет ли вызовов путей, которых у API нет). Он падает, если операция или поле недоступны в каком-то клиенте, кроме намеренных исключений (`exempt.go` и списки в `parity_test.go`), и говорит, что и где исправить.
- Консоль Web UI проверяется по настоящему дереву команд `mp` (`internal/api/console_cobra_test.go`): команду она находит так же, как cobra, — с любыми флагами перед ней; команды и флаги, которые она отклоняет или считает собственными флагами команды, в `mp` есть; каждый секретный флаг, у которого в `mp` есть двойник `--…-stdin`, она переносит на stdin.
- Регресс шаблонов: `scripts/check-templates.sh` скармливает сгенерированные конфиги настоящим `nginx -t` и `apachectl -t` (в CI — на каждый push).
- E2E (`make e2e HOST=<ssh-алиас>`): на живой панели — пользователь → сайт с пресетом → база → nginx и PHP отвечают → удаление; `mp doctor` без ошибок.
- Матрица ОС — на площадке Proxmox ([08-testbed.md](08-testbed.md)), а не в CI: одиннадцать VM (Debian 12/13, Ubuntu 22.04/24.04/26.04, AlmaLinux 9/10, Rocky Linux 9/10, Oracle Linux 9/10) с откатом к чистому снимку. Перед релизом — `make testbed-full`: матрица, переносы между панелями, CMS на каждой машине, переезд с BitrixVM и FASTPANEL, doctor везде.
- Планируются: HTTPS через Pebble (тестовый ACME), бэкап → восстановление → suspend → purge в сценарии e2e, e2e Web UI на Playwright.
