# Тестовая площадка

Площадка — это Proxmox-хост, на котором по одной виртуальной машине на каждый дистрибутив из [матрицы платформ](02-platform-matrix.md): Debian 12 и 13, Ubuntu 22.04, 24.04 и 26.04, AlmaLinux 9 и 10, Rocky Linux 9 и 10, Oracle Linux 9 и 10. Машины собираются из официальных облачных образов через cloud-init, у каждой сразу после первой загрузки снимается снимок `clean`, так что прогон всегда начинается с чистой ОС. Всё, что относится к конкретному хосту — адрес, сеть, ключ, — лежит в git-игнорируемом `.dev/testbed.env`; в репозитории только скрипты.

## Как устроено

| Файл | Где выполняется | Что делает |
|---|---|---|
| `scripts/testbed/pve.sh` | на хосте Proxmox, от root | скачивает образы, создаёт машины (`q35`, OVMF, `cpu: host`, virtio-scsi, cloud-init на `scsi1`), ждёт cloud-init и гостевой агент, снимает и откатывает снимок `clean` |
| `scripts/testbed/testbed.sh` | локально | гонит `pve.sh` по ssh с настройками из `.dev/testbed.env`, пишет ssh-алиасы `mp-<имя>` в `~/.ssh/config.d/monopanel-testbed`, собирает пакет, разворачивает панель, запускает e2e и проверки защиты, обновляет машину с прошлого релиза |
| `scripts/testbed/bootstrap.sh` | на машине, от root | ставит `.deb`/`.rpm` (или голый бинарник), `mp setup`, затем через панель — nginx, ветку PHP, СУБД, дополнительно apache/fail2ban/firewall/mail; заканчивает `mp doctor` |
| `scripts/testbed/checks.sh` | на машине, от root | [проверки защиты](#проверки-защиты): строка `PASS`/`FAIL`/`SKIP`/`EXPECTED` на проверку и итог `TOTAL`, выход 1 при любом `FAIL`; всё, что создаёт для себя, убирает |
| `scripts/testbed/upgrade-seed.sh` | на машине, от root, командами `mp` прошлого релиза | объекты, которые должно пронести [обновление](#обновление-с-прошлого-релиза): гости общей папки с shell и SFTP, сайт в режиме Apache, цель бэкапа с бэкапом, composer и общая папка, которую владелец подменил символьной ссылкой, а юнит прошлого релиза смонтировал по пути |
| `scripts/testbed/doctor-expected.sh` | его читают `checks.sh` и `full-run.sh` | предупреждения `mp doctor`, известные для машин площадки, с причиной; любое другое валит прогон |

Машина `n` получает vmid `900+n` и адрес `TB_PREFIX.(TB_IP_BASE+n)`, имя хоста `mp-<дистрибутив>`. Прошивка — OVMF без предустановленных ключей Secure Boot: образы EL10 требуют x86-64-v3, и всем машинам удобнее загружаться одинаково. Образы Oracle именуются по обновлению и сборке (`OL9U8_x86_64-kvm-b293`), новые появляются на yum.oracle.com/oracle-linux-templates.html.

Две особенности, найденные при сборке площадки. Диск cloud-init подключён к virtio-scsi, а не к `ide2`: у ядра `cloud` в Debian нет драйвера AHCI, и на q35 диск на `ide2` гость не видит. Готовность машины хост видит только по ответу гостевого агента, а закончил ли cloud-init, обёртка спрашивает по ssh: `guest-exec` в EL заблокирован фильтром агента и SELinux, а образы Oracle поставляются с уже запущенным агентом.

## Настройка

```
# .dev/testbed.env
PVE_HOST=root@pve.example.com
TB_PREFIX=192.0.2          # первые три октета сети машин
TB_GATEWAY=192.0.2.1
TB_IP_BASE=200             # машина n → 192.0.2.(200+n)
TB_SSH_KEY_FILE=~/.ssh/id_ed25519
```

## Команды

```
make testbed-up                    # создать недостающие машины, загрузить, снять clean
make testbed-status                # таблица: vmid, имя, адрес, состояние, снимок
make testbed-deploy VM=debian13    # собрать пакет, поставить панель и стек
make testbed-e2e VM=debian13       # e2e-тесты против этой машины
make testbed-checks VM=debian13    # проверки защиты на машине (scripts/testbed/checks.sh)
make testbed-reset VM=debian13     # откатить к clean
make testbed-matrix                # reset + deploy + e2e + checks на всех машинах параллельно, сводная таблица
make testbed-upgrade VM=debian13   # прошлый релиз, его объекты, обновление одним пакетом до этой сборки, checks
make testbed-migrate SRC=ubuntu2404 DST=debian13   # перенос аккаунта между двумя машинами с проверкой
make testbed-sources ARGS="migrate bitrixvm debian13"   # переезд с BitrixVM / FASTPANEL (машины-источники)
make testbed-full                  # всё для релиза: обновление, матрица с проверками, переносы, CMS, чужие источники, doctor — с итоговой сводкой
make testbed-down                  # удалить машины (образы остаются в кэше)
```

`VM=` можно опустить там, где команда имеет смысл для всех машин. Логи параллельного прогона — в `.dev/testbed/logs/<имя>.log` (обновления — `upgrade-<имя>.log`). Стек по умолчанию: nginx, PHP 8.4, Percona, на Debian и Ubuntu ещё Apache — сайты в режиме Apache бывают только там, и проверки смотрят Apache аккаунтов; переопределяется переменными `TB_PHP`, `TB_DB` (`percona`, `mysql`, `none`) и `TB_EXTRA` (`apache fail2ban firewall mail`; `TB_EXTRA=` пустая — без дополнений). В таблице матрицы у каждой машины видно, на каком шаге упало: `DEPLOY`, `E2E`, `CHECKS`; e2e и проверки идут оба, если развёртывание прошло, `TB_NO_CHECKS=1` выключает проверки, `TB_NO_RESET=1` — откат.

Панель на машине слушает самоподписанный сертификат на адрес машины, поэтому e2e идёт с `MONOPANEL_INSECURE=1` — обёртка ставит его сама. Токен для тестов выпускается через root-сокет (`mp token create`) и отзывается после прогона, пароль администратора нигде не сохраняется: он печатается один раз при первом `bootstrap.sh`. Кроме пути клиента (аккаунт, сайт с пресетом, база, удаление) e2e проверяет, что видно в API от защиты 0.8.20: смена своего пароля сессией и токеном без верного `current_password` получает 403 (на одноразовом администраторе), а администратор меняет чужой пароль без него; Services отвечает на запуск `debug-shell.service` 403 с причиной; custom-директивы nginx с `fastcgi_param PHP_VALUE` и `PHP_ADMIN_VALUE` отклоняются сообщением панели и не записываются (на одноразовом сайте), безобидная директива проходит; общая папка гостя с shell сообщается с `mount_point` в `/var/www/.shares/<гость>/`, SFTP-гостя — в его доме. Всё, что тест создаёт, удаляется и тогда, когда шаг упал (`t.Cleanup` сразу после создания). Прерванный прогон (Ctrl-C, таймаут) уборку не делает; оставшийся одноразовый администратор `e2eadm…` мешает `mp token create` от root, который выбирает единственного администратора сам: `testbed.sh e2e` убирает такого перед прогоном, на другом сервере уберите его сами — `mp user rm e2eadm… --purge --yes`.

## Полный прогон

`make testbed-full` (он же `scripts/testbed/full-run.sh`, `STAGES="matrix cms"` — часть этапов) делает всё, что проверяется перед релизом, и печатает сводку: обновление с прошлого релиза на всех машинах (первым: оно сбрасывает машины, матрица сбрасывает их снова), матрица на всех машинах вместе с проверками защиты, три переезда между панелями, четыре CMS на каждой машине (упавшая на сетевой ошибке CMS переустанавливается ещё раз), три чужих источника, `mp doctor` везде. Этап doctor падает не только на отказах, но и на любом предупреждении, которого нет в `scripts/testbed/doctor-expected.sh`; рядом с допустимым печатается его причина. Сейчас там одно: `restic sandbox` — «no Landlock» на ядрах UEK Oracle Linux 9/10, где Landlock есть в ядре, но не в его списке `lsm=`. `STAGES=checks` прогоняет проверки защиты ещё раз на уже развёрнутых машинах. Логи — в `.dev/testbed/logs/`, пароли панелей и админок CMS — в `.dev/panels.txt` и `.dev/cms.txt`. Итог `exit 1`, если хоть что-то упало. Установщики CMS теперь пишут в лог и строки `note` — повторы и пропуски шагов мастера Битрикса, которые раньше терялись на успешной установке.

Сертификат панели каждой машины выпускается один раз: у Let's Encrypt лимит пять сертификатов на имя в неделю, а откат к снимку выпускал новый. `testbed.sh deploy` хранит выпущенный сертификат в `.dev/testbed/certs/<машина>/` и ставит его обратно (`mp ssl panel import`), пока до конца срока больше месяца.

## Проверки защиты

`make testbed-checks VM=<машина>` (он же `testbed.sh checks <машина>`) копирует `checks.sh` и `doctor-expected.sh` в `/root/tb-checks/` и проверяет от root механизмы 0.8.20 на живой машине; матрица делает это после e2e, обновление — после пакета. Каждая проверка — одна строка: `PASS`, `FAIL`, `SKIP` (к этой машине не относится), `EXPECTED` (известный недостаток машины из `doctor-expected.sh` — с причиной, а не молча) или `INFO`; в конце `TOTAL pass=… fail=… skip=… expected=…`, выход 1 при любом `FAIL`. Для себя проверки создают аккаунты `tbcka`, `tbckb`, `tbcksh`, `tbcksf` с сайтами `*.<машина>.test` и общими папками (и в их домах — каталог, на который владелец подменяет папку, FIFO и файл с setuid), tmpfs `tbck-tmpfs` внутри общей папки, цели бэкапа `tbck` и `tbckmix` в `/var/backups/tbck`, при необходимости ставят composer — и в конце всё это убирают, в том числе после провала; остатки прерванного прогона убираются в начале. Пароли аккаунтов и репозиториев случайные, уходят в `mp` через stdin и нигде не печатаются.

- **панель**: `mp`, API и агент одной сборки, агент отвечает, а очередь задач пуста пять опросов подряд (после обновления или перезапуска агент может готовиться минуту и больше, а стартовая работа API начинается, когда он ответит, и идёт задачами — всё это дожидаются, и после проверок сокета тоже);
- **порт на сокете**: `monopanel-api.socket` включён и активен, API отдаёт `listen_via=socket`; порт занят во всех 150 замерах через 20 мс, пока идёт `systemctl restart monopanel-api`; `nobody` не может его занять за три перезапуска API, перезапуск агента и `kill -9` API; остановленный API поднимается первым подключением к сокету, и после всего этого он снова на сокете;
- **какие юниты трогает панель**: `mp service start` отказывает с причиной `debug-shell` (root-оболочка на tty9), экземпляру шаблона `modprobe@dccp.service` и `timers.target`, а `status debug-shell` и `reload-or-restart nginx` работают;
- **общие папки**: папка гостя с shell смонтирована в `/var/www/.shares/<гость>/<имя>`, в доме — символьная ссылка на неё, ни монтирования, ни юнита в доме нет; `.shares` — `root:root 711`, `.shares/<гость>` — `root:<гость> 750`; гость читает папку и пишет в неё через ссылку, другой аккаунт в его `.shares` не заглянет; SFTP-гость видит папку в своём chroot (дом — root'а, не доступен на запись другим, гость в `monopanel-sftp`, `sshd -T` даёт ему internal-sftp в `ChrootDirectory %h`); API сообщает те же `mount_point`; SFTP-гость, получив shell и потеряв его, уносит папку в `.shares` и обратно, а с ней и запись агента. Монтирует сам агент: ни одного mount-юнита ниже веб-корня в `/etc/systemd/system` и его `.wants`; на каждую папку — запись `root 600` в `/var/lib/monopanel-agent/shares` (каталог `root 700`): папка, точка монтирования, устройство:inode смонтированного каталога; монтирование показывает именно папку, у юнита, который systemd строит по таблице монтирований, нет файла (`FragmentPath` пуст), а группа распространения своя (`shared:N` не та, что у монтирования, где лежит папка): tmpfs, смонтированный в подкаталог папки у гостя с shell, на хосте не виден ни в папке владельца, ни у SFTP-гостя, а в пространствах монтирования php-fpm и nginx (`nsenter`) — в папке владельца; после 300 вызовов агента, входящих в пространство монтирования хоста, все его потоки — в его собственном пространстве, а не в пространстве PID 1. Прямо в сокет агента, как сделал бы взломанный API: `units/apply` mount-юнита, `start`, `restart`, `reload`, `reload-or-restart` и `enable` mount-юнита папки — 403; bind из `/var/www/.restore` и `/var/lib/monopanel-agent/restore` — 403 с причиной «не дом аккаунта» (403 за путь, которого нет, ничего не доказывает: область восстановления в веб-корне появляется только с первым восстановлением на место); `status` проходит (`stop` не пробуется: он размонтировал бы папку), монтирование на месте прежнее; занятую папку (процесс гостя работает в ней) `mp user share rm` не размонтирует, с причиной; папку, которую владелец подменил ссылкой на каталог другого аккаунта, агент не монтирует — 403 за символьную ссылку в пути (каталог чужой, и проверка владельца отказала бы и так, поэтому смотрится причина), ничего нового не смонтировано; после `mp site fix` обе папки — `failed` с причиной, каталог, на который указывает ссылка, и его файл остались как были (владелец, группа, права), а гости видят прежний каталог; когда подмену убрали, `mp site fix` монтирует их снова; строка «shared folders» в `mp doctor` — ok с числом папок;
- **Apache аккаунтов** (только Debian и Ubuntu): у каждого аккаунта с сайтами в режиме Apache свой `monopanel-apache@<логин>`, родитель — root, дети — аккаунта; общий `apache2.service` выключен, `www-data` не в `monopanel-web`; через nginx сайт отвечает 200, PHP работает от аккаунта и не видит ни секрета `X-MonoPanel-Backend`, ни `SCRIPT_URI`; `.htaccess` аккаунта A не отправит PHP в пул аккаунта B и в простаивающие пулы, не покажет server-status, символьная ссылка с `FollowSymLinks` не дотянется до файлов B, `Options -Indexes -ExecCGI -Includes -MultiViews` (Drupal, Magento) сайт не ломает, `RewriteRule` фронт-контроллера работает; запрос к Apache аккаунта напрямую, мимо nginx, от другого аккаунта получает 403 — и с подобранным секретом и поддельным `X-Real-IP`, и с `.htaccess` из `Satisfy Any`, `Order`/`Allow` с `Satisfy Any`, вложенных `<If>` и `RewriteEngine Off`; аккаунт не может занять адрес ни своего Apache, ни чужого во время его перезапуска; `backend.conf` и файл секрета nginx — `root:root 600`;
- **php-fpm**: пул `[www]` дистрибутива каждой ветки работает от `nobody` на `/run/monopanel/php/.idle-<ветка>.sock` (`root:root 600`), ни одного процесса php-fpm от `www-data` или `apache`;
- **composer**: от root отказывается, от аккаунта работает;
- **репозитории**: источники, которые пишет панель (nginx.org, MySQL, Sury, PPA), — только по https;
- **restic**: бэкап аккаунта в локальный репозиторий через панель, восстановление рядом — в `/var/lib/monopanel-agent/restore/<снимок>` (root, 700) — с тем же файлом, символьная ссылка аккаунта на `/etc/monopanel` вернулась ссылкой, а из самого `/etc/monopanel` в снимке ничего нет; каталог-репозиторий с чужими файлами отклонён, и в него ничего не записано (тот же каталог, опустошённый, принимается — и doctor считает отказ исправленным); на машине без Landlock, для которой в `doctor-expected.sh` есть правило, отказа нет (или `restic init` успевает записать репозиторий до отказа), и это `EXPECTED` с причиной, а без такого правила — `FAIL`;
- **восстановление и узлы**: бэкап дерева, где есть FIFO и файл с setuid; восстановление на место и рядом, которое вернуло бы их, отклоняется с именем узла ещё до `restic restore`, в `/var/www/.restore` ничего не появляется и рядом ничего не создаётся; поддерево рядом с ними (`data/www`) восстанавливается на место — та же задача с той же блокировкой, так что doctor считает отказы исправленными;
- **файлы пакета**: в `/etc/tmpfiles.d/monopanel.conf` каталог запуска `1771` и строка `php/`; после обновления `/etc/tmpfiles.d/monopanel-php.conf` остался ровно со строкой `d /run/monopanel/php 0755 root root -` (на свежем развёртывании его нет); `systemd-tmpfiles --clean --prefix=/run/monopanel` — разбор файлов как при загрузке, без изменений на диске — действительно их читает (выход 0, или 65 — строка чужого файла, которую он не разобрал) и не пишет `Duplicate line`; в `/etc/systemd/system` нет копий юнитов панели, шаблона Apache тоже; действует только правило пакета `/usr/lib/modprobe.d/monopanel.conf`, без `/etc/modprobe.d/monopanel.conf`; `modprobe -n -v sctp` показывает `install /bin/false`, а `socket(AF_INET, SOCK_STREAM, IPPROTO_SCTP)` от `nobody` не открывается (если модуль всё же загрузился, он выгружается, и это `FAIL`); агент не видит контейнера. У панели, поставленной голым бинарником (`testbed.sh deploy <машина> --binary`), вместо файлов пакета — файлы `mp setup`: юниты в `/etc/systemd/system` (проверка копий — `SKIP`), правило `/etc/modprobe.d/monopanel.conf` и `/etc/tmpfiles.d/monopanel-php.conf` со строкой `php/`;
- **mp doctor**: `restic sandbox` — ok, или `EXPECTED`, когда его предупреждение для этой машины есть в `doctor-expected.sh`; строка `api socket` — та, что посчитал сам API: она есть в `mp --json doctor`, `mp doctor` печатает её один раз, и считается она один раз (предупреждение, которое `mp` выводит сам, смотрится только для API без такой строки); `kernel modules` — ok; нет отказов и нет предупреждений вне списка (одна повторная попытка через 20 с: в момент проверки мог перезагружаться сервис);
- **менеджер пакетов и ежедневное обновление** (после doctor): установки развёртывания — nginx, PHP, СУБД — шли каждая в своём юните `monopanel-pkg-<запуск>.service` (`journalctl -u 'monopanel-pkg-*'`); то, что только читает (`query`, `candidates`), идёт дочерним процессом агента, поэтому там, где в журнале запусков нет (после обновления), проверки отправляют прямо в сокет агента обновление индекса пакетов и ищут его юнит в журнале — оно ничего не ставит и идёт после doctor, который судит об обновлениях по индексу, каким тот был; ни юнита, ни файла вывода запуска не остаётся; `mp stack auto-upgrade` — включено, в 04:00, со следующим запуском; у каждой ветки PHP одна версия в `mp php list`, `mp stack list` и базе пакетов;
- **SELinux** (EL): `ausearch -m avc -ts boot` пуст; домен агента — в журнале прогона.

`doctor-expected.sh` — строки `expect <где> <проверка> <деталь> <почему>`: «где» — регулярное выражение по «<машина> <ядро> <контекст>» (контекст `deploy` — свежее развёртывание, `upgrade` — обновление с прошлого релиза), «проверка» — имя проверки doctor как есть, «деталь» — регулярное выражение по её тексту. Правило описывает известное, а не нормальное: если машина получила то, чего ей не хватало, проверки скажут, что правило можно убрать.

Чего проверки не делают и что проверяют руками на машине площадки: им нельзя перезагружать машину, понижать, переустанавливать или удалять пакет, подменять базу панели и надолго ломать старт API. Поэтому вручную остаются: общие папки после перезагрузки (до старта API ни одна не смонтирована, потом смонтированы все, а подменённая остаётся `failed`); подмена папки ссылкой на `/var/lib/monopanel-agent/restore` или `/var/www/.restore` (агент отказывает тем же путём, что и при проверенной подмене на чужой каталог); 503 на изменение общей папки, пока восстановление на место идёт дольше 30 с; свой mount-юнит администратора ниже веб-корня (нужен перезапуск агента, а с ним и API); гость в системной или привилегированной группе, записи агента о папках, которых нет в восстановленной базе панели, и другой каталог в точке монтирования общей папки; обновление с гостем в системной группе и с десятками юнитов общих папок; сам вход по SFTP и FUSE-монтирование гостя (вместо него проверки монтируют tmpfs от root); понижение, переустановка и удаление пакета и установка без пакета на чистую машину; состояния `monopanel-api.socket` для строки `api socket` (выключенный и упавший, остановленный при работающем API, замаскированный — и `mp setup` при маске) и неудачный старт API (занятый `api.sock`, нечитаемый ключ TLS); строка `jobs` после удаления сайта, ключ блокировки применения вебпочты, хвост лога непереехавшего сайта и строка Apache на странице «Расширения» во время переезда; короткая ошибка обновления стека и подсказки `mp stack list`, строки TUI.

## Обновление с прошлого релиза

Матрица ставит каждую сборку на чистую ОС, а каждый сервер получает её поверх предыдущей. `make testbed-upgrade [VM=<машина>]` (он же `testbed.sh upgrade [имя...]`; без имён — все машины параллельно, по логу на машину и сводная таблица) проверяет именно это:

1. Релиз — тег перед текущей сборкой (для сборки разработки, `0.8.19-21-g…` или `0.8.19-dirty`, это последний тег, для чистой сборки тега — предыдущий) или `TB_FROM=v0.8.19`. Его deb, rpm и `SHA256SUMS` скачиваются `gh release download` (curl, если `gh` нет или он не вошёл) из репозитория origin (`TB_REPO=owner/name`, если origin не на GitHub) один раз в `.dev/testbed/releases/<тег>/`; пакеты сверяются с `SHA256SUMS`, а `SHA256SUMS` — с подписью `SHA256SUMS.sig` по ключу, вшитому в панель (`internal/updater/release.pub`; другой — `TB_RELEASE_KEY`).
2. Машина откатывается к `clean`, и пакет релиза ставит его же `bootstrap.sh` (`git show <тег>:scripts/testbed/bootstrap.sh`) — со стеком как у deploy и Apache на Debian/Ubuntu, но без токена Cloudflare: bootstrap 0.8.19 передавал его в командной строке. Панель остаётся на самоподписанном сертификате.
3. `upgrade-seed.sh` командами `mp` того релиза создаёт то, что обновление должно пронести: аккаунт `tbupown` с сайтом и папкой `shared/`, гостей `tbupsh` (с shell — до 0.8.19 папка монтировалась у него в доме) и `tbupsf` (SFTP), сайт в режиме Apache (Debian/Ubuntu — до 0.8.19 на общем `apache2`), цель `tbupbak` с одним бэкапом, composer, а последней — общую папку `attack/` для `tbupsf` (`atk`): `tbupown` подменяет её символьной ссылкой на открытый каталог `tbupsh`, лежащий за его `data/`, и юнит того релиза, перезапущенный (`systemctl restart`, как root может и там), монтирует по пути этот каталог в chroot `tbupsf` — ту самую дыру, которую закрывает обновление (если `tbupsf` его не видит, сид падает); для проверок остаётся `/root/tbup.env` с именами юнитов общих папок.
4. Пакет этой сборки ставится одним `apt-get install` или `dnf install` — так, как его ставит `mp update apply`, только с разрешением «понижения» (сборка разработки сортируется ниже своего релиза), — без `mp setup`: остальное должны сделать скрипты пакета и первый старт API. Установленная версия сверяется с версией пакета.
5. `checks.sh` с `TB_CARRIED=1`: всё перечисленное в предыдущем разделе и вдобавок перенесённое — пакет на месте без `mp setup`, гость с shell переехал в `.shares` и старого юнита в его доме нет, оба гостя читают свою папку, сайт в режиме Apache отвечает через Apache своего аккаунта, а общий `apache2` выключен, снимок прошлого релиза есть в репозитории и восстанавливается рядом с тем самым файлом, и новый бэкап пишется в тот же репозиторий; ни одного mount-юнита общих папок в `/etc/systemd/system` и его `.wants`, в журнале агента ровно одна строка «taken over» на каждый юнит прошлого релиза, записи агента для папок обоих гостей; монтирование подменённой папки снято — «taken off» в журнале, раньше удаления юнитов, — в её точке монтирования ничего нет, папка `failed` с причиной, и doctor её называет; затем проверки убирают подмену, и `mp site fix` монтирует папку снова (так doctor в конце прогона не видит предупреждения, которое дала бы лишь эта подложенная папка, и правило в `doctor-expected.sh` для неё не нужно); `monopanel-php.conf` сохранён, без `Duplicate line`, копий юнитов в `/etc/systemd/system` нет; после doctor обновление индекса проходит в юните `monopanel-pkg-<запуск>.service`.

Машина остаётся обновлённой для осмотра (пароль администратора прошлого релиза — в его логе). Пары «релиз — машина», на которых прошлый релиз не встаёт вовсе, пропускаются с причиной (`SKIP` в таблице): с v0.8.19 и более ранних это Ubuntu 26.04 — с тех пор как ppa:ondrej/php публикует resolute, они не ставят там PHP, потому что знают только rsa1024-ключ PPA, а apt 3 его отвергает; `TB_UPGRADE_ALL=1` пробует всё равно.

Самообновление здесь не проверяется: `mp update apply` ставит только опубликованный и подписанный релиз, а проверяемой сборки на GitHub ещё нет. Этот путь — для второй машины после выхода релиза: шаги 1–3 этого сценария, затем `mp update apply` вместо пакета.

## Имена в DNS

Машины сидят в частной сети, поэтому HTTP-01 до них не дотянется, а вот имена и DNS-01 — работают. Если в `.dev/testbed.env` заданы `TB_ZONE` (зона в Cloudflare) и `TB_CF_TOKEN` (API-токен с правом Zone:DNS:Edit на неё), `make testbed-dns` (он же `testbed.sh dns up`) создаёт для каждой машины `A`-записи `<имя>.tb.<зона>` и `*.<имя>.tb.<зона>` (метка `tb` меняется через `TB_DNS_LABEL`), без проксирования; `dns down` убирает их, `dns list` показывает.

С заданной зоной `deploy` называет панель её именем, а не адресом, регистрирует в ней Cloudflare как DNS-провайдера `cf` — токен уезжает на машину по stdin и нигде не печатается — и сразу выпускает панели боевой сертификат (`mp ssl panel issue --dns cf`; неудача не роняет деплой, панель остаётся на самоподписанном). Сертификат для сайта выпускается через `mp ssl issue <имя> --dns cf`; на площадке разумно брать `--staging`, чтобы не упереться в лимит Let's Encrypt на повторные сертификаты для одних и тех же имён при частых откатах к `clean`.

Проверено 2026-09-09: боевой сертификат панели alma9 через DNS-01 доверен с рабочего места, сайт `site1.rocky10.tb.<зона>` со staging-сертификатом отдаётся nginx по HTTPS (сайт создаётся с `--ssl none`, затем `mp ssl issue … --dns cf` и `mp site set … --ssl auto` — панель подхватывает уже выпущенный сертификат вместо HTTP-01). Учтите отрицательный кеш резолвера: имя под wildcard, спрошенное до появления записи, публичный резолвер может помнить как несуществующее до получаса.

## Перенос между панелями

Две любые машины площадки — готовая пара для [переноса](07-migration.md). `scripts/testbed/migrate.sh` (он же `make testbed-migrate`) создаёт на источнике аккаунт с сайтом, PHP-файлом, базой с данными и заданием cron, выдаёт токен (`mp migrate grant`), на приёмнике делает `mp migrate plan` и `mp migrate run` с `--insecure` (сертификаты самоподписанные) и проверяет, что всё приехало: unix-аккаунт с тем же хешем пароля, вход в панель старым паролем, сайт отвечает тем же PHP-файлом, строки в базе и пароль её пользователя, задание в crontab, `mp doctor` без ошибок. Аккаунт остаётся на обеих машинах для осмотра; `make testbed-reset` убирает его вместе со всем остальным.

## Чужие панели как источники

Кроме матрицы на площадке есть три машины-источника для [переезда с чужих панелей](07-migration.md#6-чужие-панели-и-серверы-без-панели): `bitrixvm` (AlmaLinux 9, vmid 913, .213), `bitrixvm7` (CentOS 7 с bitrix-env 7 — оба давно EOL, так до сих пор живут старые серверы Битрикса; vmid 914, .214, SeaBIOS, потому что у образа CentOS 7 нет EFI-раздела, репозитории cloud-init переводит на vault.centos.org) и `fastpanel` (Debian 12, vmid 912, .212). В матрицу они не входят (`pve.sh` держит их в отдельной таблице `SOURCES`), но `up`, `reset`, `status` и `dns` их знают. `scripts/testbed/sources.sh` (он же `make testbed-sources ARGS=…`):

- `install bitrixvm` ставит bitrix-env 9 официальным `bitrix-env-9.sh` (он требует выключить SELinux и перезагрузиться — скрипт делает это сам, ~15 минут) и создаёт management-пул, без которого `bx-sites` не работает; `install bitrixvm7` — старый `bitrix-env.sh` на CentOS 7, перед ним EPEL берётся из архива, Remi и Percona — с их ещё живых деревьев EL7 (ссылка на `epel-release-latest-7` в установщике мертва, а найденные репозитории он пропускает); `install fastpanel` — `install_fastpanel.sh` (пароль `fastuser` попадает в `.dev/sources.txt`).
- `seed bitrixvm|bitrixvm7 [FROM]` кладёт в `/home/bitrix/www` сайт Битрикса, который `testbed.sh cms FROM bitrix` поставил на машину матрицы (по умолчанию `alma9`), с его базой в `sitemanager` и реквизитами bitrix-env в `.settings.php`; главный сайт остаётся под `server_name _`, как у людей. `seed fastpanel [FROM]` заводит аккаунт `shop` с WordPress оттуда же, сайтом с docroot `public/`, алиасом и allow-списком, базой, crontab с `data/bin/php`, настоящим сертификатом Let's Encrypt (DNS-01 через панель FROM) и ящиком. FASTPANEL без лицензии из её биллинга не пускает ни в API, ни в интерфейс, поэтому строки аккаунта, сайтов, бэкендов, баз, сертификатов и cron пишутся прямо в `fastpanel2.db` — так, как их пишет живая панель (сверено с рабочим FASTPANEL 1.11); файлы, nginx, php-fpm и MySQL настоящие.
- Образ CentOS 7 оставляет в `resolv.conf` первым мёртвый nameserver libvirt (192.168.122.1): каждый запрос ждёт 5 секунд, вход по ssh — 40, а разбор переезда — минуты. `pve.sh` вычищает его при каждой загрузке, `prepare_centos7` — ещё раз перед установкой.
- `migrate bitrixvm|bitrixvm7 DST` и `migrate fastpanel DST` дают root машины DST ключ на источник, ставят там ветку PHP источника, делают `mp migrate plan` и `run` и проверяют: сайт отвечает по новому адресу (у Битрикса — `X-Powered-CMS`, у WordPress — по HTTPS с перевезённым сертификатом), пути `/home/bitrix` переписаны, вход в базу прежним паролем или хешем, unix-хеш совпадает с источником, cron и allow-список на месте.

Пароли, которые придумывает `seed`, лежат в `.dev/sources.txt` (git-ignored). Прогон 2026-09-12: BitrixVM → debian13 и FASTPANEL → rocky9 без замечаний.

## CMS поверх пресетов

`make testbed-cms NAME=<машина> [CMS="wordpress joomla opencart bitrix"]` (он же `testbed.sh cms`) ставит на машину CMS средствами самой панели — `mp cms install` — в сайты с соответствующими пресетами и проверяет, что сайт работает, а правила пресета действуют. Нужны имена в DNS (`dns up`): сайты называются `<cms>.<машина>.tb.<зона>` и живут по HTTP — HTTP-01 до частной сети не дотянется, а проверять пресеты TLS не нужен. Пользователь панели `cms`; сайт с файлами переустанавливается с `--force`.

- **WordPress**: главная и вход, `/wp-admin/` уводит на логин, `xmlrpc.php` закрыт (403), PHP в `wp-content/uploads/` не исполняется, ЧПУ-ссылка отдаёт 200.
- **Joomla**: главная, `/administrator/`, `configuration.php` и `cache/` закрыты, `/api/` отвечает 401, PHP в `images/` не исполняется, SEF-маршрут работает, `installation/` удалён.
- **OpenCart**: витрина, `/admin/`, `system/` и `storage/` закрыты, `.twig` не отдаётся, SEO-URL уходит в `_route_`, `install/` удалён.
- **1С-Битрикс** (пробная «Старт»): `X-Powered-CMS: Bitrix Site Manager` на главной, форма входа `/bitrix/admin/`, закрытые `php_interface/dbconn.php`, `modules/`, `.settings.php`, `cache/`, PHP в `upload/` не исполняется, несуществующий адрес обрабатывает `urlrewrite.php`, `mp site php` показывает `short_open_tag On`, `max_input_vars 20000`, `memory_limit 512M`.

Доступы к админкам печатаются строками `CREDS` один раз. Что пришлось учесть, пока сценарий был ещё ручным: на EL Percona идёт с `validate_password` (пароль базы должен содержать все классы символов, панель их генерирует так); файлы, скопированные `cp -a` из `/root`, на EL сохраняют метку SELinux `admin_home_t` — теперь это чинит `mp site fix`, а панель после распаковки метит файлы сама; `mp db create` для существующей базы не ошибается, а переустанавливает пароль.

## Что нашёл первый прогон (2026-09-09)

До площадки панель проверялась только на Ubuntu 24.04. Первый же круг по всей матрице дал шесть ошибок, первый переезд — седьмую, и каждая из них воспроизводилась только на настоящей ОС — тест с поддельным агентом их увидеть не мог:

| Где | Что было | Что сделано |
|---|---|---|
| Ubuntu 26.04 | у `ppa:ondrej/php` нет сборок для resolute, `apt update` падал на 404 | панель проверяет `dists/<codename>/Release` перед подключением, ставит PHP из самой Ubuntu (8.5), в списке веток помечает недоступные с причиной, при следующей установке проверяет PPA снова и убирает за собой негодный источник |
| EL9, EL10 | nginx не стартовал: `nginx -t`, которым агент проверяет конфигурацию, создавал `/run/nginx.pid` с меткой `var_run_t`, домен `httpd_t` его не открывал | у набора конфигов появилось поле `restore`; агент после записи файлов и создания каталогов делает `restorecon`; при первой установке nginx/PHP панель настраивает `fcontext` и булевы SELinux под хостинг ([02](02-platform-matrix.md#6-selinux-el9--el10)) |

| EL9, EL10 | Percona ставится с временным просроченным паролем root в `/var/log/mysqld.log`, плагин `auth_socket` не загружен | панель читает пароль из лога, задаёт свежий (просроченный пускает только `ALTER USER`), грузит плагин и переводит root на сокет; пароль на время трёх запросов живёт только в памяти и передаётся через окружение |
| EL (Percona) | `validate_password` MEDIUM отвергал примерно половину сгенерированных паролей баз — случайная строка без гарантии спецсимвола; Rocky прошла случайно | генератор `auth.NewPassword` гарантирует все классы символов; используется для паролей баз, ящиков и Roundcube |
| Ubuntu 24.04 | `repo.percona.com` ответил таймаутом TLS, установка упала целиком | загрузки ключей и пакетов репозиториев повторяются при сетевых ошибках |
| перенос | хеш `caching_sha2_password` с бинарной солью портился в текстовом выводе `SHOW CREATE USER` (`ERROR 1827`) | источник просит сервер печатать хеш hex-литералом |

После исправлений полный прогон `make testbed-matrix` с чистых снимков зелёный на всех машинах (Ubuntu 26.04 — с PHP 8.5, остальные — 8.4; nginx 1.30, Percona 8.4), переносы Ubuntu 24.04 → Debian 13 и Debian 12 → AlmaLinux 10 проходят все проверки.

Oracle Linux 9 и 10 добавлены 2026-09-10 и нашли ещё две особенности: образы Oracle идут с включённым firewalld (только ssh) — теперь `mp setup` открывает в нём порт панели, установка nginx — 80 и 443, почты — её порты, а `mp firewall enable` его выключает; и `remi-release-10` требует `epel-release = 10`, которого пакет `oracle-epel-release-el10` не предоставляет — на OL10 панель ставит официальный `epel-release`. После этого e2e на обеих зелёный, перенос Ubuntu 24.04 → Oracle Linux 9 прошёл все проверки.

Сама площадка тоже кое-чему научила: cloud-init-диск на `ide2` невидим для ядра `cloud` Debian; в EL гостевой агент запрещает `guest-exec` (снимается в `/etc/sysconfig/qemu-ga`), а SELinux всё равно не даёт ему запускать команды — готовность машины на EL определяется по ответу агента; `pkill -f` внутри одной ssh-команды убивает и её саму; параллельные `deploy` не должны собирать пакет каждый сам — `matrix` собирает один раз.
