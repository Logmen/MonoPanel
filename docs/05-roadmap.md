### Файловый менеджер в Web UI (2026-09-06)
- [x] `FileManager.svelte`: обзор домашнего каталога аккаунта, хлебные крошки, переход к каталогу сайта, создание папки и файла, загрузка перетаскиванием и выбором, скачивание, переименование, права, распаковка архивов, множественное выделение и удаление — всё поверх существующего `/files`-API, то есть от имени владельца через helper.
- [x] Редактор текстовых файлов: нумерация строк, Ctrl+S, Tab, защита от ухода с несохранёнными правками. Двоичные файлы (по расширению или нулевому байту) и файлы больше 1 МБ открываются только на скачивание. Без подсветки синтаксиса — она означала бы новую npm-зависимость.
- [x] Страница `/files` (с выбором аккаунта для администратора) и вкладка «Файлы» в карточке сайта, открывающаяся в его docroot.
- [x] Редактор — Monaco, то же ядро, что в VS Code (`web/static/monaco`, MIT): подсветка php/html/css/js/ts/json/xml/ini/shell/sql/yaml/markdown/python/dockerfile, поиск и замена, мультикурсор, свёртка, палитра команд, тема следует за темой панели, высота — по содержимому. Сборка урезана с 24 МБ до 4,7: без языковых служб (IntelliSense-воркеры json/css/html/ts), переводов интерфейса и лишних режимов; бинарник вырос с 26 до 31 МБ. Грузится лениво, при сбое загрузки остаётся простое поле. Вендорится в репозиторий, а не тянется из npm или CDN: панель должна ставиться на сервер без интернета, а node-инструментов в репозитории нет. ### Обновление панели из релизов (2026-09-06)
- [x] `internal/updater`: релизы GitHub (или GitHub Enterprise через `api`), выбор по версии, а не по дате публикации; канал stable/beta; имена артефактов фиксированы (`monopanel_<v>_<arch>.deb`, `monopanel-<v>.<arch>.rpm`, `monopanel-linux-<arch>`, `SHA256SUMS`, `SHA256SUMS.sig`).
- [x] Подпись релиза ed25519: `scripts/release keygen|sign|verify`, приватный ключ — секрет репозитория, публичный — `update.public_key` в `config.yaml` (root-only, менять из панели нельзя). При заданном ключе неподписанный релиз не устанавливается; агент проверяет подпись повторно, а не доверяет хешу от API-процесса.
- [x] Установка вне панели: агент `POST /v1/panel/install` запускает transient-юнит `monopanel-update.service` (`StartTransientUnit`), который переживает перезапуск API и агента; `mp update-run` ставит копию пакета из `/var/lib/monopanel-agent/updates` — агент копирует её из загрузок API и даёт ей имя, только когда её SHA-256 совпал с подписанным списком; более старую версию поверх более новой (и релиз поверх более поздней сборки `0.8.19-N-g…`) агент не ставит, — перезапускает юниты, ждёт `/health` с новой версией и откатывает прежний бинарник, если она не отвечает. Итог пишется в `<data>/updates/state.json` и попадает в audit после перезапуска. С 0.9.0 установка идёт с окружением менеджера пакетов панели (`NEEDRESTART_MODE=l`), повтор после отката переустанавливает версию, которая уже числится в базе пакетов, а автоматическое обновление оставляет эту версию администратору.
- [x] API `GET|PUT /system/update`, `POST /system/update/check|apply` (только администратор), задача `panel.update`, ежедневная проверка по расписанию и `auto_apply`; токен репозитория шифруется секрет-боксом.
- [x] `mp update`, `mp update check|apply|settings|trust`; карточка «Обновление панели» в настройках Web UI ждёт перезапуск и перезагружает страницу; проверка `update` в `mp doctor`.
- [x] Установка последней версии сама считается проверкой (2026-09-24): задача `panel.update` запоминает найденный релиз, и после `mp update apply` статус больше не называет последним тот, что видела прошлая проверка.

### Почтовый сервер (2026-09-07)
- [x] `mp mail install`: postfix + dovecot + opendkim одной задачей — пакеты, пользователь `vmail`, конфигурация, сертификат, порты в firewall. Проверено на Ubuntu 24.04: submission с настоящим сертификатом, SASL через dovecot, LMTP-доставка, IMAP/POP3/ManageSieve, подпись DKIM, отклонение подмены отправителя.
- [x] Домены, ящики и алиасы (включая catch-all) в базе панели; postfix читает `hash:`-карты, dovecot — passwd-файл с `{BLF-CRYPT}` и `userdb_quota_rule`. Выключенный ящик исчезает из обеих карт: почта не принимается, войти нельзя, письма на диске остаются.
- [x] DKIM: ключ RSA 2048 генерируется панелью, приватный хранится зашифрованным в базе и файлом у opendkim; `mp mail domain dns` показывает MX/SPF/DKIM/DMARC/PTR и сверяет их с публичными резолверами (1.1.1.1, 8.8.8.8).
- [x] Сертификат почты — из того же хранилища, что у сайтов; при выпуске и продлении задача `cert.issue` сама перезапускает postfix и dovecot. Пока сертификата нет, поднимается самоподписанный, и панель об этом предупреждает.

- [x] Вебпочта: `mp mail webmail <домен>` ставит Roundcube 1.7.4 (архив с проверкой sha256) обычным сайтом панели — своя база, свой пул php-fpm, свой сертификат, `installer` удаляется.
- [x] Web UI `/mail`: статус, порты, домены с DNS-подсказками, ящики, алиасы, установка вебпочты; CLI `mp mail`; тесты на рендер конфигурации, карты, catch-all и уступку 25-го порта.
- [x] Вебпочта на порту: `--port 2096` публикует Roundcube на имени и сертификате почтового сервера (свой серверный блок nginx в `http.d`, порт в firewall, слушает и на петле) — без отдельной записи в DNS и второго сертификата.
- [x] Домен-приёмник (`--lenient`): строгие проверки HELO и отправителя перенесены в общий список с получателем, а карта `check_recipient_access` обрывает его на `OK`. Так на dev-хосте postfix занял 25-й порт, а mail-tester забирает почту из служебного ящика по IMAP и берёт IP отправителя из `Received` — проверено настоящим письмом с внешнего адреса и несуществующим доменом отправителя (отчёт тестера: «IP отправителя 83.97.77.254 (по заголовкам)»).
- [x] Страница почты грузилась 4,3 с: восемь портов опрашивались подряд и дважды, а на портах с обёрткой TLS проба ждала баннер, которого не бывает. Опрос разом, один раз на запрос → 0,02 с; Web UI забирает четыре списка параллельно и показывает скелет.

### Ротация логов сайтов (2026-09-24)
- [x] Логи в `/var/www/<логин>/data/logs` не ротировал никто: панель не писала конфигурацию logrotate, а конфиги дистрибутива этот путь не покрывают. Теперь `/etc/logrotate.d/monopanel-sites` — блок на аккаунт с `su <логин>` (каталог клиентский, root в нём ничего не делает): раз в неделю или по 100 МБ, восемь копий, сжатие со второй, `create 0660 <логин> <логин>`. Все логи сайта — аккаунта с правами 0660: панель создаёт их до того, как их откроют nginx, Apache и php-fpm, а созданные ими раньше передаёт аккаунту — новым флагом `mode` операции агента `chown`, через открытый файл (`O_NOFOLLOW`, `fchown`, `fchmod`). Иначе logrotate 3.18 на EL9 не справлялся: ротируя, он открывает лог, а сжимая — на запись. Файл переписывается при создании и удалении аккаунта (строка удаляемого уходит до `userdel`, чтобы logrotate не встретил несуществующего пользователя) и при старте панели, перед записью проверяется `logrotate --debug`.
- [x] Рабочие процессы nginx не могли переоткрыть логи сайтов после USR1 — ни после этой ротации, ни после ночной ротации самого nginx: в `data/logs` не было прохода для группы `monopanel-web`, и в журнал nginx каждую ночь падало `emerg … Permission denied`, а запись продолжалась в старый файл. `data/logs` получила ACL `g:monopanel-web:x` при создании сайта и `mp site fix`, существующие аккаунты — при старте панели. Apache переоткрывает логи graceful-рестартом по USR1 через pid-файл: `systemctl` из logrotate на EL упирается в SELinux.
- [x] slow-лог php-fpm на EL был пустым: трассировку php-fpm снимает через `ptrace` рабочего процесса, а штатная политика молча запрещает `httpd_t` возможность `sys_ptrace`. Панель ставит свой модуль политики `monopanel` (CIL, `semodule -i`) с `allow httpd_t self:capability sys_ptrace` и `self:process ptrace` — вместе с подготовкой хоста под хостинг, а на уже подготовленных хостах при старте, без повторного relabel.
- [x] Проверено на Debian 13 (с Apache), Ubuntu 22.04 (logrotate 3.19), Rocky 9 (3.18) и AlmaLinux 10 в enforcing: после ротации nginx, Apache, PHP и php-fpm пишут в новые файлы, вторая ротация сжимает первую от имени аккаунта, в slow-логе на EL есть трассировки, `logrotate.service` проходит, отказов SELinux нет.

- [x] `mp stack install valkey` ставит Valkey из дистрибутива (Debian 13, Ubuntu 24.04/26.04, EL9/EL10 AppStream, Debian 12 — из backports, если они подключены), а где его нет — Ubuntu 22.04, Debian 12 без backports — Redis (6.0 и 7.0) с тем же протоколом; общий экземпляр пакета (127.0.0.1:6379 без пароля для всех) останавливается и выключается. Сервер не удалить, пока на нём есть экземпляры.
- [x] У аккаунта два отдельных экземпляра: `cache` (allkeys-lru, `--save ""`) и `sessions` (volatile-lru, снимок раз в минуту). Каждый — `monopanel-valkey-<login>-<purpose>.service` от имени пользователя, `Type=notify` (перезапуск возвращается, когда снимок загружен и сокет принимает), `MemoryMax` вдвое больше maxmemory с запасом, конфигурация целиком в аргументах (к `/etc/monopanel` у аккаунта доступа нет). Нужны экземпляр sessions и расширение redis у ветки PHP сайта; пока сайт держит там сессии, экземпляр и расширение не удалить (409), сайт в режиме proxy сессий не держит.
- [x] SELinux (EL): сокеты — `redis_var_run_t`, каталоги снимков — `redis_var_lib_t`, сам `/var/lib/monopanel-valkey` остаётся `var_lib_t`: init_t не может добавлять записи в каталог `redis_var_lib_t`, и `StateDirectory=` падал с EACCES без единого AVC. Юнит без `ProtectKernelTunables=`, `ProtectKernelModules=` и `RestrictAddressFamilies=`: для не-root `User=` они включают NoNewPrivileges, а политика EL9 под ним не пускает переход init_t → redis_t, и сервер оставался в init_t без права писать снимки. Живая проверка на Debian 13, Ubuntu 22.04, AlmaLinux 10 и Rocky 9 (enforcing): другой аккаунт и веб-сервер получают «Permission denied», PHP-сессия через php-fpm переживает перезапуск, AVC нет.

### После переезда сайта на Аспро/1С-Битрикс (2026-09-26)
- [x] SFTP: создание сайта и `mp site fix` отдавали домашний каталог аккаунта «только SFTP» в собственность клиента, и sshd отказывал во входе с chroot. Каталог теперь всегда `root:<login> 0750` у SFTP-only и `<login>:<login> 0710` у аккаунта с shell — одно правило для создания аккаунта, сайта и починки. Уже испорченные каталоги панель чинит сама при старте, и запись группы `r-x` в ACL даёт клиенту увидеть корень chroot (chmod при ACL её не меняет).

Агент теперь сам обходит дерево (без перехода по символьным ссылкам) и ставит файлам маску явно: чтение для веб-группы, x — только если его даёт владелец, групповая запись сохраняется.

Для сайтов с сессиями в Valkey панель включает `redis.session.locking_enabled = 1`, `lock_retries = -1` (ждать, как файловая блокировка; сама блокировка истекает через `max_execution_time`), ключи `redis.session.*` можно менять в PHP-параметрах сайта и глобально.
- [x] Параметры MySQL в панели: `GET|PUT /db/engine/config`, `mp db config [set k=v|unset k]`, карточка на странице баз. Значения панели считаются под память хоста, заданное встаёт на их место в `zz-monopanel.cnf`; `mysqld --validate-config` до перезапуска (отказ проверки не трогает работающий сервер), при неудачном запуске прежние параметры возвращаются. То, что проверка пропускает, а сервер потом не запускается, панель не принимает сама: `default_time_zone` — только смещением или SYSTEM, `innodb_buffer_pool_size` — не больше памяти хоста.
- [x] Почтовый домен «только отправка»: почту принимает другой сервер (MX у провайдера), здесь — DKIM и отправка писем сайтов. Домена нет в картах приёма postfix, поэтому письмо сайта на адрес этого же домена уходит на настоящий MX. Ящиков и алиасов у такого домена нет; подсказка DNS не требует MX на этот сервер и советует дописать сервер в SPF провайдера, а не заменить его.

### Порт панели держит systemd (2026-11-21)
- [x] HTTPS-порт панели привязывает PID 1 (`monopanel-api.socket`) и передаёт его API: пока API перезапускается, падает, остановлен или ещё не запущен на загрузке, порт занят, и локальный аккаунт не поднимет на нём поддельную панель, чтобы собирать пароли и коды TOTP администраторов. ### Apache аккаунта отвечает только nginx (2026-11-21)
- [x] Любой локальный процесс мог обратиться к Apache аккаунта напрямую и обойти `--allow`, лимит запросов и адрес клиента сайта. Теперь nginx шлёт секрет аккаунта (`X-MonoPanel-Backend`, файлы root 0600), а Apache отклоняет запросы без него правилом mod_rewrite уровня сервера, до чтения `.htaccess`: ни `Satisfy Any`, ни вложенный `<If>` в `.htaccess` сайта проверку не отменят. PHP не видит ни секрета, ни `SCRIPT_URI`/`SCRIPT_URL`, которые добавил бы включённый в виртуальном хосте mod_rewrite (схема в них была бы `http` и у сайта на HTTPS). Агент не принимает location nginx, который проксирует на Apache аккаунта без секрета, и файлы Apache аккаунта, которые выключили бы проверку ([03 §4](03-web-stack.md#4-шаблон-apache-режим-b)).
- [x] Apache, настроенные без секрета сборками разработки 0.9.0, в том числе остановленные, панель один раз переводит на него (задача `apache.backend`): сначала nginx начинает слать секрет для всех сайтов аккаунта, потом Apache начинает его требовать, без 403. `monopanel-apache@` останавливается мягко (SIGWINCH, до 60 с на запросы в работе); `mp doctor` предупреждает о выключенном, но включённом в автозагрузку `apache2.service`.

### php-fpm и nginx: запросы — только пулам сайтов (2026-11-21)
- [x] Штатный пул `[www]` каждой ветки — пустой пул панели: `nobody`, сокет root 0600, ни одного процесса без подключения; на EL журнал мастера — в syslog. Раньше он работал от `www-data` или `apache`, которым принадлежат каталоги pid-файла, сокета и журнала root-мастера. `[www]` — только в `www.conf`, `include` в `php-fpm.conf` — с шаблоном только в имени файла.
- [x] nginx: `fastcgi_pass` — только на сокет пула сайта; `fastcgi_param PHP_VALUE`/`PHP_ADMIN_VALUE`, `proxy_method` не из слова, `uwsgi_modifier1` не 0, `proxy_pass unix:` и серверы `unix:` в блоке `stream`, `include` каталога `default.d` и шаблоны в каталогах `include` агент отклоняет; `include` nginx, php-fpm и dovecot проверяется так, как его раскрывает glob(3). Отказ в своих директивах сайта API называет отказом панели, а не ошибкой nginx.

### Песочница restic (2026-11-21)

### Логи сайтов вне домашних каталогов (2026-11-21)
- [x] Root через логи сайтов: мастер nginx открывает свои логи от root при старте, reload и USR1 (переоткрывая, ещё и меняет их владельца по имени), мастер Apache — тоже, мастер php-fpm открывает slow-лог на каждую запись, а лежали логи в `data/logs` аккаунта — каталоге клиента внутри его же `data/`. Клиент или PHP-код его сайта, подменив лог символьной ссылкой на `/etc/ld.so.preload` или `/etc/cron.d/x`, получал запись от root с частично своим содержимым (строка запроса, путь скрипта) — класс CVE-2016-1247. Теперь логи сайтов, журнал ошибок PHP и логи вебпочты на порту — в `/var/log/monopanel/sites/<логин>/`: `sites/` — `root:root` 0711, каталог аккаунта — `root:<логин>` 0751, логи серверов — `root:<логин>` 0640, журнал ошибок PHP — `<логин>:<логин>` 0660. Создаёт их новая операция агента `sitelogs/ensure`: проходит дерево через открытые каталоги без символьных ссылок, не работает в каталоге, куда может писать кто-то кроме root, и сама решает по имени, чей файл. Клиент читает логи через свою группу, панель и `mp site logs` — через агент.
- [x] logrotate ротирует это дерево от root, без `su`: блок логов серверов (`create 0640 root <логин>`) и блок журналов ошибок PHP (`create 0660 <логин> <логин>`). Вместо `*.error.log` в первом блоке четыре маски: файл, который называют два блока, logrotate не принимает.
- [x] Обновлённая панель при первом старте создаёт каталоги и логи аккаунтов и переприменяет сайты, чья конфигурация пишет логи в `data/logs` (`site.apply`, вебпочту на своём порту — `mail.apply`), пока каждый не применится успешно (см. «Переезды обновления» ниже); старые файлы в `data/logs` остаются клиенту, `data/logs` больше не создаётся. На EL до переключения сайтов добавляется правило `fcontext` `/var/log/monopanel/sites(/.*)?` → `httpd_log_t` и дерево перемечается. `/var/log/monopanel` теперь `root:monopanel` 1771 — проход для аккаунтов и рабочих процессов nginx, а sticky-бит не даёт API переименовать записи root. Удаление аккаунта с `purge` убирает и его логи (`sitelogs/remove`).
- [x] `file/read` агента больше не читает файлы в домашних каталогах, а в `/var/log/monopanel`, куда может писать и API, — только через каталоги без символьных ссылок и только файлы с единственным именем.
- [x] Каталоги, где root действует по имени. `/run/monopanel/php` (мастер php-fpm удаляет, создаёт сокет и отдаёт его владельцу по пути) создавали только задания API, а в `run_dir` API может писать. Взломанный API мог сделать `php/` своим и между bind и chown подменить сокет ссылкой: chown и ACL любого файла от root. Теперь `php/` принадлежит root с загрузки (tmpfiles пакета и `mp setup`). Агент при старте делает `php/` и `sites/` root'а, забирает чужие и вычищает лишнее, а перед запуском, перезапуском и reload php-fpm, nginx и Apache, перед их проверками конфигурации, перед установкой, обновлением и удалением пакетов и перед `dnf install` почты на EL отказывает, если дерево логов не только root'а, а для php-fpm и пакетов — и если не только root'а `php/`. Если уборка при старте не удалась, остальное дерево всё равно убирается, а отказы из-за дерева логов держатся, пока оно не вычищено (агент пробует снова перед каждым таким действием); `php/` достаточно принадлежать только root. Логи сайтов пишутся только прямо в каталог аккаунта. Строк tmpfiles API больше не пишет: `/etc/tmpfiles.d` вне allow-list, confcheck принимает только строку панели, юниты `systemd-tmpfiles-*` только показывают состояние.

- [x] SELinux: правило меток дерева логов сайтов панель повторяет каждый час и перед применением сайта; без него сайт на хосте в enforcing не применяется (работает как был), в permissive — применяется с предупреждением; вебпочта на своём порту ждёт правила так же, не задерживая остальные изменения почты.

### Пакетный менеджер переживает перезапуск агента (2026-11-22)
- [x] apt-get и dnf (update-index, install, remove, upgrade и `dnf install --enablerepo=crb` почты) запускаются transient-юнитом `monopanel-pkg-<run>.service`, а не в cgroup агента: перезапуск агента (самообновление, `systemctl restart`, `Requires=` API) больше не обрывает dpkg/rpm посреди транзакции. Вывод — в файле агента (root, 0600), не в pipe; предел 2 часа останавливает юнит; после перезапуска агент ждёт оставшийся запуск, а не встречает его на блокировке dpkg; задача, чей вызов оборвался вместе с агентом, называет юнит и `journalctl -u`; установка почты с CodeReady Builder получает свои 15 минут от начала запуска, а не от запроса. Запуски самой панели (`monopanel-pkg-*`, `monopanel-update`) в `mp service` и на странице «Службы» только показывают состояние.
- [x] Обновление стека и обновление панели не идут одновременно ни в каком порядке: вторая задача ждёт в очереди; установка обновления (`monopanel-update.service`) и запуски пакетного менеджера ждут друг друга в агенте.

- [x] EL: запуски пакетного менеджера и агент очищают свои `/tmp` и `/var/tmp` сами (`ExecStopPost` `monopanel clean-private-tmp`), так что каталог `rpm_script_tmp_t`, который оставляет `%post` Percona, больше не даёт AVC при каждой установке и обновлении и не лежит до перезагрузки; перезапуск агента при обновлении с 0.8.19 тоже проходит без AVC. Площадка читает `audit.log` сама: любой отказ, кроме ожидаемого отказа своего сида (только в окне его перезапуска, с записанными именем, inode и меткой), — `FAIL`, а очистку проверяет при каждом обновлении индекса ([02 §6](02-platform-matrix.md#6-selinux-el9--el10), [08](08-testbed.md)).

### Общие папки монтирует агент (2026-11-22)
- [x] Общую папку агент монтирует сам — каталог, открытый от веб-корня без символьных ссылок и проверенный (каталог владельца в его доме, не `.restore`/`.shares`), из дескриптора, в пространстве монтирования PID 1 (`setns`, `open_tree` + `move_mount`), а не mount-юнит systemd по пути `What=`: владелец, подменивший папку ссылкой, получал при загрузке или перезапуске юнита в chroot гостя чужой дом, `/var/lib/monopanel-agent/restore` или промежуточный каталог восстановления. Монтирование получает свою группу распространения (`mount_setattr`): смонтированное гостем внутри папки в дереве сайта не появляется. При загрузке папки не монтируются — их монтирует панель при старте, а записи агента, которых нет в её базе (после восстановления базы панели), снимает. Юниты прежних версий агент забирает при первом старте: сначала записывает, проверяет их монтирования и снимает монтирование не той папки, потом удаляет юниты; юниты с заголовком панели забираются, каким бы ни был аккаунт. Папку аккаунта в системной или привилегированной группе агент не монтирует (статус `failed` с причиной), снять её можно и тогда (ниже). `/v1/units/apply` mount-юниты не пишет, `/v1/service` mount-юниты ниже веб-корня не запускает. `mp doctor` называет несмонтированные папки.
- [x] Размонтирование папок гостя, которого агент больше не считает аккаунтом панели (по записи агента); уборка при старте записей папок, которых нет в базе (`/v1/shares/records`, строка «shared folders» в doctor); папку, на пути к которой стоит точка монтирования прямо в доме владельца, агент отклоняет (монтирования глубже — том для файлов сайта, FUSE — не мешают); общую папку, от которой у агента ничего нет, панель забывает без вызова агента (гость в системной группе, учётная запись удалена); при старте панель монтирует папку из базы туда, где запись агента называет другой каталог, и doctor это показывает; неудавшееся монтирование возвращает запись агента как была; отказы агента в выдаче и удалении папки доходят до клиента со своим статусом (403, 409 — папка занята, 503 — блокировку общих папок держит распаковка, восстановление или другой долгий обход дерева), а не 502.
- [x] Восстановление отклоняет снимок с файлами устройств, FIFO, сокетами и setuid/setgid в выбранных путях; песочница restic не создаёт таких узлов; блокировка общих папок держится всё восстановление на место. Тесты — `sharebind_test.go` (порядок при старте, зависшие проверки, заголовок панели, размонтирование отклонённого гостя, список записей, каталог прямо под домом на другом монтировании, том на `data` и том глубже в доме, неудавшееся монтирование оставляет запись как была), `sharebind_ns_test.go` (шаги busy, crossed, deeper mount и data volume), `internal/api/shares_test.go` (записи без папок при старте; гость, которого агент не считает аккаунтом панели, теряет все свои папки; другой каталог в точке монтирования общей папки; статусы отказов агента), `restore_nodes_test.go`, `internal/sandbox/nodes_test.go`.

- [x] Диагностика во время переезда на Apache аккаунтов: без ложных провалов у ещё не переехавших аккаунтов, общий `apache2.service`, остановленный при непереехавших сайтах, — провал; строка jobs учитывает только ту же работу (переезд на Apache аккаунтов исправляет и `mp stack install apache`), а удалённый сайт или аккаунт снимает свои прежние неудачи (прошедший `site.delete` или `user.delete` того же ключа блокировки); «kernel modules» в контейнере; строку «api socket» считает API.

- [x] Хвост лога непереехавшего сайта — из того из двух файлов, куда писали последним: `~/data/logs/<файл>` (от имени аккаунта) или файл дерева логов; подсказки `mp stack list` по строкам и с состоянием ежедневного обновления; `u` в диагностике TUI; страницы PHP показывают установленную версию FPM; после отката самообновления `mp update`, «Настройки», TUI и `mp doctor` говорят, что версия уже числится в базе пакетов.

### Гонки задач (2026-11-22)
- [x] `sites.move-ip` переносит каждый сайт под его блокировкой и пишет только адрес (статус «ошибка» становится «ожидание»). Изменение `mp site set`, сделанное во время переноса, не теряется, `site.apply` не пишет блок сайта между его удалением и переносом, а удалённые и удаляемые сайты не переносятся и не применяются. Блок вебпочты на порту уходит вместе с блоком её сайта и пишется заново на новом адресе: раньше он оставался слушать пропавший адрес, и перенос падал на проверке nginx.
- [x] Изменения сайта пишут только то, что меняют: `mp site set`, установка CMS (её запись в конце, через минуты после чтения сайта), приостановка и возобновление, заказ сертификата для сайта и привязка выпущенного сертификата больше не возвращают адрес, который тем временем дал сайту `mp site move-ip`, и не теряют изменение другого параметра, сделанное рядом (алиас, добавленный сайту без алиасов, тоже); возврат сайта из ошибки больше не снимает приостановку, сделанную в тот же момент. Сайт, удаление которого — его самого или его аккаунта — уже запрошено, больше не меняется: `mp site set`, `apply`, `suspend`, `unsuspend`, `fix`, `mp site nginx`, заказ сертификата и установка CMS получают отказ (409), а не ответ, что всё принято; удаление, запрошенное, пока такое изменение уже идёт, ловится при его записи, и изменение не записывается. `mp site nginx --set/--clear` во время установки CMS в этот сайт ждёт её конца. Два одновременных изменения одного параметра-списка (алиасы, `--ini`, `--allow`) по-прежнему решает последнее.
- [x] Настройки почты меняются по одному: `mp mail settings`, повторная `mp mail install` и `mail.apply`, заметивший другую версию dovecot, пишут своё поверх настроек, какими они стали, — изменение, сделанное тем временем, и вебпочта, убранная вместе с её сайтом, больше не возвращаются. Изменения почты применяются по очереди: каждое пишет файлы postfix и dovecot и блок вебпочты на порту по настройкам, какими они стали к его очереди, и изменение, сделанное во время другого, тем другим больше не перезаписывается.
- [x] Вебпочта ставится под блокировкой сайта и перед этим ещё раз читает сайт и владельца. Удаление сайта или аккаунта, о котором попросили раньше, останавливает её до изменений; то, о котором попросили позже, ждёт её: удаление сайта убирает вебпочту из настроек (с `--purge` — и дерево), удаление аккаунта ещё и базу `<логин>_roundcube` с учётной записью MySQL. Удаление сайта вебпочты убирает её блок на порту и запись в настройках почты; `mp mail apply` больше не падает на сайте вебпочты, который удалила прежняя версия. Вебпочта больше не распаковывается поверх CMS, которую в тот же сайт поставили во время её загрузки: она отказывается, как для любого сайта со своими файлами ([06 §10](06-mail.md#10-вебпочта)).
- [x] Установка CMS и удаление аккаунта её сайта больше не идут одновременно: удаление ждёт конца установки и затем убирает всё, что она сделала (файлы, базу и её пользователя MySQL); установка, которую задача начала уже после того, как удаление сайта или аккаунта было запрошено, останавливается, ничего не сделав. Удаление сайта или аккаунта и установка CMS, ждущие в очереди, больше не задевают другой сайт или аккаунт, созданный, пока они ждали.
- [x] Восстановление на место не пишет в дом удаляемого аккаунта и в дерево удаляемого сайта, а удаление аккаунта или сайта отказывает (409), пока такое восстановление в очереди или идёт, — в каком бы порядке их ни запросили, даже одновременно. Аккаунт, удаление которого запрошено, больше не меняется: `mp user set` получает отказ (409), так что ни смена статуса, ни задача подготовки аккаунта, стоявшая в очереди раньше, не снимают пометку удаления. Отказ значит, что ничего не изменилось, пароль тоже. Удаление, прерванное перезапуском панели, после запуска продолжается с той же пометкой.
- [x] `mp user set` пишет только то, что меняет: смена пароля или e-mail больше не отменяет блокировку (или разблокировку), сделанную в тот же момент, и не возвращает в ожидание аккаунт, который тем временем подготовила его задача; ответ показывает аккаунт таким, каким он записан. Подготовка аккаунта больше не снимает блокировку: заблокированный аккаунт и после смены оболочки (`--shell`/`--sftp-only`) остаётся заблокированным, `mp user set … --shell --status suspended` заканчивается блокировкой, а аккаунт, заблокированный во время переноса с другой панели, остаётся заблокированным и после него.
- [x] Лимиты времени задач по типам: бэкап 8 ч, восстановление 7 ч, переезд сутки (остальные задачи — час); пока долгие задачи занимают все воркеры, ещё один берёт остальные задачи, а автоматическое обновление их ждёт; строка jobs считает сутки от падения и забывает неудачу, чей объект удалили, — сайт вебпочты или, пока сайта с таким именем нет, аккаунт, для которого её просили, — если удаление поставили в очередь после задачи или оно закончилось после её старта; удаление сайта больше не пишет пустой список, файлы, «оставленные» в несуществующем каталоге, и «оставленные» файлы, которые уносит удаление аккаунта с файлами.
- [x] Строка jobs: прошедший `user.delete` снимает и неудачи сайтов, удалённых вместе с аккаунтом; `site.apply` и `site.delete` уже удалённого сайта завершаются успешно; `user.delete` не падает, если сайт аккаунта тем временем удалил его собственный `site.delete`.

### Почтовая политика (2026-11-22)
- [x] Аккаунт не отправляет почту от доменов другого аккаунта: milter `monopanel-mailpolicy` (тот же бинарник, свой пользователь без привилегий, сокет держит systemd) отвечает postfix раньше opendkim и отклоняет письмо, у которого конверт или From в домене другого аккаунта (550 5.7.1); проверяются ящики на 587/465, sendmail по uid отправителя и SMTP с адресов сервера по uid сокета; пока политика не отвечает, почта ждёт (`default_action=tempfail`). До 0.9.0 такое письмо уходило, и opendkim подписывал его ключом чужого домена. На EL `monopanel-mailguard` закрывает порты milter 8890 и 8891 для всех, кроме root и postfix. Пересылка sieve уходит с конвертом пересылающего ящика, автоответ — с конвертом ящика; почтовый домен нельзя взять сайтом или алиасом другого аккаунта; `TrustedHosts` opendkim — только адреса сервера. Строка `mail policy` в `mp doctor`; при откате ниже 0.9.0 скрипт пакета убирает политику из `main.cf` ([06 §11](06-mail.md#11-почтовая-политика)).

## Матрица ОС

| ОС | Режимы | PHP (выборочно) | СУБД |
|---|---|---|---|
| Debian 12, 13 | A, B | 5.6, 7.4, 8.2, 8.5 | Percona 8.4, MySQL 8.4 |
| Ubuntu 22.04, 24.04, 26.04 | A, B | 7.4, 8.3, 8.5 | Percona 8.4 |
| AlmaLinux, Rocky Linux, Oracle Linux 9, 10 | A, B | 7.4, 8.4, 8.5 (+ 5.6 на EL9) | Percona 8.4, MySQL 8.4 |

Раннер: [площадка](08-testbed.md) на Proxmox — одиннадцать VM из cloud-образов с cloud-init и откатом к чистому снимку; запускается с рабочего места, не в CI. Контейнеров недостаточно для SELinux, nftables, квот и systemd-слайсов.

Сценарий `make testbed-matrix`: установка пакета → `mp setup` → nginx, PHP, СУБД → e2e (пользователь → сайт с пресетом → база → nginx и PHP отвечают → удаление) → `mp doctor` без ошибок. Перед релизом `make testbed-full` добавляет переносы между панелями, CMS на каждой машине и переезд с BitrixVM и FASTPANEL. Планируются: HTTPS через Pebble, бэкап → восстановление → suspend → purge.

Планируется периодический job (еженедельно): доступность пакетов в вендорских репозиториях по матрице и появление новых версий (PHP 8.6/9.0, nginx stable, Percona 8.4.x, релизы ОС).

## Риски и как закрыты

| Риск | Чем закрыт |
|---|---|
| Sury/Remi исчезнут или сломают совместимость | Этап 2: собственные сборки и репозиторий; OS Profile позволяет держать оба источника одновременно |
| MySQL 9.x удалит `mysql_native_password` | Остаёмся на 8.4 LTS до 2032; для старых PHP — только 8.4; переход на 9.x — ручная процедура |
| Новый релиз ОС без пакетов от разработчиков компонентов | Поддержка объявляется только после прохождения матрицы; еженедельная проверка планируется |
| Ручные правки конфигов администратором | Include-каталоги, `confhistory`, `mp doctor` показывает дрейф, `mp site apply` перегенерирует сайт |
| Взлом веб-слоя | api без привилегий; агент с allow-list; helper с setuid; секреты зашифрованы |
| Рост числа сайтов (сотни) | `pm=ondemand`, один мастер на версию, SQLite с WAL держит десятки тысяч сущностей; метрики хранятся агрегатами |
