# Testbed

The testbed is a Proxmox host with one virtual machine for each distribution in the [platform matrix](02-platform-matrix.md): Debian 12 and 13, Ubuntu 22.04, 24.04 and 26.04, AlmaLinux 9 and 10, Rocky Linux 9 and 10, Oracle Linux 9 and 10. The machines are built from the official cloud images with cloud-init, and each gets a `clean` snapshot right after its first boot, so a run always starts from a clean OS. Everything specific to a particular host — address, network, key — lives in the git-ignored `.dev/testbed.env`; the repository holds only the scripts.

## How it works

| File | Where it runs | What it does |
|---|---|---|
| `scripts/testbed/pve.sh` | on the Proxmox host, as root | downloads the images, creates the machines (`q35`, OVMF, `cpu: host`, virtio-scsi, cloud-init on `scsi1`), waits for cloud-init and the guest agent, takes and rolls back the `clean` snapshot |
| `scripts/testbed/testbed.sh` | locally | runs `pve.sh` over ssh with the settings from `.dev/testbed.env`, writes the `mp-<name>` ssh aliases to `~/.ssh/config.d/monopanel-testbed`, builds the package, deploys the panel, runs e2e and the hardening checks, upgrades a machine from the previous release |
| `scripts/testbed/bootstrap.sh` | on the machine, as root | installs the `.deb`/`.rpm` (or a bare binary), runs `mp setup`, then uses the panel to install nginx, a PHP branch, a database server and optionally apache/fail2ban/firewall/mail; finishes with `mp doctor` |
| `scripts/testbed/checks.sh` | on the machine, as root | the [hardening checks](#hardening-checks): a `PASS`/`FAIL`/`SKIP`/`EXPECTED` line per check and a `TOTAL`, exit 1 on any `FAIL`; removes whatever it creates for itself |
| `scripts/testbed/upgrade-seed.sh` | on the machine, as root, with the previous release's `mp` | the objects an [upgrade](#upgrade-from-the-previous-release) has to carry: shell and SFTP guests of a shared folder, a site in Apache mode, a backup target with a backup, composer, and a shared folder its owner swapped for a symlink that the previous release's unit mounted by path |
| `scripts/testbed/doctor-expected.sh` | read by `checks.sh` and `full-run.sh` | the `mp doctor` warnings known for the testbed machines, with the reason; any other one fails a run |

Machine `n` gets vmid `900+n`, the address `TB_PREFIX.(TB_IP_BASE+n)` and the hostname `mp-<distro>`. The cloud-init disk is attached to virtio-scsi, not to `ide2`: Debian's `cloud` kernel has no AHCI driver, and on q35 the guest does not see a disk on `ide2`. The host can tell that a machine is ready only by the guest agent answering, and the wrapper asks over ssh whether cloud-init has finished — on EL, `guest-exec` is blocked by the agent's filter and by SELinux, and the Oracle images ship with the agent already running. Oracle images are named by update and build (`OL9U8_x86_64-kvm-b293`); new ones appear at yum.oracle.com/oracle-linux-templates.html. The firmware is OVMF without pre-enrolled Secure Boot keys, because the EL10 images require x86-64-v3 and it is simpler for all machines to boot the same way.

## Configuration

```
# .dev/testbed.env
PVE_HOST=root@pve.example.com
TB_PREFIX=192.0.2          # first three octets of the machines' network
TB_GATEWAY=192.0.2.1
TB_IP_BASE=200             # machine n → 192.0.2.(200+n)
TB_SSH_KEY_FILE=~/.ssh/id_ed25519
```

## Commands

```
make testbed-up                    # create the missing machines, boot them, take the clean snapshot
make testbed-status                # table: vmid, name, address, state, snapshot
make testbed-deploy VM=debian13    # build the package, install the panel and the stack
make testbed-e2e VM=debian13       # e2e tests against this machine
make testbed-checks VM=debian13    # the hardening checks on the machine (scripts/testbed/checks.sh)
make testbed-reset VM=debian13     # roll back to clean
make testbed-matrix                # reset + deploy + e2e + checks on all machines in parallel, summary table
make testbed-upgrade VM=debian13   # the previous release, its objects, an upgrade by the package alone to this build, checks
make testbed-migrate SRC=ubuntu2404 DST=debian13   # move an account between two machines and check it
make testbed-sources ARGS="migrate bitrixvm debian13"   # move from BitrixVM / FASTPANEL (source machines)
make testbed-full                  # everything for a release: upgrade, matrix with checks, migrations, CMS, foreign sources, doctor — with a final summary
make testbed-down                  # delete the machines (the images stay in the cache)
```

`VM=` can be left out where the command makes sense for all machines. The logs of a parallel run are in `.dev/testbed/logs/<name>.log` (those of an upgrade in `upgrade-<name>.log`). The default stack is nginx, PHP 8.4, Percona, and on Debian and Ubuntu Apache as well — sites in Apache mode exist only there, and the checks look at the accounts' Apaches; it is overridden with the variables `TB_PHP`, `TB_DB` (`percona`, `mysql`, `none`) and `TB_EXTRA` (`apache fail2ban firewall mail`; an empty `TB_EXTRA=` for no extras). The matrix table shows for each machine the step that failed: `DEPLOY`, `E2E`, `CHECKS`; e2e and the checks both run once the deploy went through, `TB_NO_CHECKS=1` turns the checks off and `TB_NO_RESET=1` the rollback.

The panel on a machine serves a self-signed certificate for the machine's address, so e2e runs with `MONOPANEL_INSECURE=1` — the wrapper sets it itself. The token for the tests is minted over the root socket (`mp token create`) and revoked after the run; the administrator password is not stored anywhere: it is printed once, on the first `bootstrap.sh`. Besides a customer's path (an account, a site with a preset, a database, removal), e2e checks what the API shows of the hardening of 0.8.20: changing one's own password over a session and over a token without the right `current_password` gets 403 (on a throwaway administrator), while an administrator changes another account's password without it; Services answers a start of `debug-shell.service` with 403 and the reason; custom nginx directives with `fastcgi_param PHP_VALUE` and `PHP_ADMIN_VALUE` are refused with the panel's message and not written (on a throwaway site), while a harmless directive goes through; a shared folder of a guest with a shell is reported with a `mount_point` in `/var/www/.shares/<guest>/`, an SFTP guest's in its home. Everything a test creates is removed even when a step fails (`t.Cleanup` right after the creation). An interrupted run (Ctrl-C, a timeout) does no cleanup; a throwaway administrator `e2eadm…` left behind gets in the way of `mp token create` as root, which picks the only administrator by itself: `testbed.sh e2e` removes such a leftover before the run, on another server remove it yourself with `mp user rm e2eadm… --purge --yes`.

## Full run

`make testbed-full` (also `scripts/testbed/full-run.sh`; `STAGES="matrix cms"` runs only some of the stages) does everything that is checked before a release and prints a summary: the upgrade from the previous release on all machines (first: it resets the machines, and the matrix resets them again), the matrix on all machines together with the hardening checks, three migrations between panels, four CMSs on each machine (a CMS that failed on a network error is reinstalled once more), three foreign sources, `mp doctor` everywhere. The doctor stage fails not only on failures but on any warning that `scripts/testbed/doctor-expected.sh` does not list, and prints the reason next to each one it allows. For now it lists one: `restic sandbox` — "no Landlock" on the UEK kernels of Oracle Linux 9/10, which have Landlock built in but not in their `lsm=` list. `STAGES=checks` runs the hardening checks once more on the machines as they are deployed. The logs are in `.dev/testbed/logs/`, the passwords of the panels and of the CMS admin areas in `.dev/panels.txt` and `.dev/cms.txt`. The result is `exit 1` if anything at all failed. The CMS installers now also write `note` lines to the log — retries and skipped steps of the Bitrix wizard, which used to get lost when an install succeeded.

Each machine's panel certificate is issued once: Let's Encrypt has a limit of five certificates per name per week, and a rollback to the snapshot used to issue a new one. `testbed.sh deploy` keeps the issued certificate in `.dev/testbed/certs/<machine>/` and installs it back (`mp ssl panel import`) as long as more than a month remains until it expires.

## Hardening checks

`make testbed-checks VM=<machine>` (also `testbed.sh checks <machine>`) copies `checks.sh` and `doctor-expected.sh` to `/root/tb-checks/` and checks the mechanisms of 0.8.20 on the live machine as root; the matrix does it after e2e, the upgrade after the package. Each check is one line: `PASS`, `FAIL`, `SKIP` (does not apply to this machine), `EXPECTED` (a known shortfall of the machine from `doctor-expected.sh` — with the reason, not silently) or `INFO`; at the end `TOTAL pass=… fail=… skip=… expected=…`, exit 1 on any `FAIL`. For themselves the checks create the accounts `tbcka`, `tbckb`, `tbcksh`, `tbcksf` with sites `*.<machine>.test` and shared folders (and in their homes the directory an owner swaps its folder for, a FIFO and a set-user-ID file), a tmpfs `tbck-tmpfs` inside a shared folder, the backup targets `tbck` and `tbckmix` in `/var/backups/tbck`, composer when it is missing — and remove all of it at the end, also after a failure; leftovers of an interrupted run are removed at the start. The passwords of the accounts and repositories are random, go to `mp` on stdin and are printed nowhere.

- **panel**: `mp`, the API and the agent are the same build, the agent answers and the job queue is empty in five polls in a row (after an upgrade or a restart the agent may take a minute and more to get ready, and the API's start-up work begins once it answers and runs as jobs — all of it is waited for, after the socket checks too);
- **port on the socket**: `monopanel-api.socket` is enabled and active, the API reports `listen_via=socket`; the port is bound in all 150 samples 20 ms apart while `systemctl restart monopanel-api` runs; `nobody` cannot take it through three API restarts, an agent restart and a `kill -9` of the API; a stopped API is started by the first connection to the socket, and after all of it it is on the socket again;
- **which units the panel acts on**: `mp service start` refuses `debug-shell` (a root shell on tty9), the template instance `modprobe@dccp.service` and `timers.target` with the reason, while `status debug-shell` and `reload-or-restart nginx` work;
- **shared folders**: the folder of a guest with a shell is mounted at `/var/www/.shares/<guest>/<name>`, its home holds a symlink to it, with no mount and no unit in the home; `.shares` is `root:root 711`, `.shares/<guest>` `root:<guest> 750`; the guest reads the folder and writes to it through the symlink, another account cannot look into its `.shares`; an SFTP guest sees the folder in its chroot (the home is root's and not writable by others, the guest is in `monopanel-sftp`, `sshd -T` gives it internal-sftp in `ChrootDirectory %h`); the API reports the same `mount_point`s; an SFTP guest that gets a shell and loses it again takes the folder to `.shares` and back, and the agent's record with it. The agent binds them itself: no mount unit below the web root in `/etc/systemd/system` or its `.wants`; per folder a record `root 600` in `/var/lib/monopanel-agent/shares` (directory `root 700`) naming the folder, the mount point and the device:inode of the directory bound; the mount shows the folder itself, the unit systemd builds from the mount table has no file (`FragmentPath` empty), and the mount has a peer group of its own (`shared:N` other than that of the mount the folder lies on): a tmpfs mounted in a directory of the folder at the shell guest's shows on the host neither in the owner's folder nor at the SFTP guest's, and in the mount namespaces of php-fpm and nginx (`nsenter`) not in the owner's folder; after 300 agent calls that join the host's mount namespace every thread of the agent is in the agent's own namespace, not PID 1's. Straight at the agent's socket, as a compromised API would: `units/apply` of a mount unit, `start`, `restart`, `reload`, `reload-or-restart` and `enable` of a folder's mount unit get 403; a bind of `/var/www/.restore` or `/var/lib/monopanel-agent/restore` gets 403 saying they are no account's home (a 403 for a path that does not exist proves nothing: the web root's restore area appears only with the first in-place restore); `status` passes (`stop` is not tried: it would unmount the folder), and the mount point holds the mount it held; a folder in use (a process of the guest's works in it) is not unmounted by `mp user share rm`, which says why; a folder its owner swapped for a symlink to another account's directory is not bound — 403 for the symlink on the way (the directory is another account's, so the owner check would refuse it anyway: the reason is what is checked), nothing new mounted; after `mp site fix` both shares are `failed` with why, the directory the symlink points at and its file are as they were (owner, group, mode), while the guests see the directory bound before; once the swap is undone `mp site fix` binds them again; the "shared folders" line of `mp doctor` is ok with the count;
- **the accounts' Apaches** (Debian and Ubuntu only): every account with sites in Apache mode has its own `monopanel-apache@<login>`, the parent root's, the children the account's; the shared `apache2.service` is off, `www-data` is not in `monopanel-web`; through nginx the site answers 200, PHP runs as the account and sees neither the `X-MonoPanel-Backend` secret nor `SCRIPT_URI`; account A's `.htaccess` cannot send PHP to account B's pool or to the idle pools, shows no server-status, a symlink with `FollowSymLinks` does not reach B's files, `Options -Indexes -ExecCGI -Includes -MultiViews` (Drupal, Magento) does not break the site, a front controller's `RewriteRule` works; a request straight to an account's Apache, past nginx, from another account gets 403 — also with a guessed secret and a forged `X-Real-IP`, and with an `.htaccess` of `Satisfy Any`, `Order`/`Allow` with `Satisfy Any`, nested `<If>` and `RewriteEngine Off`; an account can take the address neither of its own Apache nor of another one while that one restarts; `backend.conf` and nginx's secret file are `root:root 600`;
- **php-fpm**: the distribution's `[www]` pool of every branch runs as `nobody` on `/run/monopanel/php/.idle-<branch>.sock` (`root:root 600`), with no php-fpm process of `www-data` or `apache`;
- **composer**: refuses root, runs as an account;
- **repositories**: the sources the panel writes (nginx.org, MySQL, Sury, the PPA) are https only;
- **restic**: a backup of an account into a local repository through the panel, a restore aside — into `/var/lib/monopanel-agent/restore/<snapshot>` (root, 700) — with the same file, the account's symlink to `/etc/monopanel` comes back as the symlink and nothing of `/etc/monopanel` itself is in the snapshot; a repository directory holding files of someone else's is refused and nothing is written into it (the same directory, emptied, is accepted — and the doctor counts the refusal as fixed); on a machine without Landlock that `doctor-expected.sh` has a rule for there is no refusal (or `restic init` writes the repository before it), which is `EXPECTED` with the reason, and `FAIL` without such a rule;
- **restores and nodes**: a backup of a tree holding a FIFO and a set-user-ID file; restores in place and aside that would bring them back are refused before `restic restore` runs, naming the node, nothing appears in `/var/www/.restore` and nothing is restored aside; a subtree beside them (`data/www`) is restored in place — the same job with the same lock, so the doctor counts the refusals as fixed;
- **package files**: `/etc/tmpfiles.d/monopanel.conf` holds the run directory `1771` and the `php/` line; after an upgrade `/etc/tmpfiles.d/monopanel-php.conf` stays with exactly `d /run/monopanel/php 0755 root root -` (a fresh deploy has none); `systemd-tmpfiles --clean --prefix=/run/monopanel` — the files parsed as at boot, nothing changed on disk — really reads them (exit 0, or 65 for a line of another file it cannot parse) and prints no `Duplicate line`; `/etc/systemd/system` holds no copy of the panel's units, the Apache template's included; only the package's rule `/usr/lib/modprobe.d/monopanel.conf` applies, with no `/etc/modprobe.d/monopanel.conf`; `modprobe -n -v sctp` shows `install /bin/false`, and `socket(AF_INET, SOCK_STREAM, IPPROTO_SCTP)` as `nobody` fails (a module that loaded anyway is unloaded, and that is a `FAIL`); the agent sees no container. A panel installed as a bare binary (`testbed.sh deploy <machine> --binary`) has mp setup's files instead: its units in `/etc/systemd/system` (the copies check is `SKIP`), its rule `/etc/modprobe.d/monopanel.conf`, and `/etc/tmpfiles.d/monopanel-php.conf` with the `php/` line;
- **mp doctor**: `restic sandbox` is ok, or `EXPECTED` when `doctor-expected.sh` lists its warning for this machine; the `api socket` line is the one the API judged itself: it is in `mp --json doctor`, `mp doctor` prints it once, and it counts once (the warning `mp` prints of its own is looked at only for an API without that line); `kernel modules` is ok; no failures and no warnings outside the list (with one more try after 20 s: a service may have been reloading at that moment);
- **package manager and the daily upgrade** (after the doctor): the deploy's installs — nginx, PHP, the database — each ran in a unit of its own, `monopanel-pkg-<run>.service` (`journalctl -u 'monopanel-pkg-*'`); what only reads (`query`, `candidates`) runs as the agent's child, so where the journal holds no run (after an upgrade) the checks send an index refresh straight to the agent's socket and look for its unit in the journal — it installs nothing, and runs after the doctor, which judges the updates by the index as it was; no unit and no output file of a run is left; `mp stack auto-upgrade` is on, at 04:00, with a next run; each PHP branch has one version in `mp php list`, `mp stack list` and the package database;
- **SELinux** (EL): `ausearch -m avc -ts boot` is empty; the agent's domain goes into the run's log.

`doctor-expected.sh` holds lines `expect <where> <check> <detail> <why>`: "where" is a regular expression on "<machine> <kernel> <context>" (context `deploy` for a fresh deploy, `upgrade` for the upgrade from the previous release), "check" the doctor check's name as it is, "detail" a regular expression on its text. A rule describes what is known, not what is fine: once a machine gets what it lacked, the checks say that the rule can go.

What the checks do not do, and what is checked by hand on a testbed machine: they may not reboot the machine, downgrade, reinstall or remove the package, replace the panel's database, or break the API's start for long. So these stay manual: the shared folders after a reboot (none mounted until the API starts, all of them afterwards, a swapped one still `failed`); a folder swapped for a symlink to `/var/lib/monopanel-agent/restore` or `/var/www/.restore` (the agent refuses it the way it refuses the swap to another account's directory, which is checked); the 503 for a change of a shared folder while an in-place restore takes more than 30 s; an administrator's own mount unit below the web root (it takes an agent restart, and the API's with it); a guest in a system or privileged group, the agent's records of folders a restored panel database does not have, and another directory at a share's mount point; an upgrade with a guest in a system group and with dozens of shared folders' units; the SFTP login itself and a FUSE mount by the guest (the checks mount a tmpfs as root instead); a downgrade, a reinstall and a removal of the package, and an install without the package on a clean machine; the states of `monopanel-api.socket` behind the `api socket` line (disabled and failed, stopped while the API runs, masked — and `mp setup` with the mask) and a failed start of the API (`api.sock` held, the TLS key unreadable); the `jobs` line after a site's deletion, the lock key of the webmail's apply, the log tail of a site not moved yet and the Apache row of the Extensions page during the move; the short error of a stack upgrade and the hints of `mp stack list`, the TUI's rows.

## Upgrade from the previous release

The matrix installs each build on a clean OS, while every server gets it on top of the previous one. `make testbed-upgrade [VM=<machine>]` (also `testbed.sh upgrade [name...]`; without names, all machines in parallel, with a log per machine and a summary table) checks exactly that:

1. The release is the tag before the current build (for a development build, `0.8.19-21-g…` or `0.8.19-dirty`, the last tag; for a clean build of a tag, the one before it), or `TB_FROM=v0.8.19`. Its deb, rpm and `SHA256SUMS` are downloaded with `gh release download` (with curl when there is no `gh` or it is not signed in) from the origin repository (`TB_REPO=owner/name` when origin is not on GitHub) once into `.dev/testbed/releases/<tag>/`; the packages are checked against `SHA256SUMS`, and `SHA256SUMS` against the `SHA256SUMS.sig` signature with the key built into the panel (`internal/updater/release.pub`; another one with `TB_RELEASE_KEY`).
2. The machine is rolled back to `clean`, and the release's package is installed by its own `bootstrap.sh` (`git show <tag>:scripts/testbed/bootstrap.sh`) — with the stack as for deploy and Apache on Debian/Ubuntu, but without the Cloudflare token: the bootstrap of 0.8.19 passed it on a command line. The panel stays on its self-signed certificate.
3. `upgrade-seed.sh` creates, with that release's `mp` commands, what the upgrade has to carry: the account `tbupown` with a site and the folder `shared/`, the guests `tbupsh` (with a shell — up to 0.8.19 the folder was mounted in its home) and `tbupsf` (SFTP), a site in Apache mode (Debian/Ubuntu — up to 0.8.19 on the shared `apache2`), the target `tbupbak` with one backup, composer, and last a shared folder `attack/` for `tbupsf` (`atk`): `tbupown` swaps it for a symlink to an open directory of `tbupsh`'s behind its `data/`, and that release's unit, restarted (`systemctl restart`, as root may there too), mounts that directory by path in `tbupsf`'s chroot — the very hole the upgrade closes (the seed fails unless `tbupsf` sees it); `/root/tbup.env` stays for the checks, with the names of the shared folders' units.
4. This build's package is installed with a single `apt-get install` or `dnf install` — the way `mp update apply` installs it, only allowing a "downgrade" (a development build sorts below its release) — without `mp setup`: the rest has to be done by the package's scripts and the API's first start. The installed version is compared with the package's.
5. `checks.sh` with `TB_CARRIED=1`: everything in the previous section, and what was carried over — the package in place without `mp setup`, the guest with a shell moved to `.shares` with no old unit left in its home, both guests reading their folder, the site in Apache mode answering through its account's Apache with the shared `apache2` off, the previous release's snapshot in the repository and restored aside with that very file, and a new backup written into the same repository; no mount unit of a shared folder in `/etc/systemd/system` or its `.wants`, exactly one "taken over" line in the agent's journal per unit of the previous release, the agent's records for both guests' folders; the mount of the swapped folder taken off — "taken off" in the journal, before the units went —, nothing at its mount point, the folder `failed` with why, and the doctor naming it; then the checks undo the swap and `mp site fix` binds the folder again (so the doctor at the end of the run sees no warning that only this planted folder would give, and `doctor-expected.sh` needs no rule for it); `monopanel-php.conf` kept, no `Duplicate line`, no copies of the units in `/etc/systemd/system`; after the doctor an index refresh runs in a `monopanel-pkg-<run>.service` unit.

The machine stays upgraded for inspection (the previous release's administrator password is in its log). Pairs of release and machine on which the previous release does not install at all are skipped with the reason (`SKIP` in the table): from v0.8.19 and earlier that is Ubuntu 26.04 — since ppa:ondrej/php publishes resolute, they cannot install PHP there, because they know only the PPA's rsa1024 key, which apt 3 refuses; `TB_UPGRADE_ALL=1` tries anyway.

The self-update is not checked here: `mp update apply` installs only a published, signed release, and the build under test is not on GitHub yet. That path is for a second machine once the release is out: steps 1–3 of this scenario, then `mp update apply` instead of the package.

## DNS names

The machines sit in a private network, so HTTP-01 cannot reach them, but names and DNS-01 do work. If `TB_ZONE` (a zone in Cloudflare) and `TB_CF_TOKEN` (an API token with the Zone:DNS:Edit permission on it) are set in `.dev/testbed.env`, `make testbed-dns` (also `testbed.sh dns up`) creates `A` records `<name>.tb.<zone>` and `*.<name>.tb.<zone>` for each machine (the `tb` label is changed with `TB_DNS_LABEL`), without proxying; `dns down` removes them, `dns list` shows them. With a zone set, `deploy` refers to the panel by name rather than by address, registers Cloudflare in the panel as the DNS provider `cf` — the token travels to the machine over stdin and is never printed — and right away issues the panel a production certificate (`mp ssl panel issue --dns cf`; a failure does not break the deploy, and the panel stays on the self-signed one). A site certificate is issued with `mp ssl issue <name> --dns cf`; on the testbed it makes sense to use `--staging`, so as not to run into Let's Encrypt's limit on duplicate certificates for the same names with frequent rollbacks to `clean`. Tested on 2026-09-09: the alma9 panel's production certificate obtained via DNS-01 is trusted from the workstation, and the site `site1.rocky10.tb.<zone>` with a staging certificate is served by nginx over HTTPS (the site is created with `--ssl none`, then `mp ssl issue … --dns cf` and `mp site set … --ssl auto` — the panel picks up the already issued certificate instead of using HTTP-01). Mind the resolver's negative cache: a name under the wildcard that was looked up before the record appeared may be remembered by a public resolver as non-existent for up to half an hour.

## Migration between panels

Any two testbed machines make a ready pair for a [migration](07-migration.md). `scripts/testbed/migrate.sh` (also `make testbed-migrate`) creates an account on the source with a site, a PHP file, a database with data and a cron job, issues a token (`mp migrate grant`), runs `mp migrate plan` and `mp migrate run` on the target with `--insecure` (the certificates are self-signed) and checks that everything arrived: the unix account with the same password hash, signing in to the panel with the old password, the site answering with the same PHP file, the rows in the database and its user's password, the job in the crontab, `mp doctor` without errors. The account stays on both machines for inspection; `make testbed-reset` removes it along with everything else.

## Foreign panels as sources

Besides the matrix, the testbed has three source machines for [moving in from foreign panels](07-migration.md#6-foreign-panels-and-servers-without-a-panel): `bitrixvm` (AlmaLinux 9, vmid 913, .213), `bitrixvm7` (CentOS 7 with bitrix-env 7 — both long past EOL, which is still what old Bitrix servers run on; vmid 914, .214, SeaBIOS, because the CentOS 7 image has no EFI partition; cloud-init switches the repositories to vault.centos.org) and `fastpanel` (Debian 12, vmid 912, .212). They are not part of the matrix (`pve.sh` keeps them in a separate `SOURCES` table), but `up`, `reset`, `status` and `dns` know them. `scripts/testbed/sources.sh` (also `make testbed-sources ARGS=…`):

- `install bitrixvm` installs bitrix-env 9 with the official `bitrix-env-9.sh` (it requires SELinux to be switched off and a reboot — the script does this itself, ~15 minutes) and creates the management pool, without which `bx-sites` does not work; `install bitrixvm7` runs the old `bitrix-env.sh` on CentOS 7, with EPEL taken from the archive beforehand and Remi and Percona from their still-live EL7 trees (the installer's link to `epel-release-latest-7` is dead, and it skips the repositories it finds already in place); `install fastpanel` runs `install_fastpanel.sh` (the `fastuser` password goes into `.dev/sources.txt`).
- `seed bitrixvm|bitrixvm7 [FROM]` puts into `/home/bitrix/www` the Bitrix site that `testbed.sh cms FROM bitrix` installed on a matrix machine (`alma9` by default), with its database in `sitemanager` and bitrix-env credentials in `.settings.php`; the main site stays under `server_name _`, as on real servers. `seed fastpanel [FROM]` creates the account `shop` with WordPress from the same machine, a site with docroot `public/`, an alias and an allow-list, a database, a crontab with `data/bin/php`, a real Let's Encrypt certificate (DNS-01 through the FROM panel) and a mailbox. Without a license from its billing, FASTPANEL lets you into neither the API nor the interface, so the rows for the account, sites, backends, databases, certificates and cron are written straight into `fastpanel2.db` — the way a live panel writes them (checked against a working FASTPANEL 1.11); the files, nginx, php-fpm and MySQL are real.
- The CentOS 7 image leaves libvirt's dead nameserver (192.168.122.1) first in `resolv.conf`: every lookup waits 5 seconds, an ssh login 40, and a migration dry run takes minutes. `pve.sh` removes it on every boot, and `prepare_centos7` once more before the install.
- `migrate bitrixvm|bitrixvm7 DST` and `migrate fastpanel DST` give root on the DST machine a key to the source, install the source's PHP branch there, run `mp migrate plan` and `run` and check: the site answers at the new address (Bitrix with `X-Powered-CMS`, WordPress over HTTPS with the certificate that came along), the `/home/bitrix` paths are rewritten, the database login works with the old password or hash, the unix hash matches the source, cron and the allow-list are in place.

The passwords that `seed` makes up are in `.dev/sources.txt` (git-ignored). The run of 2026-09-12: BitrixVM → debian13 and FASTPANEL → rocky9 with no issues.

## CMS on top of presets

`make testbed-cms NAME=<machine> [CMS="wordpress joomla opencart bitrix"]` (also `testbed.sh cms`) installs CMSs on a machine with the panel's own tools — `mp cms install` — into sites with the matching presets, and checks that the site works and the preset's rules take effect. DNS names are required (`dns up`): the sites are called `<cms>.<machine>.tb.<zone>` and are served over HTTP — HTTP-01 cannot reach into the private network, and TLS is not needed to check presets. The panel user is `cms`; a site that already has files is reinstalled with `--force`.

- **WordPress**: the home page and the login, `/wp-admin/` redirects to the login, `xmlrpc.php` is closed (403), PHP in `wp-content/uploads/` does not execute, a pretty URL returns 200.
- **Joomla**: the home page, `/administrator/`, closed `configuration.php` and `cache/`, `/api/` answers 401, PHP in `images/` does not execute, a SEF route works, `installation/` is removed.
- **OpenCart**: the storefront, `/admin/`, closed `system/` and `storage/`, `.twig` is not served, an SEO URL goes to `_route_`, `install/` is removed.
- **1C-Bitrix** (the trial "Start" edition): `X-Powered-CMS: Bitrix Site Manager` on the home page, the `/bitrix/admin/` login form, closed `php_interface/dbconn.php`, `modules/`, `.settings.php`, `cache/`, PHP in `upload/` does not execute, a non-existent address is handled by `urlrewrite.php`, `mp site php` shows `short_open_tag On`, `max_input_vars 20000`, `memory_limit 512M`.

Admin credentials are printed once, as `CREDS` lines. What had to be dealt with while the scenario was still manual: on EL, Percona comes with `validate_password` (a database password must contain all character classes, and that is how the panel generates them); files copied with `cp -a` from `/root` keep the SELinux label `admin_home_t` on EL — `mp site fix` now repairs that, and the panel labels the files itself after unpacking; `mp db create` on an existing database does not fail but resets the password.

## What the first run found (2026-09-09)

Before the testbed, the panel had been tested only on Ubuntu 24.04. The very first round over the whole matrix turned up six bugs and the first move a seventh, and each of them reproduced only on a real OS — the test with a fake agent could not see them:

| Where | What happened | What was done |
|---|---|---|
| Ubuntu 26.04 | `ppa:ondrej/php` has no builds for resolute, and `apt update` failed with a 404 | the panel checks `dists/<codename>/Release` before adding the source, installs PHP from Ubuntu itself (8.5), marks unavailable branches in the branch list with the reason, checks the PPA again on the next install and cleans up a broken source after itself |
| EL9, EL10 | nginx did not start: `nginx -t`, which the agent uses to check the configuration, created `/run/nginx.pid` with the `var_run_t` label, and the `httpd_t` domain could not open it | the config set gained a `restore` field; after writing files and creating directories the agent runs `restorecon`; on the first install of nginx/PHP the panel sets up `fcontext` and the SELinux booleans for hosting ([02](02-platform-matrix.md#6-selinux-el9--el10)) |
| EL9 | `semanage fcontext` rejects `/run/...` because of the `/run` ↔ `/var/run` equivalence rule (on EL10 it is the other way round) | the panel follows semanage's hint |
| EL9, EL10 | Percona installs with a temporary, expired root password in `/var/log/mysqld.log`, and the `auth_socket` plugin is not loaded | the panel reads the password from the log, sets a fresh one (an expired one allows only `ALTER USER`), loads the plugin and moves root to the socket; for the three queries this takes, the password lives only in memory and is passed through the environment |
| EL (Percona) | `validate_password` MEDIUM rejected about half of the generated database passwords — a random string with no guaranteed special character; Rocky passed by chance | the `auth.NewPassword` generator guarantees every character class; it is used for database, mailbox and Roundcube passwords |
| Ubuntu 24.04 | `repo.percona.com` answered with a TLS timeout, and the whole install failed | downloads of repository keys and packages are retried on network errors |
| migration | a `caching_sha2_password` hash with a binary salt got corrupted in the text output of `SHOW CREATE USER` (`ERROR 1827`) | the source asks the server to print the hash as a hex literal |

After the fixes, a full `make testbed-matrix` run from clean snapshots is green on all machines (Ubuntu 26.04 with PHP 8.5, the rest with 8.4; nginx 1.30, Percona 8.4), and the migrations Ubuntu 24.04 → Debian 13 and Debian 12 → AlmaLinux 10 pass all checks.

Oracle Linux 9 and 10 were added on 2026-09-10 and turned up two more quirks: the Oracle images come with firewalld enabled (ssh only) — now `mp setup` opens the panel port in it, installing nginx opens 80 and 443, installing mail opens its ports, and `mp firewall enable` switches firewalld off; and `remi-release-10` requires `epel-release = 10`, which the `oracle-epel-release-el10` package does not provide — on OL10 the panel installs the official `epel-release`. After that, e2e is green on both, and the move Ubuntu 24.04 → Oracle Linux 9 passed all checks.

The testbed itself taught a few lessons as well: a cloud-init disk on `ide2` is invisible to Debian's `cloud` kernel; on EL the guest agent forbids `guest-exec` (lifted in `/etc/sysconfig/qemu-ga`), and SELinux still does not let it run commands — so on EL a machine's readiness is judged by the agent answering; `pkill -f` inside a single ssh command also kills that command itself; parallel `deploy` runs should not each build the package on their own — `matrix` builds it once.
