### Updating the panel from releases (2026-09-06)
- [x] `internal/updater`: GitHub releases (or GitHub Enterprise via `api`), chosen by version rather than by publication date; stable/beta channel; fixed artefact names (`monopanel_<v>_<arch>.deb`, `monopanel-<v>.<arch>.rpm`, `monopanel-linux-<arch>`, `SHA256SUMS`, `SHA256SUMS.sig`).
- [x] Release signature with ed25519: `scripts/release keygen|sign|verify`, the private key is a repository secret, the public one is `update.public_key` in `config.yaml` (root-only, cannot be changed from the panel). With a key set, an unsigned release is not installed; the agent verifies the signature again rather than trusting the hash from the API process.
- [x] Installing outside the panel: the agent's `POST /v1/panel/install` starts the transient unit `monopanel-update.service` (`StartTransientUnit`), which survives the restart of the API and the agent; `mp update-run` installs the copy in `/var/lib/monopanel-agent/updates` — the agent copies it out of the API's downloads and names it only once its SHA-256 matches the signed list; an older version (or a release over a later `0.8.19-N-g…` build) is refused —, restarts the units, waits for `/health` with the new version and restores the previous binary if it does not answer. The outcome is written to `<data>/updates/state.json` and goes into the audit log after the restart. Since 0.9.0 the install runs with the environment of the panel's package manager (`NEEDRESTART_MODE=l`), a retry after a rollback reinstalls the version the package database holds, and the automatic update leaves that version to an administrator.
- [x] API `GET|PUT /system/update`, `POST /system/update/check|apply` (administrator only), the `panel.update` job, a scheduled daily check and `auto_apply`; the repository token is encrypted with secretbox.
- [x] `mp update`, `mp update check|apply|settings|trust`; the "Panel update" card in the web UI's Settings waits for the restart and reloads the page; an `update` check in `mp doctor`.
- [x] Installing the latest version counts as a check in itself (2026-09-24): the `panel.update` job remembers the release it found, and after `mp update apply` the status no longer reports the release seen by the previous check as the latest.
- [x] Packages: `make packages` (deb+rpm × amd64+arm64 + binaries + SHA256SUMS), `make release VERSION=…`, the `release.yml` workflow on a `v*` tag; `preremove` no longer stops the panel during an update, `postinstall` restarts the units only on an upgrade.

### Site log rotation (2026-09-24)
- [x] Nobody rotated the logs in `/var/www/<login>/data/logs`: the panel wrote no logrotate configuration, and the distribution's configs do not cover that path. Now `/etc/logrotate.d/monopanel-sites` has a block per account with `su <login>` (the directory belongs to the client, root does nothing in it): weekly or at 100 MB, eight copies, compression from the second one, `create 0660 <login> <login>`. All of a site's logs belong to the account with mode 0660: the panel creates them before nginx, Apache and php-fpm open them, and hands over to the account the ones those daemons created earlier — via a new `mode` flag of the agent's `chown` operation, through an open file (`O_NOFOLLOW`, `fchown`, `fchmod`). Otherwise logrotate 3.18 on EL9 could not cope: when rotating it opens the log, and when compressing it opens it for writing. The file is rewritten when an account is created or removed (the removed account's entry goes before `userdel`, so that logrotate does not meet a non-existent user) and when the panel starts; before writing, it is checked with `logrotate --debug`.
- [x] nginx worker processes could not reopen the site logs after USR1 — neither after this rotation nor after nginx's own nightly rotation: `data/logs` had no traverse permission for the `monopanel-web` group, so every night `emerg … Permission denied` landed in the nginx log and writing continued into the old file. `data/logs` got the ACL `g:monopanel-web:x` on site creation and on `mp site fix`, and existing accounts got it at panel start. Apache reopens its logs with a graceful restart on USR1 via the pid file: `systemctl` called from logrotate runs into SELinux on EL.
- [x] The php-fpm slow log on EL was empty: php-fpm takes the trace via `ptrace` of the worker process, and the stock policy silently denies `httpd_t` the `sys_ptrace` capability. The panel installs its own policy module `monopanel` (CIL, `semodule -i`) with `allow httpd_t self:capability sys_ptrace` and `self:process ptrace` — together with preparing the host for hosting, and on already prepared hosts at startup, without another relabel.
- [x] Verified on Debian 13 (with Apache), Ubuntu 22.04 (logrotate 3.19), Rocky 9 (3.18) and AlmaLinux 10 in enforcing: after rotation nginx, Apache, PHP and php-fpm write to the new files, the second rotation compresses the first as the account, the slow log on EL has traces, `logrotate.service` succeeds, no SELinux denials.

### Valkey per account (2026-09-24)
- [x] `mp stack install valkey` installs Valkey from the distribution (Debian 13, Ubuntu 24.04/26.04, EL9/EL10 AppStream, Debian 12 — from backports, if they are enabled), and where it has none — Ubuntu 22.04, Debian 12 without backports — Redis (6.0 and 7.0) with the same protocol; the package's shared instance (127.0.0.1:6379 without a password, for everyone) is stopped and disabled. The server cannot be removed while there are instances on it.
- [x] An account has two separate instances: `cache` (allkeys-lru, `--save ""`) and `sessions` (volatile-lru, a snapshot every minute). Each one is `monopanel-valkey-<login>-<purpose>.service` running as the user, `Type=notify` (a restart returns once the snapshot is loaded and the socket accepts connections), `MemoryMax` at twice maxmemory for headroom, the whole configuration in the arguments (the account has no access to `/etc/monopanel`). It listens only on a unix socket with mode 600 in a 0700 directory (`RuntimeDirectory=`), snapshots go to `StateDirectory=`; `mp valkey add|list|restart|rm`, `/users/{login}/valkey[/{purpose}]`, the valkey button on the "Users" page. Removing an account takes its instances with it; migration between panels carries over their settings without the data.
- [x] A site's PHP sessions in Valkey: `mp site set <domain> --sessions valkey|files`, the "PHP sessions" field in the site settings; the pool gets `session.save_handler = redis` and the path `unix://…/valkey.sock` through php_admin_value. This needs the sessions instance and the redis extension on the site's PHP branch; while a site keeps its sessions there, neither the instance nor the extension can be removed (409); a site in proxy mode keeps no sessions.
- [x] SELinux (EL): the sockets are `redis_var_run_t`, the snapshot directories `redis_var_lib_t`, while `/var/lib/monopanel-valkey` itself stays `var_lib_t`: init_t cannot add entries to a `redis_var_lib_t` directory, and `StateDirectory=` failed with EACCES without a single AVC. The unit has no `ProtectKernelTunables=`, `ProtectKernelModules=` or `RestrictAddressFamilies=`: for a non-root `User=` they turn on NoNewPrivileges, and under it the EL9 policy does not allow the init_t → redis_t transition, so the server stayed in init_t without the right to write snapshots. Live check on Debian 13, Ubuntu 22.04, AlmaLinux 10 and Rocky 9 (enforcing): another account and the web server get "Permission denied", a PHP session through php-fpm survives a restart, no AVCs.

### After moving an Aspro/1C-Bitrix site (2026-09-26)
- [x] SFTP: creating a site and `mp site fix` handed an SFTP-only account's home to the client, and sshd refused the chrooted login. The home is always `root:<login> 0750` for SFTP-only and `<login>:<login> 0710` for a shell account now — one rule for creating the account, the site and the fix. Homes already broken are repaired at the panel's startup, and an `r-x` group ACL entry lets the client see the root of its chroot (chmod leaves that entry alone when ACLs exist).
- [x] ACLs: `mp site fix` recalculated the mask over all group entries, and files inherit a `group::r-x` entry from their directory — the mask gained x and files turned 650/654. The agent now walks the tree itself (not following symlinks) and sets the files' mask explicitly: read for the web group, x only where the owner has it, the group entry kept.
- [x] Sessions in Valkey: phpredis does not lock the session by default, and parallel AJAX requests of one visitor overwrote each other's changes. For sites with sessions in Valkey the panel sets `redis.session.locking_enabled = 1`, `lock_retries = -1` (wait like a file lock; the lock itself expires after `max_execution_time`), and the `redis.session.*` keys can be changed among the site's and the global PHP settings.
- [x] MySQL settings in the panel: `GET|PUT /db/engine/config`, `mp db config [set k=v|unset k]`, a card on the Databases page. The panel's values are sized for the host's memory, a value set takes their place in `zz-monopanel.cnf`; `mysqld --validate-config` runs before the restart (a refused file leaves the running server alone), and the previous settings come back if the server does not start. What the check lets through and the server then fails on is refused by the panel itself: `default_time_zone` only as an offset or SYSTEM, `innodb_buffer_pool_size` no larger than the host's memory.
- [x] Send-only mail domains: another server receives the mail (MX at a provider), this one signs with DKIM and sends the sites' mail. The domain is not in postfix's receiving maps, so a site's letter to an address of the same domain goes to the real MX. Such a domain has no mailboxes or aliases; the DNS hints do not ask for the MX to point here and suggest adding this server to the provider's SPF instead of replacing it.

### An Apache per account (2026-11-21)

### Only nginx talks to an account's Apache (2026-11-21)
- [x] Any local process could reach an account's Apache directly and bypass the site's `--allow` list, rate limit and client address. The agent refuses an nginx location that proxies to an account's Apache without the secret, and files of an account's Apache that would switch the check off ([03 §4](03-web-stack.md#4-apache-template-mode-b)).
- [x] Apaches set up without the secret by 0.9.0's development builds, stopped ones included, the panel switches to it once (job `apache.backend`): nginx starts sending it for every site of the account first, then the Apache starts demanding it, with no 403. `monopanel-apache@` stops gracefully (SIGWINCH, up to 60 s for the requests in flight); `mp doctor` warns about an `apache2.service` that is off but enabled at boot.

### php-fpm and nginx: requests to the sites' pools only (2026-11-21)

### Site logs outside the homes (2026-11-21)
- [x] Root through the site logs: the nginx master opens its logs as root at start, reload and USR1 (and when it reopens them it also changes their owner by name), so does the Apache master, the php-fpm master opens the slow log on every write — and the logs lived in the account's `data/logs`, the client's own directory inside its own `data/`. By swapping a log for a symlink to `/etc/ld.so.preload` or `/etc/cron.d/x`, the client or PHP code of its site got a root write there with partly its own content (the request line, a script path) — the CVE-2016-1247 class. Now the site logs, the PHP error log and the logs of the webmail on its port live in `/var/log/monopanel/sites/<login>/`: `sites/` is `root:root` 0711, the account's directory `root:<login>` 0751, the servers' logs `root:<login>` 0640, the PHP error log `<login>:<login>` 0660. A new agent operation, `sitelogs/ensure`, makes them: it walks the tree through opened directories without symlinks, refuses a directory anyone but root may write to, and decides by the name whose file it is. The client reads its logs through its group, the panel and `mp site logs` through the agent.
- [x] logrotate rotates that tree as root, without `su`: a block for the servers' logs (`create 0640 root <login>`) and a block for the PHP error logs (`create 0660 <login> <login>`). Instead of `*.error.log` the first block has four masks: logrotate refuses a file that two blocks name.
- [x] An upgraded panel makes the accounts' directories and logs at its first start and re-applies the sites whose configuration writes the logs into `data/logs` (`site.apply`, and `mail.apply` for the webmail on its own port) until each has applied (see "The upgrade's moves" below); the old files in `data/logs` stay with the client, and `data/logs` is no longer created. On EL, before the sites switch, the `fcontext` rule `/var/log/monopanel/sites(/.*)?` → `httpd_log_t` is added and the tree relabelled. `/var/log/monopanel` is `root:monopanel` 1771 now — a way through for the accounts and the nginx worker processes, and the sticky bit keeps the API from renaming root's entries. Deleting an account with `purge` removes its logs too (`sitelogs/remove`).
- [x] The agent's `file/read` no longer reads files in the homes, and in `/var/log/monopanel`, which the API may write to as well, only through directories without symlinks and only files with a single name.
- [x] Directories where root acts by name. `/run/monopanel/php` (the php-fpm master removes, creates and hands over sockets by path) was made only by API jobs, and the API may write to `run_dir`. A compromised API could make `php/` its own and swap a socket for a symlink between bind and chown: a root chown and ACL of any file. Now `php/` is root's from boot (the package's and `mp setup`'s tmpfiles). At its start the agent makes `php/` and `sites/` root's, takes over others' and clears what does not belong. Before starting, restarting or reloading php-fpm, nginx and Apache, before their configuration checks, before it installs, upgrades or removes packages and before the mail installation's `dnf install` on EL, it refuses while the site log tree is not root's alone, and for php-fpm and the packages also while `php/` is not. If the clearing at the start fails, the rest of the tree is still cleared; the refusals for the site log tree hold until it is cleared (the agent tries again before each such action), while `php/` only has to be root's alone. Site logs go only right in an account's directory. The API writes no tmpfiles lines any more: `/etc/tmpfiles.d` is off the allow-list, confcheck accepts the panel's line alone, and the `systemd-tmpfiles-*` units only report their state.

### The agent binds the shared folders (2026-11-22)

### Job races (2026-11-22)
- [x] `sites.move-ip` moves each site under its lock and writes the address alone (an error status goes back to pending). A `mp site set` change made during the move is no longer lost, a `site.apply` no longer writes a site's block between its removal and the move, and sites deleted or being deleted are neither moved nor applied. The webmail's block on its port goes with its site's block and is written again on the new address: it used to stay listening on the lost address, and the move failed nginx's check on it.
- [x] Site changes write only what they change: `mp site set`, a CMS install (its record at the end, minutes after it read the site), suspending and resuming, ordering a site's certificate and attaching an issued one no longer put back an address `mp site move-ip` gave the site meanwhile, nor lose a change of another setting made beside them (an alias added to a site that had none included); taking a failed site back to pending no longer lifts a suspension made at that moment. A site whose removal — its own or its account's — is under way takes no more changes: `mp site set`, `apply`, `suspend`, `unsuspend`, `fix`, `mp site nginx`, ordering its certificate and a CMS install are refused (409) instead of being answered as accepted; a removal asked for while such a change is under way is caught when the change is written, and the change does not go in. `mp site nginx --set/--clear` waits for a CMS install running in that site to end. Two changes of one list setting at once (aliases, `--ini`, `--allow`) still end with the later one.
- [x] The mail settings change one at a time: `mp mail settings`, `mp mail install` run again and a `mail.apply` that notices another dovecot write their part over the settings as they are by then — a change made meanwhile, and a webmail taken out along with its site, no longer come back. Mail changes are rendered one at a time: each writes the postfix and dovecot files and the webmail's block on its port from the settings as they are when its turn comes, and one made while another renders is no longer written over by it.
- [x] The webmail installs under its site's lock and reads the site and its owner again first. A deletion of the site or its account asked for earlier stops it before it changes anything; one asked for later waits for it. A site's deletion takes the webmail out of the settings (and the tree with `--purge`); an account's deletion also drops the `<login>_roundcube` database with its MySQL account. Deleting the webmail's site takes its block on the port and its entry in the mail settings; `mp mail apply` no longer fails on a webmail site an older version deleted. The webmail is no longer unpacked over a CMS installed into the same site while it downloaded: it refuses, as for any site that holds files of its own ([06 §10](06-mail.md#10-webmail)).
- [x] A CMS install and the removal of its site's account no longer run side by side: the removal waits for the install to end and then takes everything it made (the files, the database and its MySQL account); an install whose job starts once the removal of the site or the account was asked for stops without making anything. A removal of a site or an account, and a CMS install, that waits in the queue no longer reaches another site or account made while it waited.
- [x] An in-place restore does not write into the home of an account or the tree of a site being deleted, and the deletion of an account or a site is refused (409) while such a restore is queued or running — in whichever order they are asked for, even at the same moment. An account whose removal was asked for takes no more changes: `mp user set` is refused (409), so neither a status change nor a provisioning job queued before the removal lifts its mark. A refusal means nothing changed, the password included. A removal broken off by a restart of the panel goes on after the start with the same mark.
- [x] `mp user set` writes only what it changes: a change of the password or the e-mail no longer undoes a suspension (or its end) made at the same moment, nor puts an account its provisioning job activated meanwhile back to pending; the answer shows the account as stored. Provisioning no longer lifts a suspension: a suspended account stays suspended after a switch of its shell (`--shell`/`--sftp-only`), `mp user set … --shell --status suspended` ends suspended, and an account suspended while it is moved from another panel stays suspended after the move.
- [x] Job time limits by type: a backup 8 h, a restore 7 h, a migration a day (every other job an hour); while long jobs hold every worker, one more takes the other jobs, and the automatic update waits for them; the doctor's jobs line counts the day from the failure and forgets a failure whose object went — the webmail's site, or the account it was asked for while no site of that name is there — when the removal was queued after the job or ended after it started; a site's removal no longer logs an empty list, files kept in a tree that is gone, nor files kept that the account's purge takes along.
- [x] The jobs line: a `user.delete` that went through clears the failures of the sites deleted along with the account too; a `site.apply` or `site.delete` of a site already deleted ends done; a `user.delete` no longer fails when a site of the account was deleted meanwhile by its own `site.delete`.

### Mail policy (2026-11-22)
- [x] No account sends mail as another account's domain: the milter `monopanel-mailpolicy` (the same binary, a user of its own without privileges, a socket systemd holds) answers postfix before opendkim and refuses a message whose envelope or From is in another account's domain (550 5.7.1); it checks mailboxes on 587/465, sendmail by the sender's uid and SMTP from the server's addresses by the socket's uid; while the policy does not answer, mail waits (`default_action=tempfail`). Before 0.9.0 such a message left, and opendkim signed it with the other domain's key. On EL `monopanel-mailguard` closes the milter ports 8890 and 8891 to everyone but root and postfix. Sieve redirects leave with the forwarding mailbox as envelope sender, vacation replies with the mailbox; a mail domain cannot be taken as a site or an alias of another account; opendkim's `TrustedHosts` are the server's addresses only. The `mail policy` line of `mp doctor`; on a downgrade below 0.9.0 the package's script takes the policy out of `main.cf` ([06 §11](06-mail.md#11-mail-policy)).

## Risks and how they are addressed

| Risk | Mitigation |
|---|---|
| Sury/Remi disappear or break compatibility | Stage 2: own builds and repository; OS Profile allows keeping both sources at once |
| MySQL 9.x removes `mysql_native_password` | We stay on 8.4 LTS until 2032; for legacy PHP — 8.4 only; upgrading to 9.x is a manual procedure |
| A new OS release without packages from the component developers | Support is announced only after the matrix passes; a weekly check is planned |
| Manual config edits by the administrator | Include directories, `confhistory`, `mp doctor` shows drift, `mp site apply` regenerates the site |
| Compromise of the web layer | api without privileges; agent with an allow-list; helper with setuid; secrets are encrypted |
| Growth in the number of sites (hundreds) | `pm=ondemand`, one master per version, SQLite with WAL holds tens of thousands of entities; metrics are stored as aggregates |
