# 10. Shared folders: a contractor's access to one folder of a site

A common request: "give the contractor (an exchange service, the accountants, an agency) SFTP access to one folder of our site". The first idea is to create a user with its home directory inside the site. In MonoPanel that is neither needed nor possible:

- sshd chroots an SFTP user into its home and insists that the directory is owned by root and not writable by the group or others. A site folder belongs to the site owner, and if root took it, the site itself could not write there.
- The panel expects every account's home at `/var/www/<login>` with `data/www`, logs, tmp and the web server's ACLs. A foreign path in `home` sooner or later breaks `mp site fix`, backups or a migration.
- One unix user per account and a `0710` home is what keeps clients apart.

Instead the panel hands out a **shared folder**: the guest stays an ordinary account with its own home, and the panel's agent mounts the site folder inside its chroot (for a guest with a shell, in `/var/www/.shares`, with a symlink in its home). After signing in the guest sees only that folder (and its own empty `data`), both sides and the web server read and write the files, and the site can be told never to execute PHP from the folder.

## 1. How it works

On `mp user share add` the panel:

1. creates the folder inside the site's docroot (if missing) — owned by the site owner, mode `2770`, setgid keeps the owner's group on new files;
2. sets ACLs on the folder: `rwx` for the guest and the owner, `r-x` for the web group, inherited by everything created inside;
3. makes a root-owned mount point. For an SFTP-only guest it lies in the guest's home (`/var/www/<guest>/<name>`): the home is root's anyway — the chroot stays root-owned, sshd is happy. A guest with a shell owns its home, so the folder is mounted in `/var/www/.shares/<guest>/<name>` (`.shares` root 0711, `.shares/<guest>` root:<guest> 0750, the mount point root 0755), and the home gets the symlink `/var/www/<guest>/<name>` pointing there;
4. the agent binds the folder there itself: it opens it from the web root one directory at a time without following any symlink, checks that it is a directory of the site owner's in the owner's home (not in `.restore` or `.shares`) and that no mount point right in the owner's home lies on the way (that is where shared folders given to the owner as a guest lie), and mounts the very directory it opened — in the host's mount namespace, not in its own, where nobody would see the mount. The mount has a peer group of its own: whatever the guest mounts inside the folder (`fusermount` in a directory of its own there, say) stays the guest's and does not show up in the site's tree. The agent records every folder in `/var/lib/monopanel-agent/shares/` (a file per mount point, root's alone). There is no systemd unit: nothing mounts the folders at boot; the panel binds them again at its start;
5. with `--no-php` adds a `location` to the site configuration that answers 403 to any `.php`, `.phtml` or `.phar` in the folder; for a site in apache mode the account's Apache also reads no `.htaccess` in it (otherwise the guest could hand a file of any name to PHP or switch off the owner check of symlinks), runs no PHP from it — also for a request that goes past nginx — and follows a symlink in it only to a file of the link's own owner. A `.htaccess` in such a folder has no effect, as in php-fpm mode;
6. with `--entry` writes a `Match User <guest> Group monopanel-sftp` block with `internal-sftp -d /<name>` into the sshd drop-in: the SFTP session starts right inside the folder rather than at the chroot root. The block applies to accounts without a shell only.

Why. A path is resolved again whenever it is used and follows symlinks. So the mount point lies only below directories of root's that nobody else may write to (the ACL mask and the entries it holds back now counted), with no symlink on the way — otherwise a guest renaming an entry in its own home could have the folder bound over `/etc/systemd/system`; any other mount point the agent refuses (403). The folder, though, lies in its owner's tree. Before 0.9.0 a systemd unit mounted it by its `What=` path — at boot and at every start of the unit — and an owner who swapped the folder (or a directory above it) for a symlink would have shown another account's home, `/var/lib/monopanel-agent/restore` or the staging of an in-place restore in `/var/www/.restore` in the guest's chroot. So the agent mounts the folder from the descriptor it opened and checked itself: a folder that is a symlink, one with a symlink on the way, someone else's, one in `.restore`, in `.shares` or below another shared folder's mount point is refused (403, with why), and a swap during the bind changes nothing — the guest sees the directory that was checked. The agent tells another shared folder's mount point on the way even when its records do not know of it yet, or any more (the walk to the folder runs before the shared folders' lock): the directory right below the owner's home on the way to the folder must lie on the home's own mount — that is the only place in a home where shared folders' mount points lie. On `data` (the way to any folder of a site goes through it) no such mount point ever lies — the panel gives no shared folder that name, and the agent binds only on directories of root's — so mounts on `data` and deeper down — an administrator's volume or ZFS dataset for an account's or a site's files, the owner's own FUSE mount — do not trouble this check. So is a folder whose guest or owner does not pass the check of a panel account — the rules of an account's own units: a uid of `UID_MIN` or more, a home below the web root, a primary group of its own and no system or privileged group among the others (`users`, `sudo`, `wheel`, `adm`, `docker`, `lxd`, `disk` and the like). While the agent knows a shared folder (its records in `/var/lib/monopanel-agent/shares/`), no operation of the agent hands a directory on the way to its mount point to an account, makes it writable, removes it or puts something else in its place: a home that holds a mount point is not handed to its account (409 "remove or move the shared folders of <login> first").

There is no way out of the chroot of an SFTP-only guest: symlinks pointing outside do not resolve inside the chroot, `../` stops at the guest's home. A guest with a shell moves around the server with its account's rights anyway; to it the folder is one more directory, behind a symlink in its home. On EL the site's SELinux labels are kept; nothing extra to set up.

Switching a guest between a shell and SFTP-only moves its folders within the same job (`user.provision`): out of the home before the home becomes the account's, back into it after it is root's again.

A folder in use (a session with its working directory inside) cannot be unmounted (`mp user share rm` gets 409 "it is in use"). For an SFTP-only guest such a folder blocks the removal of the folder, of the site or of the guest, and the switch to a shell: end the guest's sessions (`loginctl terminate-user <guest>`) and try again. When the folder of a guest being switched to SFTP-only is in use, the switch goes through and the folder stays in `.shares`: a warning in the job's log, the error of the last apply on the folder (in the list of folders; `status: failed` in the JSON). For a guest with a shell whose folder still sits in its home (where a panel up to 0.8.19 left it), the agent removes a unit the older panel left even while the folder is in use — nothing mounts it there again —, the folder gets the same error, and the move finishes once the folder is free. Either way the panel tries again at its next start or with `mp site fix <domain>` (the domain of the folder's site); the empty old mount point in the home gives way to the symlink. While an extraction, an in-place restore or another long walk of a tree below the web root (the owner and ACL change over a site in `mp site fix`, say) holds the shared folders' lock, giving a folder and taking it away wait up to 30 seconds and then get 503 — try again once it is done; 502 means the agent is down or the operation itself failed.

Folders the panel's database does not have. The agent remembers every folder it bound (a record in `/var/lib/monopanel-agent/shares/`), and while the record is there the way to its mount point stays root's (409 "remove or move the shared folders of <login> first"). When the panel's database no longer has such a folder — it was restored from a copy made before the folder was given, say — the panel unbinds it through the agent at its start, removes the record and the empty mount point (in `.shares` also the guest's directory once it is empty) and logs "a shared folder the panel no longer knows was unbound" in the `monopanel-api` journal. The symlink in the home of a guest with a shell stays and leads nowhere; the guest removes it. A folder in use stays, and the panel tries again at its next start; until then the "shared folders" line of `mp doctor` names it: "… kept by the agent that no shared folder of the panel names — <mount point>: in use". End the sessions that hold it (`loginctl terminate-user <guest>`) and restart the panel: `systemctl restart monopanel-api`. When the database has a share with that mount point but the agent's record names another directory (the name was given again after that copy of the database was made, the site's docroot changed), the panel binds the database's folder there at its start — the old one is taken off, in use or not — and logs "a shared folder showed another folder than its share's: the share's own is bound there now"; until the database's folder is bound, the "shared folders" line of `mp doctor` names the share: "<name> of <guest> (<site>/<path>): another folder is mounted there, <directory>", and `mp site fix <domain>` binds it again.

Boot and the panel's start. Between boot and the API's start no shared folder is mounted. At every start of its own the panel binds every folder that is not in place (after a reboot, all of them), moves the folders out of the homes of guests with a shell into `/var/www/.shares/<guest>/<name>`, with a symlink in the home, applies again a folder whose last apply failed, and unbinds and forgets the agent's records that no shared folder of its database names (as after a restore of the panel's database from a backup). A folder the agent refused to bind shows: its status is `failed` with why (`mp user share list --json`, the "folders" button on the Users page), and the "shared folders" line of `mp doctor` names it — "K of N not mounted — <name> of <guest> (<domain>/<path>): <why>". Fix the cause (put the real directory back in the folder's place, take the account out of the system group) and run `mp site fix <domain>`, which binds the site's folders again; the panel's next start does the same. After a site's docroot changes, its shared folders move to the new docroot the same way — at the panel's next start or with `mp site fix`.

A guest that was added to a system group (`users`, `video` and the like) or to a privileged one (`sudo`, `wheel`, `docker`…) after its folders were given no longer counts as a panel account for the agent: no new folder is bound for it (the error names the group), and after a reboot its folders stay unbound (`failed`). They can always be taken away, as can the folder of an owner that fails the check: `mp user share rm` and `mp user rm` unbind a folder the agent has a record of (or an older version's unit in the panel's form) without the account check, and a share the agent keeps nothing of — it refused to bind it (after a restore of the panel's database, say, or once the guest's system account is gone) — the panel simply forgets without asking the agent; a failed attempt to give such a guest a new folder leaves no empty mount point behind either. The exception is a folder mounted without a record of the agent's (early development builds of 0.9.0 left such): the agent does not unbind it for such a guest; take the guest out of the group, or unmount the folder by hand (`umount <mount point>`). `mp user rm` does not remove an account in a privileged group itself — the agent refuses; take it out of the group (`gpasswd -d <guest> sudo`) and run it again.

Upgrading from 0.8.19 and from early development builds of 0.9.0: as it starts, the agent takes over the shared folders' mount units the older versions wrote. It first records every folder (in `/var/lib/monopanel-agent/shares/`). Then it checks what is mounted: a mount that does not show the folder (systemd mounted it by path, through the owner's symlink), or shows a folder the agent would refuse now, is taken off at once, in use or not. Only then does it disable and remove the units (`daemon-reload`). A unit that could not be removed stays recorded, and the agent checks what it mounted again at its next start; a check that does not end within 10 seconds (an NFS server with the homes gone, say) leaves only that mount as it is. A mount it could not take off the agent names in its journal: take it off yourself (`umount -l <mount point>`) and run `mp site fix <domain>`. A unit with the panel's header (`# Generated by MonoPanel: shared folder of …`) is taken over even when its guest or owner no longer passes the panel's account check (a member of a system group such as `users`, or of `sudo`). The agent binds no such folder: what the unit mounted is taken off at once when the owner fails the check, while the folder of a guest that fails it, mounted where it belongs, stays so until a reboot; once the panel tries to bind such a folder again (at its start, when the folder is not in place, or with `mp site fix`), its status is `failed` with why. A unit not in the panel's form stays, and the agent warns about it ([§4](#4-what-not-to-do)).

## 2. Step by step

Example: the site `vstrade.kz` of the account `bitrix`; the contractor needs the folder `kaspy` for file exchange.

**Step 1. The guest.** If the contractor has no account yet, create one without a shell — SFTP is enough:

```bash
mp user add userkaspy --generate        # the password is printed once
```

The password is for SFTP (and for the panel, where the guest sees only its own folders).

**Step 2. The folder.** Hand out the site folder. The path is relative to the site's docroot; the folder is created if missing:

```bash
mp user share add userkaspy --site vstrade.kz --path kaspy --no-php --entry
```

Keep `--no-php` whenever the folder is for files rather than code: without it the contractor could drop a `.php` there and the site would execute it as the `bitrix` account — with all the site's rights. `--name` sets the folder name in the guest's home when it should differ from the last path segment.

`--entry` makes the folder the entry point: after connecting the contractor lands straight in `kaspy`, as if it were the home directory. Without the flag the session starts in the home, where `data` and `kaspy` are visible. The entry point can be set later, and taken back:

```bash
mp user share entry userkaspy kaspy        # sign in straight into kaspy
mp user share entry userkaspy kaspy --off  # in the home again
```

An account has one entry point: setting a new one clears the previous. An account with a shell gets none — it goes wherever it likes anyway.

**Step 3. Check.**

```bash
mp user share list userkaspy
```

The `MOUNTED` column should say `yes`, `PHP` — `denied`, `ENTRY` — `yes`. `IN HOME` is the folder's path in the guest's home (a symlink for a guest with a shell); where it is really mounted, `--json` gives as `mount_point`. The contractor connects over SFTP as `userkaspy` with the password from step 1 and lands straight in the folder `kaspy` — that is the site's `/var/www/bitrix/data/www/vstrade.kz/kaspy`. One level up is the home with an empty `data`; there is no way further. On the server `findmnt /var/www/userkaspy/kaspy` shows the mount (source `…[/var/www/bitrix/data/www/vstrade.kz/kaspy]`) and `mp doctor` a "shared folders" line with "N mounted".

The same in the web UI: Users → the "folders" button on the account → site, folder, the "no PHP" and "entry point" boxes → Add. The "entry point" button in the table sets and clears it on a folder already handed out.

**Step 4. When the access is no longer needed.**

```bash
mp user share rm userkaspy kaspy
```

The agent unmounts the folder and forgets it, the guest's ACLs are dropped, the PHP denial leaves the site configuration and the entry point leaves the sshd drop-in; for a guest with a shell the symlink in its home goes too, and so does its directory in `.shares` once no folder is left in it. The files stay in the site folder. Deleting the guest account (`mp user rm`) or the site does the same by itself.

## 3. File permissions

- Everything the guest creates belongs to the guest, everything the site creates to the site owner; thanks to the inherited ACLs both sides read each other's files and nginx serves them to visitors.
- A file uploaded over SFTP with mode `0644` (the way clients usually upload) can be read and deleted by the other side but not rewritten in place: the ACL mask limits the rights to the file's group bits. For a "drop it — they pick it up" exchange that is enough. If both sides need to edit each other's files in place, `mp site fix <domain>` recalculates the masks of everything already in the folder.
- `mp site fix` knows about shared folders: after recalculating the ACLs of the whole site tree it restores the guests' entries. It no longer resets the folder's owner and mode through its mounted mount point: before 0.9.0 it left the folder root:root 0755, and neither the guest nor the owner could write to it.
- A panel-to-panel migration does not carry shared folders: the files travel with the site, and the guest gets the folder on the new server with the same command. A guest with a shell finds no symlink to the folder in its home: the migration stream leaves out a symlink that leads from the home to `/var/www/.shares` (the job's log mentions it).
- A server backup reads `/var/www` with its mount points, so a shared folder's content lands in the snapshot a second time — in the home of an SFTP-only guest or in `/var/www/.shares`. An in-place restore leaves the mount points and the way to them alone: the folder comes back with its site. While one runs — from `restic restore` to the end of the merge — no shared folder is bound or unbound: a change of a shared folder waits for it up to 30 seconds and then is refused with 503, "a shared folder cannot be bound or unbound now" (try again once the restore is done). A restore — in place or aside — brings back no device file, FIFO, socket or set-user-ID / set-group-ID file: a snapshot with such a node in the paths chosen the agent refuses by its listing, before restic writes anything — the restore job fails, naming the first such node; choose the paths without it (`--include`). Set-group-ID directories (such as the shared folder itself, `2770`) are restored.

## 4. What not to do

- Do not change the guest's `home` by hand in `/etc/passwd` — see the top of this page.
- Do not hand out a folder without `--no-php` to someone you would not trust to write code as the site.
- Do not hand out the whole docroot: the guest would get write access to the entire site, `bitrix/` and `.settings.php` included. Someone who edits the site itself needs an account with access to the site, not a guest.
- Do not change the owner, mode or ACL of a guest's home or of `/var/www/.shares` by hand: while a shared folder exists the agent refuses such changes (409), and it binds no folder whose way to the mount point is no longer root's. When the check complains about ACL entries the mask holds back, `setfacl -b <directory>` clears them.
- Do not bind-mount anything yourself (your own units, fstab) below directories that accounts own: the same race — systemd mounts it by path, and mount(8) follows symlinks. The agent never starts, restarts, reloads or enables a mount unit of yours below the web root (`mp service`, the Services page: 403 — use `systemctl`), answers a chown or an ACL change over a tree that holds its mount point with 409 (so `mp site fix` fails for that site), and warns at its start about units not in the panel's form. A volume of your own at `<home>/data` or deeper down, for an account's or a site's files, is no hindrance to shared folders ([§1](#1-how-it-works)).
