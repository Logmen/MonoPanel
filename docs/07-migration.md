# 07. Перенос между панелями

> Проектный документ. Реализованы прямой перенос между двумя MonoPanel и адаптеры для BitrixVM и FASTPANEL (`mp migrate`, страница «Перенос» в Web UI и раздел «Перенос» в TUI); пакет-файл и остальные адаптеры описаны здесь как проект. Что работает — в [README](../README.md) и отметках [x] в [05-roadmap.md](05-roadmap.md).

Задача звучит просто: «перевезти сайт (аккаунт, сервер) сюда» — и чтобы человек нажал одну кнопку. Внутри это три разные задачи, и путать их нельзя: **переезд между двумя MonoPanel**, **приём сервера с чужой панелью** и **приём сервера без панели вообще**. Общий у них только формат посылки; собирают её разные руки.

## 1. Что переносим

Единица переноса — **аккаунт**: пользователь и всё, что ему принадлежит. Сайт — подмножество аккаунта, сервер — набор аккаунтов плюс серверные настройки.

| Область | Что внутри |
|---|---|
| `user:<login>` | аккаунт панели, unix-пользователь, домашний каталог, сайты, базы, cron, app-сервисы, экземпляры Valkey (настройки, без данных), почтовые домены и ящики, сертификаты |
| `site:<domain>` | один сайт с файлами, базой (если она одна и его), cron-заданиями, которые его упоминают, сертификатом |
| `server` | все аккаунты + firewall, real-ip, DNS-провайдеры, настройки почты, ветки PHP |

Не переносим: сам сервер (ОС, ядро, сеть), правки в `/etc` мимо панели, метрики и журнал задач, сессии и API-токены (их выпускают заново), бэкап-цели с их паролями от репозиториев, общие папки между аккаунтами (файлы приезжают с сайтом, а выдать папку гостю заново — `mp user share add`).

## 2. Пакет переезда (проект)

Один архив, который сам описывает своё содержимое. Он же годится, чтобы поднять новый сервер из ничего. Сейчас данные едут напрямую между панелями (см. §5); пакет-файл ещё не реализован.

```
manifest.json          формат, версия панели-источника, область, время, sha256 каждого файла
state/
  users.json           логин, роль, argon2id-хеш пароля панели, uid/gid, shell, квота, shadow-хеш unix-пароля
  sites.json           домен, алиасы, режим, PHP, docroot, php_ini, preset, allow_from, где PHP держит сессии, свои nginx-директивы
  databases.json       базы и аккаунты со строкой аутентификации из SHOW CREATE USER
  cron.json            расписания и команды
  apps.json            app-сервисы: команда, workdir, env
  valkey.json          экземпляры Valkey: назначение (cache, sessions) и память — без данных
  mail.json            домены, ящики (bcrypt), алиасы, ключи DKIM
  certificates.json    имена, тип, автопродление
files/                 домашние каталоги
dumps/                 mysqldump на каждую базу
certs/                 fullchain и ключ действующих сертификатов
```

**Пароли переезжают хешами, а не текстом.** Панельный пароль — argon2id прямо из строки БД; unix-пароль — хеш из shadow и `chpasswd -e` на другой стороне; MySQL — `IDENTIFIED WITH ... AS '<хеш>'`, который отдаёт `SHOW CREATE USER`; почтовый ящик — тот же `{BLF-CRYPT}`, что лежит в passwd-файле dovecot. Никто не вводит пароли заново, пользователи не замечают переезда, а панель нигде не видит открытый текст.

Исключение — то, что зашифровано ключом исходной панели: приватные ключи DKIM, секреты TOTP, токен репозитория обновлений. Это перешифровывается при сборке пакета, поэтому **пакет всегда зашифрован**: либо парольной фразой, которую человек переносит сам, либо публичным ключом целевой панели (при прямом переносе он известен).

## 3. Как пакет попадает на новый сервер

**Панель → панель, по требованию** (работает). На источнике администратор разрешает переезд и получает одноразовый токен с областью и сроком жизни (`mp migrate grant user:alex` или «Перенос» → «Отдать аккаунт» в Web UI). На целевой панели — разбор и перенос: адрес, токен, что взять. Дальше **цель тянет данные сама**: у неё свободнее ресурсы, она знает своё состояние и может докачать прерванное. Источник при этом только отдаёт поток и пишет в audit, кто и что забрал.

**Файлом** (планируется). `mp migrate export --scope user:alex --out alex.mp` → скопировать → `mp migrate import alex.mp`. Будет работать всегда, в том числе когда исходный сервер уже не поднимается, а остались только бэкапы.

**Через репозиторий restic** (планируется). Экспорт кладёт `state/` рядом со снимком существующей бэкап-цели, импорт читает оттуда. Почти бесплатно — вся машинерия уже есть — и заодно закрывает «восстановить сервер целиком на новом железе».

## 4. Порядок переезда

Переезд ломается не на копировании, а на переключении DNS: пока запись смотрит на старый сервер, новый нельзя ни проверить браузером, ни получить для него сертификат по HTTP-01. Поэтому импорт задуман не как одно действие, а как четыре; сейчас работают первые два (см. §5), досинхронизация и завершение — планируются.

1. **Разбор** (`mp migrate plan`, в Web UI — «Проверить»). Цель отвечает отчётом до того, как что-то создаст: что приедет и сколько весит, что конфликтует (логин занят, домен уже обслуживается, база с таким именем есть), чего не хватает (nginx или Apache не установлены, ветка PHP не установлена, MySQL нет, мало места), что не переносится совсем.
2. **Копия** (`mp migrate run`, в Web UI — «Перенести аккаунт»). Задача создаёт аккаунт, кладёт файлы, поднимает базы, применяет состояние. Сайт поднимается сразу, но DNS на него ещё не переключён — страница «Перенос» показывает готовую команду `curl --resolve` и строку для `hosts`, чтобы посмотреть его глазами.
3. **Досинхронизация** (планируется). `mp migrate resync` проходит только по изменившемуся: файлы по времени и размеру, свежие дампы. Делается прямо перед переключением DNS и занимает минуты вместо часов — сайт на старом сервере всё это время работает.
4. **Переключение** (планируется). Человек меняет DNS, затем `mp migrate finish`: панель ждёт, пока имя начнёт резолвиться на неё, заказывает ACME-сертификаты (до этого работает перевезённый сертификат, поэтому HTTPS не рвётся ни на секунду), и по явной команде ставит сайты на источнике в suspend. Пока этого шага нет, DNS переключают вручную, а сертификат сайту без него заказывают `mp ssl issue <домен>`.

Ничего на источнике не удаляется автоматически. Единственное, что импорт делает с чужим сервером, — читает.

## 5. Что уже работает

Прямой перенос между двумя MonoPanel: `mp migrate grant` на источнике, `mp migrate plan` и `mp migrate run` на приёмнике — или то же на странице «Перенос» в Web UI ([09](09-web-ui.md#перенос)). На старой панели вкладка «Отдать аккаунт» выдаёт токен на выбранный аккаунт и срок от 1 до 168 часов и показывает адрес панели, токен (один раз) и готовую строку `mp migrate plan …`; ниже — токены переноса, которые выдал этот администратор: до какого времени действует, пользовалась ли им уже новая панель, и кнопка отзыва. На новой панели, на вкладке «Принять аккаунт», выбирают источник — MonoPanel, FASTPANEL или BitrixVM; вставленная в поле адреса строка `mp migrate plan …` заполняет форму сама, ключ ssh вставляют текстом или из файла. «Проверить» показывает разбор: что мешает — со ссылкой на страницу, где это исправляют, — предупреждения, заметки источника, отпечаток ключа его ssh-хоста и всё, что приедет, по разделам. «Перенести аккаунт» ставит задачу; API перед этим разбирает источник ещё раз и отказывает (409), если за это время что-то стало мешать. Перенос, начатый раньше, страница показывает снова, с журналом задачи.

Источник **только читает**: он отдаёт состояние (`/migrate/plan` без секретов, `/migrate/state` с хешами и ключами) и два потока — `/migrate/files` (tar домашнего каталога или Maildir) и `/migrate/dump` (mysqldump). Ничего не меняется даже в его собственной базе, кроме записей в audit о том, кто и что забрал (выдача токена, состояние, каждый поток файлов и каждый дамп — отдельной записью), и отметки, когда токеном пользовались в последний раз.

Токен переезда выдаётся с областью `migrate:user:<логин>` и сроком жизни. Он **ограниченный**: пускает только на GET под `/migrate` и только для своего аккаунта; на `/users` тем же токеном приходит 403. Такая область открывает хеши паролей, ключи, файлы и базы аккаунта, поэтому бывает только у токенов администраторов: обычный аккаунт не может записать её в свой токен (`POST /tokens` отвечает 403), администратор — в токен, который выпускает обычному аккаунту, а обработчики `/migrate` требуют роль администратора, какая бы область ни стояла в токене. Токены обычных аккаунтов с такой областью, выпущенные до этого правила, панель отзывает при старте и пишет об этом в audit. Остальные области панель по-прежнему считает пометками — токены, выпущенные раньше, работают как работали.

У `mp migrate plan|run` флаги `--token` и `--insecure` относятся к источнику; свой токен и проверку сертификата для `--server` команда берёт из окружения (`MP_TOKEN`, `MP_INSECURE=1`). Токен источника можно передать и на stdin (`--token-stdin`), пароль ssh чужой панели — `--password-stdin`. В консоли Web UI перенос с MonoPanel работает так же — набранный там `--token` команда получает на stdin, а не в командной строке; для чужих панелей консоль не годится: ключ из файла (`--key`) она не читает, а пароль на stdin передать не может, — их вводят на странице «Перенос».

Потоки идут насквозь: `tar -c` на источнике → HTTPS → `tar -x` здесь, между ними ничего не складывается на диск. Для этого у агента появились две операции (`/v1/stream/out`, `/v1/stream/in`) и рекурсивный `chown` — распаковка идёт от root, а владельцем должен стать клиент.

Приёмник делает всё остальное: создаёт аккаунт (всегда с ролью `user`) с перенесённым хешем пароля панели и unix-пароля, разворачивает домашний каталог, поднимает базы вместе с их аккаунтами (`SHOW CREATE USER` → `CREATE USER ... AS '<хеш>'`), создаёт сайты, cron, app-сервисы (выключенными), экземпляры Valkey (пустыми; сайт оставляет PHP-сессии в Valkey, только если здесь Valkey установлен и у его ветки PHP включено расширение redis, иначе переходит на файлы), почтовые домены с ключами DKIM, ящики с их `{BLF-CRYPT}` и алиасы, ставит перевезённые сертификаты и применяет конфигурацию.

Свои директивы nginx сайтов с другой MonoPanel не применяются: здесь их пишет только администратор, а работают они с правами веб-сервера. Они ложатся рядом с `custom.conf` сайта файлом `sites/<домен>.d/custom.conf.migrated`, который server-блок не подключает, и разбор говорит об этом заранее (в Web UI их показывает кнопка «свой nginx» у сайта). Проверив, их применяют командой `mp site nginx <домен> --set <файл>` или вставляют на вкладке «nginx» сайта.

**Посылка — это ввод, а не конфигурация.** Источник — другой сервер: FASTPANEL или BitrixVM, прочитанные по ssh, или MonoPanel, у которой свой администратор. Поэтому каждое значение посылки приёмник проверяет по тем же правилам, что API применяет к тому же значению, набранному человеком в Web UI, `mp` или TUI. Что правило нарушает, разбор показывает в «что мешает», и перенос не запустится. Задача проверяет посылку ещё раз — источник мог измениться после разбора, — такие записи не берёт, называет каждую в журнале и завершается ошибкой: молча ничего не пропадает.

- *Аккаунт.* Логин годится для unix-учётки и не совпадает ни с системной учёткой или группой (root, www-data, mysql, vmail, postfix и другие службы, которые ставит панель), ни с `scheduler` и `system`, ни с unix-пользователем или группой, которые на сервере уже есть. MonoPanel, ответившая не тем аккаунтом, что просили, получает отказ. Хеш пароля панели — argon2id, unix-пароля — crypt из shadow (yescrypt, SHA-512, SHA-256, bcrypt), и оба с обычной ценой вычисления: хеш, который просит гигабайты памяти, клал бы вход на каждой попытке. Другой хеш не переезжает, пароль задают заново (`mp user set <логин> --generate`). Аккаунт с доступом по SSH приезжает с ним же, и разбор об этом предупреждает.
- *Сайты* проходят правила создания сайта. Имя самой панели или её почтового сервера и домен, который здесь уже обслуживается, не принимаются; адреса старого сервера заменяются адресами этого.
- *Базы.* Имя — из `a-z`, цифр и `_`, не системная схема MySQL, не занятое здесь и не под префиксом `<логин>_` другого аккаунта. Переезжают только локальные аккаунты MySQL (localhost, 127.0.0.1, ::1), остальные пропускаются с предупреждением. `CREATE USER` источника не выполняется как есть: из него берутся плагин (`mysql_native_password` или `caching_sha2_password`) и хеш, а запрос собирается заново. Дамп загружается клиентом `mysql` с `--binary-mode` и `--local-infile=0` от имени аккаунта самой базы, у которого нет прав за её пределами; `DEFINER` в дампе заменяется на `CURRENT_USER`.
- *Cron* — правила `mp cron add`: одна строка без управляющих символов и расписание, которое понимает cron. Пути старого домашнего каталога в командах заменяются новым.
- *App-сервисы* — правила API: команда с абсолютным путём, рабочий каталог и `EnvironmentFile` внутри домашнего каталога, значения, которые не добавят строк в юнит.
- *Почта.* Домен — по правилам имён DNS, не имя самой панели и не имя, которое есть или лежит под сайтом или почтовым доменом другого аккаунта; селектор DKIM — одна метка, закрытый ключ DKIM соответствует открытому; адрес ящика собирается из локальной части и домена, хеш пароля — только `{BLF-CRYPT}`, алиас не может занять адрес ящика. При записи карт — те же проверки, что для заведённых в панели ([06](06-mail.md#11-границы)).
- *Сертификаты* ставятся только для сайтов, которые приезжают: ключ подходит, срок не истёк, имена читаются из самого сертификата, а не со слов источника. Сертификат с именем сайта другого аккаунта или самой панели не ставится; не от Let's Encrypt — ставится загруженным, без автопродления.
- *Файлы.* Поток tar переписывается по пути к `tar -x`: остаются обычные файлы, каталоги, символьные и жёсткие ссылки внутри дерева, без setuid и setgid, без файлов устройств и FIFO; в почтовом хранилище символьная ссылка не выходит за свой каталог. «Дыры» разреженных файлов разворачиваются не больше чем в 4 ГБ нулей на архив.
- Заметки и имена источника теряют управляющие символы, прежде чем попасть на экран или в журнал задачи; ответ MonoPanel-источника — не больше 64 МБ.

Проверено на двух настоящих серверах [площадки](08-testbed.md) 2026-09-09 (Ubuntu 24.04 → Debian 13, `make testbed-migrate`): аккаунт с сайтом, PHP-файлом, базой и cron приехал целиком — вход в панель и SFTP старыми паролями, сайт отвечает тем же файлом, строки и пароль пользователя MySQL на месте, задание в crontab. Первый живой прогон поймал ошибку, которую двухпанельный тест с поддельным агентом увидеть не мог: хеш `caching_sha2_password` содержит бинарную соль, и через текстовый вывод клиента `SHOW CREATE USER` он приезжал испорченным (`ERROR 1827`). Теперь источник просит сервер печатать хеш hex-литералом (`print_identified_with_as_hex`), и приёмник воспроизводит его без потерь.

Разные семейства ОС переезду не мешают: Debian 12 → AlmaLinux 10 прошёл те же проверки. Всю конфигурацию приёмник рендерит заново под свои пути и имена сервисов, а в разборе остаётся предупреждение: свои директивы nginx и команды cron могут ссылаться на пути старой ОС.

Чего пока нет: досинхронизации (`resync`), завершения переезда (`finish`), областей `site:` и `server:` и пакета-файла.

## 6. Чужие панели и серверы без панели

Формат один — тот же `MigrationBundle`, что отдаёт MonoPanel, — собирают его разные адаптеры. Дальше импорт общий: разбор конфликтов, аккаунт, потоки, сайты, сертификаты, cron работают одинаково для любого источника.

| Адаптер | Откуда берёт | Состояние |
|---|---|---|
| `monopanel` | API исходной панели по токену переезда | работает |
| `bitrixvm` | «1С-Битрикс: Веб-окружение» (bitrix-env 7–9): nginx-конфиги `/etc/nginx/bx/site_enabled`, `bitrix/.settings.php` и `dbconn.php` каждого сайта, `/root/.my.cnf` | работает |
| `fastpanel` | FASTPANEL 2: её SQLite `fastpanel2.db` (аккаунты, сайты, бэкенды, базы, сертификаты), crontab пользователя, `/var/www/httpd-cert` | работает |
| `plain` | сканирует vhosts nginx/apache, `/var/www`, список баз MySQL и предлагает сопоставление — сервер без панели | план |
| `ispmanager`, `cpanel` | позже; у cPanel свой формат `cpmove`, его проще принять как есть | план |

Чужие панели не умеют отдавать аккаунт по API, поэтому адаптеры читают старый сервер **по ssh от root** — паролем или приватным ключом (`--key`, по умолчанию первый найденный из `~/.ssh/id_ed25519`, `id_rsa` и `id_ecdsa` того, кто запускает `mp`; в Web UI ключ вставляют на странице «Перенос»). Всё, что уходит на источник, — `cat`, `ls`, `test`, `getent`, `mysql -e SELECT`, `tar -c`, `mysqldump`: на нём ничего не меняется.

Ключ хоста источника не с чем сверить, поэтому его отпечаток печатается в разборе — сравните с тем, что показывает старый сервер. Пароль ssh в задаче лежит зашифрованным ключом панели и стирается вместе с ней. Каждая команда — отдельная ssh-сессия, и если у старого сервера сломан DNS (мёртвый nameserver в `resolv.conf`), sshd тратит по 5 секунд на обратные запросы на каждую из них: разбор тогда идёт минуты, а не секунды — почините `resolv.conf` на источнике.

```
mp migrate plan --from bitrixvm  --source root@old.example.com --domain shop.example.com
mp migrate run  --from bitrixvm  --source root@old.example.com --domain shop.example.com [--as shop]
mp migrate plan --from fastpanel --source root@old.example.com                 # перечислит аккаунты
mp migrate run  --from fastpanel --source root@old.example.com --scope user:shop [--password-stdin]
```

**BitrixVM.** Unix-пользователь там один — `bitrix`, поэтому область всегда `user:bitrix` (другой логин здесь — `--as`).

- *Сайты.* Основной живёт в `/home/bitrix/www` под `server_name _`, имя ему даёт `--domain`; дополнительные — в `/home/bitrix/ext_www/<домен>`, у них имена есть. Сайты типа *link* делят ядро основного через абсолютные симлинки: `tar` на источнике переписывает их цели под новый домашний каталог (`--transform` только для целей симлинков). Значение `root` в конфиге nginx bitrix-env пишет в кавычках — они снимаются; сервер с `root` вне `/home/bitrix` не переносится, и разбор это говорит.
- *Пути.* После распаковки `/home/bitrix/…` → `/var/www/<логин>/…` правится в `dbconn.php`, `.settings*.php` и командах cron — так `BX_TEMPORARY_FILES_DIRECTORY` из bitrix-env продолжает работать. Собственные файлы сайтов, где зашит `/home/bitrix/` (скрипты экспорта, `bitrix/php_interface`, `local/`; ядро `bitrix/` и `upload/` не просматриваются), разбор находит `grep` на источнике и перечисляет, а после переноса переписывает так же — не больше 200 файлов на сайт.
- *База.* Реквизиты берутся из `.settings.php`: пароль известен открытым текстом, и аккаунт MySQL заводится здесь заново `IDENTIFIED WITH … BY` с явно названным плагином — `mysql_native_password`, если среди сайтов есть PHP ниже 7.4 (разбор предупреждает), иначе `caching_sha2_password`.
- *Cron.* Кроме crontab пользователя `bitrix` читается crontab root: на BitrixVM всё делают от root, и задания с путями `/home/bitrix/` (экспорт, обмен) переезжают в crontab аккаунта с пометкой «from root's crontab»; остальные задания root не переносятся, разбор их перечисляет. `/usr/bin/php` в командах становится `php` — это `~/data/bin/php`, ветка сайтов, а не PHP дистрибутива по умолчанию. Задание, которое запускает что-то из `/tmp`, `/var/tmp`, `/dev/shm` или скачивает скрипт прямо в shell, приезжает выключенным с пометкой: так выглядят закладки после взлома. `mp migrate plan` печатает все переносимые задания.
- *Кеш и окружение.* Если в `.settings.php` или `dbconn.php` кеш не файловый (memcache, кластерный `CPHPCacheMemcacheCluster`), разбор об этом пишет: неработающий кеш заставляет шаблоны пересчитывать всё на каждом хите и занимает все процессы php-fpm. Сам кеш (`bitrix/cache`, `managed_cache`, `stack_cache`), push-сервер, memcached и msmtp окружения не переезжают — заметки об этом есть в разборе.
- *Пароли.* Unix-пароль едет хешем; пароль для входа в панель аккаунту не задаётся — `mp user set bitrix --generate`.

**FASTPANEL.** Область — `user:<логин панели>`; без `--scope` разбор перечисляет, кто есть.

- *Сайты.* Раскладка совпадает с нашей (`/var/www/<логин>/data/www/<домен>`), едет `data/www` целиком; `index_dir` FASTPANEL (абсолютный docroot) становится относительным `docroot`. Бэкенд `php_fpm` — наш `fpm`, `fcgi` и `mod_php` — `apache`, версия PHP из `handler_version`. Сгенерированный панелью конфиг nginx не переносится (он весь про старый сервер), но его allow-список с `deny all` превращается в `allow_from`; о сайтах с `manual_changes` разбор напоминает.
- *Базы.* Пароли FASTPANEL хранит зашифрованными, поэтому едут хеши из `SHOW CREATE USER`; старый `mysql_native_password` при необходимости включается здесь. Хеш `caching_sha2_password` в `mysql_native_password` не переделать: если такой аккаунт приезжает к сайту на PHP ниже 7.4, задача переноса пишет, какой `ALTER USER` выполнить.
- *Сертификаты.* Загруженные лежат в её базе текстом, Let's Encrypt — файлами в `/var/www/httpd-cert`; самоподписанные и просроченные остаются на месте.
- *Почта и пароли.* Почта FASTPANEL не переносится (разбор говорит, сколько ящиков). Пароль веб-панели там — unix-пароль (PAM); он приезжает хешем и работает для SFTP, а пароль для входа в MonoPanel задают заново.

Старые серверы Битрикса чаще всего живут на bitrix-env 7 и CentOS 7 (обе ветки давно EOL): адаптер их тоже читает — раскладка та же, а дамп MySQL 5.7 по пути очищается от `NO_AUTO_CREATE_USER` в `sql_mode`, который MySQL 8 не принимает.

Проверено на площадке 2026-09-12 (`scripts/testbed/sources.sh`): BitrixVM 9.0 на AlmaLinux 9 → Debian 13 (сайт с ядром 1 ГБ, база `sitemanager`, пути переписаны, вход в базу и unix-хеш прежние), bitrix-env 7 на CentOS 7 с MySQL 5.7 → Ubuntu 24.04 и FASTPANEL 1.11 на Debian 12 → Rocky Linux 9 (WordPress с настоящим сертификатом Let's Encrypt — сразу по HTTPS, сайт с docroot `public/`, алиасом и allow-списком, база с прежним хешем, два задания cron с `data/bin/php`).

## 7. Границы

- Поток, а не «собрать в памяти»: домашние каталоги бывают в десятки гигабайт, докачка обязательна.
- Разные версии PHP и MySQL на источнике и цели — нормальная ситуация; ловит dry-run, ветку PHP панель предлагает поставить сама.
- Почтовые Maildir'ы переносятся как файлы; синхронизация почты «на живую» (`doveadm sync`, imapsync) — отдельный шаг, не в первой версии.
- Токен переезда — отдельная область: только чтение, только экспорт, с TTL, видимый в audit обеих панелей; выдаёт его и пользуется им только администратор.
- Перенос между разными семействами ОС (Debian → EL) разрешён: пути PHP и имена сервисов разные, поэтому конфигурацию приёмник рендерит заново, а dry-run предупреждает, что свои директивы nginx и команды cron могут ссылаться на пути старой ОС.
